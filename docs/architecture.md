# Casse-Robot — architecture

This document describes the project for those who contribute to it: the commands, the architecture, the technical choices, the recipes for adding a game element, and the roadmap. The contribution guide is [`CONTRIBUTING.md`](../CONTRIBUTING.md), the map authors' guide is [`maps.md`](maps.md).

Prototype of a multiplayer game of destructible block robots (inspired by Robocraft), in the browser. The documentation is in English; the code comments are in French. The long-term goal is a clean multiplayer game: the architecture must stay tidy (see "Architecture rules").

## Commands

Node.js 20 or newer. Strict TypeScript, Vite, Vitest.

- `npm run dev`: dev server (http://localhost:5173, opens the browser). It does not watch the built bundles, and only looks for its dependencies from `index.html` (vite.config.ts): a working copy of the repository stored inside the folder (its tsconfig files) made it empty its cache in the middle of a match. If the arena is no longer drawn after a dependency re-optimization (only the sky, "'<' : syntax error" in the console, a shader that is the HTML page), the browser is mixing old Babylon chunks, kept in its permanent cache, with new ones: two copies of the shader store (`ShaderStore`). Clear the page's cache (developer tools open, right-click on "Reload": "Empty Cache and Hard Reload").
- `npm run check`: type checking + tests. **Run it after every change.** Continuous integration (`.github/workflows/check.yml`) runs it on every push and every *pull request*, along with `npm run map:check`. The code is licensed under AGPL-3.0-or-later (`LICENSE`, `package.json`); the contributors' guide is `CONTRIBUTING.md`. The sounds and music in `public/sounds/` (ElevenLabs) are not under this license: their terms forbid distributing them on their own, outside the game.
- `npm run typecheck`: three passes, `tsconfig.json` (the whole project, the `tools/` scripts included, except `src/server/main.ts`), `src/shared/tsconfig.json` (shared code **without the DOM**, to guarantee that it runs on the server) and `src/server/tsconfig.json` (server, with Node's types).
- `npm run server`: builds the game server (`vite build --ssr` into `dist-server/`) and starts it on port 8787 (`PORT` to change it); it keeps the players' progression in `casse-robot-progress.json` (`PROGRESS_FILE` to change it, ignored by git), and also serves the compiled game page (`dist/`, `CLIENT_DIR` to change it; its status at `/status`). It loads the community maps from the `maps/` folder (`MAPS_DIR` to change it; `MAPS_ONLY=1`: only those in the rotation; an invalid map is left out, and the log says why). The client connects to it through the "Multiplayer" menu (`defaultServer`, client/net/netClient.ts: in development or under `vite preview`, `ws://<machine de la page>:8787` (the page's host); otherwise the page comes from the game server, which is therefore at the same address, over `wss` if the page is on https).
- `npm run share` (`tools/share.mjs`): share the game over the Internet. Builds the page and the server (`--no-build` to skip that), starts the server, then a Cloudflare quick tunnel (`cloudflared tunnel --url`, no account needed; an `https://….trycloudflare.com` link that changes on every launch) and prints the link to send, along with the address on the local network (that of the network card that goes out to the Internet, found with a connected UDP socket that sends nothing). A single address for the page and the match: the tunnel lets the WebSocket through. The server serves the page compressed (gzip, kept in memory per file: the ~5.8 MB bundle arrives as ~2.2 MB), and the files in `assets/` with permanent caching (`staticFiles.ts`, pure logic, tested by `tests/staticFiles.test.ts`: nothing outside the client folder). Measured through a tunnel: page loaded in ~2.5 s, WebSocket connection in ~0.3 s, ~19 frames per second and ~180 KB/s per player.
- `npm test` (once) or `npm run test:watch`; a single file: `npx vitest run tests/simulation.test.ts`; a single test: `npx vitest run -t "Grue"`.
- `npm run bench`: cost of a simulation step during 20 s of combat with 12 robots (`BATTLE_ROSTER`), broken down by stage of `Simulation.step` (measured by `sim.profile`; `sim.measure(nom, travail)` times a stage, and a sub-stage such as "ia › conduite" (AI › driving) is not added to the total). About 3.2 ms, of which 1 ms of physics, 0.5 ms of wheels and 1.1 ms of AI. The same test (`tests/perf.test.ts`) runs in `npm test` with a generous budget (there it shares the machine with the other test files).
- `npm run battle`: eight battles between AIs (Battle mode, headless) and a balance report: match durations, kill causes (`botKilled.cause`), average cost of a step, share of the time ground robots are stuck (in an unsticking maneuver, or blocked for more than a second), and per robot: kills, deaths, lifetime, time flipped over or stunned, causes of its deaths. At the Depot; another arena via `BATTLE_ARENA` (`BATTLE_ARENA=canyon npm run battle`), or a community map from `maps/` by its file name (`BATTLE_ARENA=val-du-lac npm run battle`). `npm test` plays two short ones (`tests/battle.test.ts`) to check that a real match runs without errors: this is how accesses to already-freed Rapier bodies (`RuntimeError: unreachable`) get caught.
- `MELEE_REPORT=1 npx vitest run tests/melee.test.ts --silent=false`: the measurements from the melee weapon tests (reaction, precession, imbalance, ricochet, hammer); with `MELEE_BATTLE=1` as well: six battles where each team has its Reaper and its Pounder, their per-robot report (kills, deaths, time flipped over, hits) and the cost of the "contact" stage (the benchmark, `BATTLE_ROSTER`, has no melee weapon). Likewise for the energy weapons: `ENERGY_REPORT=1 npx vitest run tests/meleeEnergy.test.ts --silent=false` (blade, whip, lance, field), and `ENERGY_BATTLE=1` (six battles with a Duelist and an Urchin per team; more than half an hour on a loaded machine). Likewise for the biting weapons: `MELEE_REPORT=1 npx vitest run tests/meleeBite.test.ts --silent=false` (equilibrium spin, damage depending on spin, breach, grip, ricochet, drill, roll, network), and `MELEE_BATTLE=1` (the Sawyer and the Borer on each side, and the time they spend biting). And for the mechanical strikes: `MELEE_REPORT=1 npx vitest run tests/meleeMechanics.test.ts --silent=false` (flipper, flail, jaw), `MELEE_BATTLE=1` (six battles with a Catapult, a Crusher and a Thresher per team; `MELEE_SEEDS=1,2,3`: those particular seeds, to split them across several processes). For the spinners and the cutting propeller: `MELEE_REPORT=1 npx vitest run tests/spinners.test.ts --silent=false`, and `SPINNER_BATTLE=1` (six battles with a Tumbler, a Drummer and a Whirlwind per team; three minutes on an idle machine, nearly an hour on a loaded one).
- `npm run build`: type checking then production build into `dist/`; `npm run preview` to test it.
- `npm run map:check -- [cartes…]`: checks community maps the same way as the game and the server (without a file: those in `maps/`; exit code 1 if one of them is not playable; `--lang en`); `npm run map:terrain -- <image.png|relief.r16> --cells N --step S --low L --high H [--mountains DEPUIS,HAUTEUR] [--into carte]` imports a terrain into a map (`DEPUIS,HAUTEUR`: from, height; `carte`: map); `npm run map:example` regenerates the example map (`maps/val-du-lac.casse-map.json` and its source terrain `tools/maps/val-du-lac.png`). The tool (`tools/maps/cli.ts`) is compiled by `vite build --ssr` into `dist-tools/` (ignored by git). `MAP_PERF=1 npx vitest run tests/communityMaps.test.ts --silent=false`: the cost of a combat step on each map in `maps/`, compared with the Depot and the Valley. The authors' guide: `docs/maps.md`.
- `npm run sounds`: prepares the generated sounds (`tools/sounds/build.mjs`, with ffmpeg): for each sound in `tools/sounds/catalog.json`, its kept variants (`tools/sounds/raw/<son>/`, ignored by git) become `public/sounds/<son>-<n>.ogg` (see "Sound"). Redoing everything takes more than ten minutes: `npm run sounds -- <son> [<son>…]` prepares only those (the encoding is reproducible, `bitexact`: a sound rebuilt without changes gives the same file).
- In the browser console, `__casse` gives access to the match: `sim(n)` advances by `n` steps of 1/60 s, `pause(true)` freezes the AI, `spawnWave(["tank", "heli"])` spawns those robots, `bots`, `world`, `camera`, `scene`, `applyDamage(point, dir, WEAPONS.cannon)`, `fireAt(x, y)` (without an ammo limit), `game` (the whole `ArenaGame`), `garage` (the `Garage`: `garage.load({ name, color, design })` opens a design in it), `presets` (the preset robots, `PRESET_BOTS`), `maps` and `testMap(carte)` (the community maps) and `editor` (the map editor: `editor.map`, `editor.history`, `editor.lastRebuild` and `editor.lastCheck` in ms).

## Technical choices already made

- **Babylon.js** for rendering, **Rapier** (`@dimforge/rapier3d-compat`) for physics. Rapier was preferred over Havok because it also runs in Node (server), it is deterministic and it allows snapshot/restore of the world.
- **Babylon imported piece by piece:** the client imports `* as B from "./babylon"` (`client/babylon.ts`, which re-exports only the classes in use and registers the side effects: ray casting, shadows, instances), never `@babylonjs/core` directly (checked by `tests/architecture.test.ts`). An extra class gets added there. The bundle went from 11.5 to 5.8 MB, of which 4.2 MB is Rapier.
- Versions pinned exactly (Babylon 9.28, Rapier 0.21): Rapier's API changes from one version to the next (`castRay`, `timeOfImpact`, joints…). Check the `.d.ts` files before upgrading. Rapier's generic joints have neither motors nor limits in JS: a joint with two degrees of freedom is made with two joints and an intermediate body.
- **Authoritative-server multiplayer (done, first version):** the clients send only their inputs (`PlayerInput`), the Node server simulates with Rapier at a fixed step and sends 20 frames per second (events + binary snapshot), the clients replay 100 ms behind, interpolating. Transport: WebSocket (`ws`). No client-side prediction or snapshot compression yet.

### Languages (i18n)

The game speaks French and English; the player chooses in the settings (Profile tab, `Settings.language`, by default the browser's language: `detectLocale(navigator.languages)`, English as a fallback), and the change applies live. Only what the player sees is translated: code comments and messages for developers (console, errors, server logs, names of the profiler steps) stay in French; the documentation is in English.

- **Message catalogs (`client/i18n/locales/<langue>/`):** one file per part of the game (zone), the same in every language: `common` (units, teams, buttons), `catalog` (names of blocks, weapons, melee weapons, wheels, props, damage types), `world` (arenas, map places, game modes, AI modes, kill causes), `bots` (preset robots), `design` (design issues, clearance), `net` (server refusals, credits), `picker` (robot picker), `keys` (actions, keys, gamepad, controls help), `menu` (screens and settings), `hud` (HUD and page), `garage`, `parts` (part info sheets), `maps` (community maps: their screen, `MapIssue`, terrain import errors). Each key starts with the name of its section (`menu.pause.resume`, `block.armorHeavy`) and is in only one file (`tests/i18n.test.ts` checks this). **French is the source language**: the `MessageKey` type is the set of its keys; each file of another language is checked against the French one (`as const satisfies ZoneOf<typeof fr>`: a missing or extra key is flagged right there), then the whole language in locales/index.ts (`complete`: extra keys, parameters that differ from the French ones; the offending keys show up in the TypeScript error). Each message is written as a single string: a concatenation "…" + "…" would lose the literal type, and with it the parameter check (`WidenedKeys`, rejected for French by `source` and for the other languages by `complete`). A section that is exhaustive over the identifiers of a game catalog is written `...section("block", { armor: "Blindage", … } as const satisfies Record<BlockType, Message>)` (locales/section.ts): a block type without a name is an error, like an exhaustive `Record` in the renderer; an optional section (not every action has a detail): `Partial<Record<…>>` and `tMaybe`.
- **`t(clé, paramètres)` (i18n.ts):** TypeScript checks the key and the parameters against the French message (a missing or extra parameter: an error). Parameters `{nom}`; a number passed as is gets written the language's way (at most two decimals, digit grouping above 9,999: a port stays "8787"). **Plurals:** a message is a text or its forms `{ one: "{n} pièce", other: "{n} pièces" }` (and `zero`, `two`, `few`, `many` for the languages that have them), chosen by the `n` parameter according to `Intl.PluralRules` (0 and 1 are singular in French, only 1 in English); a sentence with two counts is made of two messages. A text that agrees with a thing ("les mâchoires entreraient", "the jaws would go in") receives `n` = 2 if that thing is made of several parts (`Zone.plural`). An optional key built on the fly: `tMaybe("actionDetail.boost")`. `translate(langue, clé, …)` for a given language (tests).
- **Numbers (`format.ts`):** `num(x, décimales)` (at most, without useless zeros), `fixed` (exactly: the instruments that change every frame), `pct` ("85 %", "85%"), `signed` ("−1,5", a true minus sign), with `Intl` formats cached per language and per precision; `measure(x, unité, décimales)` (i18n.ts) for a measurement (`unit.<id>` in `common`: the symbol and its position, a non-breaking space: "0,5 m", "1200 tr/min", "1200 rpm", "40 PS", "40 HP"). No more `.replace(".", ",")`. `fold` (search ignoring accents and case) and `compareText` (the language's alphabetical order): the searches in the garage and the robot picker work on the displayed text, in the displayed language.
- **Fallback language:** a language that is being translated may have only some of the keys (`LocaleInfo.messages` is partial): what is missing is displayed in English, then in French; in development, each missing translation or absent parameter is reported once in the console (`report`). The shipped languages are complete (TypeScript, and `tests/i18n.test.ts`).
- **What comes from shared code and the server (`names.ts`):** `src/shared` (which also runs on the server) has no displayed text: the catalogs have only identifiers (a block no longer has a `label`, a preset robot no longer has a `name` or a `trait`, an arena no longer has a `name` or a `description`, a map place has a `PlaceId`), and what shared code tells the player is a code with its parameters, which the client translates: `validateDesign` returns `DesignIssue`s (`designIssueText`), clearance returns `ZonePart`s and `ConflictReason`s (`zonePartName`, `conflictText`, `conflictLine`), `matchReward` returns `RewardLine`s (`rewardLineText`), the server `Refusal`s (`refusalText`; `PROTOCOL_VERSION` 25), map validation `MapIssue`s (`mapIssueText`), and the list of unlocked parts comes as `Part`s. `botName(profile)`: the name a person gave (garage robot, player in multiplayer, `BotProfile.name`, optional) or that of the preset robot in the displayed language (`bot.<id>`); `botTrait`. A player without a name is called "Robot 3" (the server writes no text to translate). Zone letters (A, B, C) are not translated. What a person wrote for a community map (its name, its description, its named places) is displayed as is, or in the displayed language if the author wrote it in that language (`authored`): `arenaName` (an identifier, or the arena itself: a map received from a server is known only to the replica), `arenaInfo`, `placeLabel`.
- **The page (`dom.ts`):** an element of index.html carries the key of its text (`data-i18n`) or of its attributes (`data-i18n-title`, `data-i18n-aria-label`, `data-i18n-placeholder`); a text mixed with a child element (a key `<kbd data-key-action>`) is wrapped in a `<span data-i18n>`; the game's name carries `translate="no"`. `applyDom` at startup (main.ts: the saved language from the very first loading screen) and on every language change, along with the page's `lang`.
- **Live switching:** `setLocale` (state.ts) notifies those who listen (`onLocaleChange`): the page (`applyDom`), the HUD (weapon bar, key help, scoreboard, title, the robots' 3D labels, minimap), the garage. The settings screen redraws itself (`MenuView.id`: the same screen keeps its focus); the other screens are built when they open, in the language of the moment. Lines already shown in the kill feed stay in the old language (they fade out within a few seconds).
- **Translation choices (English):** American English (armor, color, gray), sentence case for labels ("Main menu"), a concise game tone, the informal French "tu" → "you". The names of the preset robots and arenas are translated: they are common nouns that say what the robot or the place is (Scarabée → Scarab, Bélier → Ram, Vallée → Valley, Île volcanique → Volcanic Island), and the code identifiers are already those words; "Casse-Robot" stays the game's name. Lexicon kept consistent from one screen to another: bloc → block; pièce → part; plan → design; blindage → armor; points de structure (PS) → hit points (HP); dégâts → damage; destruction (score, fil) → kill; partie → match; arme de contact → melee weapon; tourelle → turret; viseur → scope; réticule → crosshair; verrouillage → lock-on; toupie → spinner; régime → spin; leurres → flares; IEM → EMP; paralysé → stunned; réacteur → thruster; propulseur → booster; turboréacteur → turbojet; rotor orientable → tilt rotor; hélice → propeller; patin anti-gravité → hover pad; gouverne → control surface; roue directrice → steered wheel; roulette → caster; chenille → track; galet → roller; crédits → credits; débloquer → unlock; se saborder → self-destruct; réapparition → respawn; caméra libre → free camera; tableau → scoreboard; fil des destructions → kill feed; pilote automatique → autopilot; gaz → throttle; palonnier → rudder. Keys that type a character keep the name from the player's keyboard layout (`codeLabel`); the others have their own name in each language ("Espace", "Space").
- **Tests:** `tests/i18n.test.ts` (all languages have all the keys and the same parameters, one key per file, plurals and numbers in both languages, default language and setting, live switching, page keys); `tests/i18nSource.test.ts` rejects French hard-coded in the code and the page (heuristic in `tests/frenchText.ts`: accented letters, « » quotes, function words, common interface words; excluding comments, import paths, console and error messages, shaders); a string that is not displayed text but looks like French is marked `// i18n-ignore` on its line. `tests/keyMessages.test.ts`: no message names a key hard-coded (a `{key}` parameter, filled in from the chosen keys: see "Keys and gamepad").

### Simulation

- **Simulation → rendering contract:** the `Simulation` emits `SimEvent`s (`shared/sim/events.ts`) **synchronously**, at the exact moment the structure changes (`partAdded`, `blockAttached`, `blockDestroyed`, `wheelRemoved`, `debrisAdded`, `shot`, `fireStarted`, `smokeAdded`, `botKilled`…). `WorldView` creates or destroys its meshes only from these events, then `sync()` copies the body poses every frame. The blocks of a part are grouped by appearance (type, color) into batches of **thin instances** (`thinInstanceAdd`) parented to the part's node, each with **its own copy of the geometry** (Babylon stores the thin instances' color buffer on the geometry: batches sharing it would overwrite each other, and on a real GPU some would no longer be drawn): one matrix per batch per frame, and the instances only go back to the GPU when a block changes (removal by swapping with the last one, "dirty" batches flushed in `sync`). What follows a block (turret head, flame, fire) is attached to its frame (`anchor`), created on demand. **Wings and control surfaces** are not in the batches: a part's wings (per type) are a single piece, and each row of control surfaces another one, which pivots as a unit around its hinge (`SurfacePiece`, `buildSurfaces`); their merged cells (`mergeSegments`, render/surfaceModels.ts) each have a profile according to what touches them (`surfaceSides`, shared/robot/surfaces.ts: rounded leading edge, tapered trailing edge, wingtip rounded only at the ends; nothing is drawn between two cells that continue into each other, two wings of the same design or two cells of a row with the same profile; a flat face closes a side against a block, a control surface that moves separately or a cell with another profile, `CLOSED_*`: a hidden face flush with the skin striped it with a dotted line, the depth buffer hesitating between them), and their wear is a vertex color; their vertices are rounded to a hundredth of a millimeter, so that two neighboring cells have exactly the same edge. A change in the robot's structure (`blockAttached`, `blockDestroyed`, `blockRebuilt`) has them rebuilt at the start of the next frame, only those whose key (part, blocks and profiles, hinge, carrier row) has changed; `partRemoved` takes its own with it. A row of control surfaces just behind another (the flap of an aileron two rows deep in chord) is attached to it and only turns by the difference between their deflections. In the garage and in previews, one instance per cell, from the source of its profile (`Assets.surfaceSource`, from `designSurfaceSides`); a lone cell (debris, thumbnail, part to place) has all four sides shaped (`SIDES_ALONE`). A Plane: 7 pieces (before: one batch and 19 control-surface instances); rebuilding all of its pieces costs ~4 ms, checking that none has changed ~0.2 ms, pivoting the control surfaces of three planes ~0.01 ms (Chrome without GPU). Later, the server will send these same events. Any new structural change must emit its event; the `expectEventsInSync` test in `tests/simulation.test.ts` checks this.
- **Solver:** `SOLVER_ITERATIONS` = 4 (Rapier's default value; 8 cost 30% more physics without changing anything in the tests or the battles). The AI's avoidance rays are recast every 50 ms.
- **Step (`Simulation.step`):** detection → AI (or player commands) of each robot, and energy balance → air (lift, gusts) → wheels (`stepWheels`) → physics (`world.step`, which fills the contact force queue, then wheel placement: `placeWheels`) → collisions → melee weapons (`updateMelee`, "contact" stage) → projectiles → engine flame jets (`updateScorch`, "jets" stage) → fires, smoke, repairs → props, debris → match. Each stage is timed when `sim.profile` is active.
- **Arenas (`arena/layout.ts`):** `ARENAS` (Depot, Fortress, Trenches, Construction Site, Valley, Canyon, Volcanic Island, City, City by Night, Harbor) describes each arena as data: its dimensions (`ArenaBounds`: walls or foot of the mountains `half`, area where the AI roams `roam`, spawn lines `spawnLine`/`spawnSpread`, aircraft circuit `circuit`; the small arenas all have `SMALL`, ±36 m), scenery boxes (`StaticBox`: wall, ramp, pillar, platform, low wall, rock, container, bridge deck `deck` and roadway `road`, both drivable), props (`PropSpot`), capture zones, and optionally a terrain (`terrain`), a water level (drawn only: you drive through it), paths (`paths`, drawn; `surface`, `PathSurface`: dirt, grass (a lawn, the short grass of an airstrip), sand, gravel road that stays visible on rock, gravel lane, ballast, pavement) and a sky (`sky`: color, fog). Further options (arena/features.ts, all optional: an arena that doesn't declare them behaves as before; fixed data, nothing in the protocol): `deepWater` (beyond this depth, the water is real: you drown in it, the AI doesn't venture into it, hover pads glide over it, `waterBelow` in robot/supports.ts), `lava` (flows and lakes, `LavaShape`, `lavaAt`), `navGrid` (the AI's nav grid, see below) or `nav` (nav graph, `NavGraph`, arena/navGraph.ts: see "Getting around scenery"), `ground` (ground palette, `GroundStyle`: ground, dirt, sand, rock, summit, basalt around the lava, cliff strata, color patches, tint of slopes (a city's embankments), of lawns, tighter pattern; without it, the Valley's), `waterColor`, `vents` (fumaroles, `Vent`) and `falls` (waterfalls, `Waterfall`), and a box look (`StaticBox.look`, `BoxLook`: sandstone, timber framing, railway track, railcar, planks, basalt, rusted steel; for rendering only). A large arena can build its terrain, scenery, props and nav graph on first read (getters, like the Canyon: ~1 s paid only by a match played there, not by the page load). Spawn lines stay clear. `sim.arena` is the current arena; `sim.loadArena(id)` replaces the static scenery and the terrain (the flat ground stays, underneath), resets the props and emits `arenaChanged` (to be done before placing the robots). Everything that used to read the scenery or the arena size (AI cover and destinations, spawns, aircraft pilot, camera) reads `sim.arena`. The client draws the scenery with `ArenaView.show`.
- **Terrain (`arena/terrain.ts`):** a square of heights at the vertices of a grid (`makeTerrain`, from a pure function; fixed noise `noise2`, without `rand`: it is data), which the physics turns into a Rapier heightfield (arena.ts, `static` group: wheels, projectiles, debris and sight see it as the ground), with `HeightFieldFlags.FIX_INTERNAL_EDGES` (without which a crate rubbing against the terrain snags on the edge between two triangles as on a step). A rock (`StaticBox` of kind `rock`) has as its collider the convex hull of the dented ball you see (`rockShape`, arena/rocks.ts, which the renderer also draws): a box let its corners stick out by more than half a meter, invisible obstacles against which the Dragster at full speed stopped dead. An invisible boundary (`bound`) closes off the Valley at the back of its mountains: not drawn, not seen by the camera, not on the map. `terrainHeight` interpolates like Rapier (each cell cut by the diagonal (ix+1, iz)–(ix, iz+1); checked by `tests/terrain.test.ts`), `rayTerrain` casts a ray on it, without physics (camera, also online). `groundLevel(arena, x, z)`: ground height; robots spawn on it (`spawnHeight`, wave.ts), flying robots and planes count their altitude above it and above the terrain ahead of them (`flightLevel`, layout.ts; `Instruments.ground`, ai/pilot.ts).
- **The Valley (`arena/valley.ts`):** the large map, ±105 m of playing field within mountains (too steep to climb); a shallow river running diagonally, spanned by a stone bridge (zone C, taken on the deck); to the northeast the village (brick houses with tiled roofs, church and bell tower, zone B), to the east the fort hill (plateau at 9.5 m, concrete rampart, blockhouse, zone A), to the west the factory (warehouses, tanks, containers, chimney, zone E), to the southwest the airfield (runway, open hangar, control tower, zone D), a sawmill and a cabin in two woods, oaks and rocks in the fields. North = +z, west = +x (right-handed frame: a robot facing north has west on its left). The places are roughly symmetric about the center. The terrain is computed: swell, flattened sites (`FLATS`), fort hill (via a maximum: a flattened site at its foot doesn't cut into it as a cliff), riverbed, mountains; slopes of 31° at most in the playing area (the flanks of the fort). The buildings are made by `house` (wall panels, roof in strips resting on their walls, diamond-shaped gables), the trees placed by a fixed draw. A combat step costs as much there as in the small arenas (~3 ms), robots get stuck there just as rarely (~7% of the time, as at the Depot), and matches last longer (2 to 4 min in Battle).
- **The Canyon (`arena/canyon.ts`):** another large map (±105 m, sandstone mountains around it, invisible boundaries at ±140 like the Valley), a red desert: a plateau at 12 m cut from east to west by a winding canyon (centerline `canyonZ`, dry bed at 2.6 m, `floorHalf`: 19 m wide, a basin to the east, a gorge to the west; sheer walls 4 m wide). You can only get down into it by trails (`Trail`: a polyline, its height along it, `graded`: a constant slope eased to flat over `EASE` m at each end, with no crease where a low robot would catch its nose; cut into the slope on one side, built up on fill on the other): four in the walls, in an X on either side of the viaduct (one goes down where the other goes up: they don't narrow the bed by facing each other), and the two ravines of the oasis. You cross it by the railway's trestle viaduct (zone C, deck `rail`, timber legs and braces), or by the natural arch (zone A) that joins the two halves of the Mesa, an elliptical mesa at 24 m that you climb by a ledge trail on each side. The railway, leveled, goes through two buttes in tunnels (a cut in the terrain, a sandstone roof `platform` 5 m above the rails); to the northeast the wooden Wild West town (saloon with a false front, general store, sheriff's office, church and bell tower, station and its platform, water tower: tank `watertank` on stilts; zone B), to the southwest the mine (headframe, winch house, crusher shed, bunkhouse, spoil heaps, mine carts, tank; zone D), to the east the oasis at the bottom of the canyon (pond, oaks, adobe ruin; zone E), cacti (`cactus`), rocks and hoodoos. North = +z, west = +x; the map is symmetric about the center (town and mine, buttes, trails; the oasis and the Mesa face each other). Terrain at 1 m per vertex (at 1.375 m, Rapier rays falling exactly on certain lines of vertices went through the heightfield: a step that is a power of two), desert tints and cliff strata (`ground`), ambience: the Fortress wind (no desert ambience recorded yet). Measurements (`BATTLE_ARENA=canyon npm run battle`): see the roadmap.
- **The Volcanic Island (`arena/island.ts`):** an island of ±116 m surrounded by the sea (`deepWater` 1.1 m: beyond that, you drown; invisible boundaries at ±172 m, far enough out for planes), dominated at the center by a volcano (crater rim at 31 m, radius 15; floor at 26 m; foot at 52 m; gullied flanks too steep to climb). Two switchback roads (`spiralRoad`: 9 m wide, 250°, an even grade based on the distance traveled, a radial end in line with a breach in the rim; embankments of `BANK` m) climb from the north and the south to the crater, where a lava lake boils (zone A, on the other side of the line between the breaches). Two flows (`LAVA`: northeast and southwest) run down from fissures at the foot of the volcano to the sea, where they smoke (steam); each is cut by a ford of solidified basalt about a dozen meters wide (`FORD_WEST`). Two gorges (floor under deep water, steep walls, a spring cascading at their head), to the northwest and southeast, are crossed on wooden bridges (decks along the z axis, connected to the terrain by their abutments). The land rises gently toward the volcano (`RISE`). Places, symmetric about the center: the fishing village (zone B, northwest; plank huts, tile or sheet-metal roofs, three huts on stilts in the shallow lagoon, connected by pontoons) and the bunkers (zone C, southeast; concrete casemates, low walls, coastal gun), the grass airstrip (zone D, southwest; open hangar, shelter, tank, windsock) and the wreck beach (zone E, northeast; a rusty freighter lying on its side, its containers, straw huts); the spawn lines are on the northern and southern beaches. The jungle: 124 palms and kapok trees (`palm`, `kapok`: a trunk that topples and burns, a crown of fronds or an umbrella canopy with buttresses), in symmetric groves and along the coast, away from paths, roads, gorges, lava and places. The terrain is computed in ~0.3 s at load time (the polylines are stored in bundles of known footprint, `Polyline`, and the flattened sites are ruled out by their footprint). Measured (`ISLAND_REPORT=1 npx vitest run tests/island.test.ts --silent=false`, and a probe on the same loaded machine): a combat step costs as much as in the Valley (8.0 vs. 8.1 ms under load, driving 1.6 vs. 1.3 ms), robots get stuck there just as much (16 vs. 16% of samples stopped while pushing, in the same match), a Battle lasts 5 to 8 minutes, a Zone Capture under 2 minutes.
- **The City (`arena/city.ts`):** a city in ruins, ±94 m of streets (`urban`), enclosed by a continuous row of gutted apartment buildings (`StaticKind` `tower`: indestructible blocks, with windows) and rubble embankments, with more towers in the haze and invisible boundaries. A large square and its monument in the center (zone C), a central avenue and boulevards (spawn lines) 160 to 180 m long; to the east an elevated expressway (deck `deck` on piers, `underpass`: you can go under it; terrain embankments at both ends, taken from their foot, `approach`; concrete abutments under its ends; zone E on the deck); to the west the station (tracks `track` at the bottom of a 3 m cutting with gentle banks, ramps down at both ends, a platform domed into the terrain under a canopy, zone A); to the northeast the park (mound, bandstand, zone B), to the southwest a ruined tower of ~32 m and a multistory parking garage (platform and two tall ramps, zone D). The map is symmetric about the center (the expressway mirrors the station). The buildings (`building`) are facade panels (`facade`, `tenement`: a 3.6 m story, windows), each resting on the one below, with a flat roof in concrete strips; some have lost their top, two city blocks are piles of rubble. Cars (`car`: dynamic; worn down, it burns for its 5 s fuse then explodes, look `car`), anchored wrecks (`wreck`), lampposts that topple (`lamppost`), bus shelters, kiosks, barricades. Surfaces (`TerrainPath.surface`: lawns, walkways, ballast, pavements) and a city palette (`ArenaLayout.ground`: flagstones and cobbles in a tight pattern, grime, earth banks on slopes, rubble above 10.5 m, lawns), gray sky and dust in suspension (`ArenaSky.dust`, `dustFx`). The AI's planes fly above the tower (`airFloor` 34), its flying robots above the rooftops (`hoverFloor` 14). The ambience is the Trenches' (wind, distant cannon fire), for lack of its own. About 535 props; a combat step costs as much there as in the Valley.
- **The Harbor (`arena/port.ts`):** a large map of quays (±100 m) by the sea, to the east; low hills to the north, south and west, invisible boundaries at ±200 m (at ±135, planes drifting away on patrol crashed into them). Symmetric about the east-west axis (z → -z). In the middle, the basin where a freighter is moored (zone C on its deck, at 7.2 m, level with the top of its gangways: a platform in the water, reached by two gangways 7 m wide at 7.6°, one on each side; containers at the bow, hatch cover, superstructure and funnel at the stern), a channel spanned by a swing bridge (a deck between two lattice girders), a dock basin at the end (a barge, two tower cranes). On each side: two container gantry cranes (front legs against the parapet), a container terminal (stacks of one to three, aisles of 9 to 10 m, zone B or D in the middle, one stack you can climb by a ramp), two warehouses you can drive through (`HouseSpec.through`: the opening is repeated in the back panel), an oil depot (zone A or E between two rows of tightly packed tanks, which blow up in a chain), the railway (railcars on one track, well spaced); to the west the harbor office, three silos (round boxes, `StaticBox.round`: a cylinder for physics and rendering) and their gallery; to the east the fishermen's low quay (1.5 m lower, behind a retaining wall with a parapet, two ramps) and the lighthouse jetties. Quays at 6 m, water at 3 m, bottom at 0.2 m (`deepWater` 1.5: you drown in the basin, the dock basin, the sea, sim/hazards.ts): the water's edges fall on terrain vertices and a quay wall (`road`, look `quay`) hides the terrain slope; parapets (low walls for the AI) line the water, except at the foot of the gangways and at the root of the jetties. Roads as asphalt paths, rails (`track`) flush with the quay. The AI uses the nav grid (`navGrid`, 2 m cells) and goes around warehouses and containers as in a city (`urban`). Aircraft floor altitude: 28 m (the gantry booms pass 25 m above the water). Ambience: the Depot's, until it gets its own.
- **AI nav grid (`arena/navgrid.ts`, `ArenaLayout.navGrid`):** the arena in cells (2.5 m on the island), passable or not according to the slope (at the center of the cell and halfway to its neighbors: a cell at the foot of a wall is closed), lava (with a margin) and deep water; a deck connected to the ground at both ends (a bridge, `bridgeDecks`) is passable, even above a gorge, if it covers the whole cell; a raised deck (the floor of a hut on stilts) closes what is under it. What can be walked on whatever the terrain beneath (`walkways`) is open: a ramp (over the whole cell), and, above deep water, a roadway that plunges into it (a quay, a jetty) or a platform that rises from it (the deck of the Harbor's freighter, with its gangways). Only the largest connected region stays open (`keepLargestRegion`): every open cell is reachable. Computed once per arena, on first request. `navigate` (ai/navigation.ts) goes through it first (`gridWaypoint`): a closed destination becomes the nearest open cell; if the straight line (`clearLine`) crosses a closed cell, the robot follows a path (weighted A*, `GREED` 1.4, heap in typed arrays: 0.2 to 2 ms) and aims at the farthest of the next cells on it that it can see; one search per step in total (`SEARCHES_PER_STEP`), no more than one per second per robot (`MIN_REPLAN`), a new one when the destination has moved by 4 cells, when it has strayed from the path, or after 4 s. In combat (`engage`, `support`, `charge`), a path longer than 2.5 times the straight line plus 25 m isn't worth the detour: it just goes as close as it can among the neighboring cells (`approachPath`); otherwise a robot at the foot of the volcano went all the way around the mountain to reach an enemy on the other switchback of the road. A bridge that the route crosses is taken from one end and followed along its axis (`bridgeGoal`: near it, a point on the axis `PURSUIT` m further on; only in an arena with a grid, the Valley keeps its behavior). Also: random destinations (`wander`), those brought back into the arena (`clampToRoam`), landing destinations (`landing`) and spawn spots (`isClear`, wave.ts) are taken from open cells (`passable`, `nearestPassable`: true everywhere without a grid). Local avoidance (brain.ts) sees lava and deep water as an obstacle 1.5 m from their edge (`hazardDistance`, not under a bridge).
- **Terrain hazards (`sim/hazards.ts`, `updateHazards`, in the "fire, smoke, repair" stage, in 0.25 s slices):** lava burns blocks and wheels less than `LAVA_HEIGHT` (1.3 m) above it (`LAVA_DPS` 40, damage type `fire`), sets them alight, sets wood on fire and blows up a barrel; a robot whose cockpit plunges into deep water drowns (`DROWN_DPS` 160 to the cockpit, damage type `energy`: 5 s), and the water puts out the burning blocks it covers. Kill causes `lava` and `drown` (`KillCause`, "lava", "drowning" in the feed). An arena without lava or deep water has none of this.
- **Entities** (`shared/sim/entities.ts`): `Bot` → `Part` (a `RigidBody`) → `Block`. `bot.blocks` only contains living blocks. `sim.parts` lists all the parts in the world (including those of robots outside `sim.bots`).
- **Merged colliders (`robot/colliders.ts`):** a part doesn't have one collider per block: `rebuildColliders` merges neighboring cubes of the same type into large boxes (greedy merging), plates and shaped blocks keep their own (one convex hull per piece of the shape, `addShape`), and the density gives exactly the nominal mass. `attachBlock`/`detachBlock` only mark the part (`dirty`); the colliders are rebuilt at spawn and at the end of each damage batch (`rebuildDirtyParts`), then the mass is recomputed immediately (otherwise Rapier only removes the old one at the next step). `hitTargetOf` finds the block hit from the grid cell at the impact point. Rebuilt colliders are only visible to raycasts at the next step: this is why piercing goes through a robot by advancing through its grid (`pierceRobot`). **Hittable turret heads (`addHeads`):** a weapon's head and barrel stick out of its block, whose collisions are only the cube; each turret therefore has its hittable zone (`Part.heads`, `TurretHitbox`): a box for the head (`TurretSpec.head`, at `HITBOX_SHARE` of the drawn head) and a capsule for the barrel (`TurretSpec.caliber`, at least `MIN_CALIBER`, up to its muzzle; not for the bomb bay), massless (zero density) and without contact (`hitbox` group: a barrel grazing the ground doesn't snag on it). Shots and rays without a group filter see them (not the wheel rays); a hit on them strikes the turret's block (owner `head`, `hitTargetOf`, `ownerBot`). They follow the head's yaw and pitch, as the renderer draws it (`syncHeads`, every step after the AI, only when it has turned), and are rebuilt with the part's colliders. Without them, a shot at the weapon went through it and only hit the block below.
- **Collision groups (`physics/groups.ts`):** debris only collides with the static scenery; a mounted wheel only collides with what moves (robots, props: `wheel`), and its suspension ray only sees the static scenery (`groundRay`); a turret's hittable zone collides with nothing (`hitbox`). Every new collider must be given its group. Each entity has a unique `id` within its simulation, which serves as a key on the rendering side and later on the network side.
- **`sim.colliders`** (handle → `ColliderOwner`) links a ray impact to what the collider represents. It must be kept up to date on every collider creation or removal.

- **`World` (`sim/world.ts`):** what the renderer, the sound and the HUD read (robots, time, player, match, detection, projectiles and mines, events). The `Simulation` implements it, and so does the network replica: the views are typed `World`, never `Simulation`.

### Multiplayer (`shared/net/`, `server/`)

- **Room (`server/room.ts`):** an endless six-versus-six battle; a player who joins (`join`: name, preset robot or garage design, validated by the server) replaces an AI robot on the team with the fewest humans; they pilot through `Bot.input` (their commands, clamped on receipt, `readInput`: the look direction `look` is normalized or dropped; `PROTOCOL_VERSION` 25); on leaving, they hand their robot back to the AI; a new match starts 8 s after the end, in the next arena (`NetEvent` `arena`, before the props and the match; `zone` when a zone changes hands; the zones' state is in the snapshot). The room receives text and sends through a `Connection`: the tests run it without a network (`tests/network.test.ts`). Its arenas follow one another (`Room.rotation`): the game's, then the community maps it is given (`RoomOptions.maps`, the `maps/` folder in server/main.ts). A community map is sent only once to whoever doesn't have it (`map` message, before the frame that puts it in place: on joining, and on each arena change); on joining, the client announces those it already has (`join.maps`, their identifiers, at most `KNOWN_MAPS`).
- **Progression on the server (`server/progressBook.ts`):** each browser draws a secret token once (`playerToken`, client/progress.ts) and sends it when joining; the server keeps the credits and unlocked parts per token (`Ledger`), in memory (`ProgressBook`, with no disk, for the tests) and in a file (server/main.ts: read at startup, rewritten one second after each change, via a temporary file). A garage robot with parts that are not unlocked on this server is only accepted if the player has enough credits there: the parts are then unlocked (`unlockParts`, all or nothing), otherwise it is refused with the list and the price. Preset robots are always accepted. At the end of a match, each player earns their credits (`matchReward`: match played, victory, their kills, counted from `Bot.input`) and receives the `progress` message; the client turns it into a line in the feed. Local progression (matches against the AI) stays in the browser, separately.
- **Frames:** every `SNAPSHOT_EVERY` steps, a JSON header (`FrameHeader`: the `NetEvent`s since the previous frame, the player's robot and its current lock-on) followed by a binary snapshot (`snapshot.ts`: match, detection, state of the robots and their weapons (rate of fire, heat, ammo, reload of the current round; one deflection per row of control surfaces), part poses, wheels and hub carriers, debris, moving props, projectiles). An anchored prop isn't in it: its `NetEvent` `prop` gives its spot (`spot`, in `arena.props`, from which the replica gets its pose, `spotPose`, and its dimensions); once released (`propFree`), it enters the snapshots. A player who arrives first receives everyone (`describeWorld`), including wood that is burning or has burned (`propFire`: burning or not, its charred share) and the ongoing fire puddles (`groundFire`, `groundFireGone`); the replica knows about a prop's fire only from these announcements (`Prop.burn` is 1 while it burns). `World` also gives the props present (`props`) and the puddles (`groundFires`): an effect attached mid-match finds there what is already burning.
- **Encoder (`net/encoder.ts`):** translates `SimEvent`s into `NetEvent`s (entities named by their `id`). A robot that has appeared is described in full at send time (`BotDesc`: living blocks and their part, hit points, wheels, broken links); its structure is deduced from its design. **Any new structural change must have its `NetEvent`**, just as it has its `SimEvent`.
- **Replica (`net/replica.ts`):** rebuilds the same entities (with `newBot`, `newBlock`, `registerOrgans`, `addThrusters` from lifecycle.ts), with bodies without physics (`PoseBody`: pose, velocities, center of mass, mass) and the wheel poses (`WheelBody`); a mounted wheel has a hub carrier (`hub`), as in the simulation (this is how queries recognize a driven wheel). It replays the events when their frame is reached and emits the same `SimEvent`s. The arena of a `NetEvent` `arena`: a game arena, a received map (`addArena`), or a map the client already has (`resolveArena`, the browser's library); if unknown, it keeps its own and notes it (`missingArena`). `tests/network.test.ts` checks that it reproduces the server's world and that what the HUD reads works there.
- **Client:** `ArenaGame.startOnline(net)` binds the views to the replica (`bind`); the loop then replaces the physics with `replica.advance` and sends the commands (`INPUT_RATE` per second). Online, aiming goes through the Babylon scene (`WorldView.belongsTo` to aim through your own robot). An exception in a frame is reported once without stopping Babylon's loop (it wouldn't restart).
- Removing a robot (`removeBot`) marks its blocks as destroyed: turrets, missiles or an AI that were targeting it don't read its freed bodies.

### Community maps (`shared/map/`, `client/maps/`, `maps/`)

The authors' guide, field by field, with importing from Gaea, World Machine, Blender, terrain.party and Unity: `docs/maps.md`.

- **Format (`MapFile`, map/format.ts):** versioned JSON data (`format: 1`, `.casse-map.json` files), in meters and degrees, in the game's frame. `meta` (name, author, description, license: text written by a person, displayed as is, with an optional name and description per language), `terrain` (a centered square grid: `cells` from 16 to 440, `step` 1 or 2 m, 440 m per side at most, little-endian Uint16 heights from `min` to `max` in base64, in the order of Rapier's heightfield), `bounds` (only `half` required; the rest as a percentage of `half`, `airFloor` from the highest point of the scenery), `limits` (enclosure walls that follow the terrain, invisible boundary at `half` + 35 m by default), `sky`, `ground` (`preset`: the palette of a game arena, the Valley by default, `VALLEY_GROUND` in features.ts, and what you change in it), `water` (`level`, `deep`: you drown beyond it, `color`), `lava`, `vents`, `falls` (`dir` in degrees), `paths`, `urban`, `ambience` (that of a game arena: `ArenaLayout.ambience`), `nav` (nav grid: by default on a map with terrain, deep water or lava, 2.5 m cells, 26°; `false`: none), `boxes` (`StaticBox`: `size`, `yaw`/`pitch`/`roll`, placed on the ground when without `y`, a rock half buried), `props` (`PropSpot`: on the ground when without `y`; `size` for a slab, `scale`, `rests` as indices into `props`, `group` for a building), `prefabs`, `zones` (one to five, A to E), `places` (free names: `ArenaPlace` is a translated place, `place`, or a named one, `name`). Unknown fields are ignored.
- **Reading (`readMap`, `readMapText`, map/read.ts):** untrusted input, copied field by field (types, finite and bounded numbers, bounded texts without control characters, lists bounded before being traversed, language codes and colors checked, booby-trapped keys refused); nothing in it throws an exception or does excessive work (a file of 4 MB at most, a million props refused without being read). Returns a clean `MapFile` (absent optional fields not written) or `MapIssue`s (24 at most; `path`: the faulty field, "props[3].type"). Migration: `upgradeMap` applies `MAP_MIGRATIONS[n]` (from n to n + 1) up to `MAP_FORMAT`; a map in a newer format is refused (`formatTooNew`).
- **Arena (`arenaFromMap`, map/build.ts):** the decoded terrain (`decodeTerrain`, codec.ts), the boxes and props placed (at the lowest point of the ground under their footprint, `lowestUnder`; a movable prop slightly above), the map's props first (their `rests` keep their indices), then the unfolded prefabs (`expandPrefab`, map/prefabs.ts, stopped beyond the allowed number of props), then the limits. **Prefabs:** `house` (the Valley's `house`, built at the origin then rotated by `yaw` and placed: its panels keep their supports and form a building), `tenement` (the City's `building`, which takes a `ground`), `fence` (panels of 2.5 m at most along a polyline), `woods` and `rocks` (sown by a fixed draw, `seeded`, away from paths, zones, spawn lines, water, lava and scenery; `Taken`: an 8 m grid), `ramp` (`incline`), `bridge` (deck, parapets, piers down to the ground), `containers`. After that, nothing distinguishes the map from a game arena: simulation, nav grid (computed on first request), rendering, minimap, network.
- **Identifier (`mapKey`, map/key.ts):** `map-` and 16 hexadecimal digits, the hash (64 bits, in the manner of cyrb53) of the map written in a canonical form (`canonicalJson`: sorted keys); the same map has the same identifier everywhere, the slightest modification makes it a different one. `ArenaLayout.id` is an `ArenaKey` (`ArenaId` or `MapKey`).
- **Validation (`checkMap`, `checkMapText`, `validateMap`, map/validate.ts):** the same in the browser, on the server and in the tool: reading, then what the built arena says: counts after the prefabs (`MAP_LIMITS`: 400 boxes, 900 props including 120 movable; the City has 152 and 530, the Harbor 78 movable; and, so that the worst case is checked in 2 s at most, 1,200 sown trees and rocks, 1,024 points for all paths, 512 for all lava, nav grid cells of 2 m at least), slabs without dimensions, terrain covering the playing area and the invisible boundary, consistent dimensions, nothing outside the map, zones (one to five, different letters, within the playing area, **reachable**: an open nav grid cell in their disc), **spawn lines** (at least half of their spots free and passable, nothing dangerous within 8 m: lava, a prop that explodes). Returns `{ map, arena, key, issues }`: the checked arena is the one to play (its nav grid is already computed).
- **Imported terrain (map/heightmap.ts, png.ts):** `decodePng` (8- or 16-bit grayscale PNG, color or palette reduced to their average, row filters, no interlacing, 4,097 pixels per side at most; the decompression is supplied: `DecompressionStream("deflate")` in the browser, `zlib` in Node), `decodeRaw16` (square, little- or big-endian), `imageFromBytes` (an image passed through the canvas, 8 bits), `smoothImage`, `heightsFromImage` and `terrainFromImage` (bilinear resampling at the map's step, vertical scale `low`/`high`, smoothing of 8-bit images by default, mountains at the edge: `mountains`), `imageFromHeights` and `encodePng` (exporting a terrain). The image reads like the map: top to the north, left to the west. Errors have a code (`isHeightmapError`, `heightmap.<code>`).
- **Loading:** `registerArena` (arena/layout.ts) makes a map known to this process (`arenaById`, `communityArenas`); `registerMap(carte)` (map/load.ts) builds it once and makes it known; `Simulation.loadArena` takes a known identifier or an arena. In the browser, `MapLibrary` (client/maps/library.ts) holds the maps shipped with the game (`import.meta.glob` of `maps/`, loaded during the startup screen), those imported or made here (IndexedDB, `library` store: client/maps/db.ts; a map can weigh several hundred KB) and those received from a server (`cache` store), rechecked when loading them; `arena(key)` makes one playable. Menu: the arena choice lists the community maps after the game's arenas, and "Community maps…" imports (a checked file, its issues displayed), exports (`downloadMap`) or deletes. **Editor API (phase 2):** `blankMap`, `checkMap`, `arenaFromMap`, `mapKey`, terrain import (`heightImageFromFile`, client/maps/files.ts, then `terrainFromImage`), `MapLibrary.save`/`remove`/`list`/`importText`, `downloadMap`, `downloadHeightPng`, and `App.testMap(carte, { mode, pilot, back })` (a test match; returns the map's issues); in the console, `__casse.maps` and `__casse.testMap(carte)`.
- **Free spawn lines (`MapFile.spawns`):** optional (`format: 1` stays): for each team, a midpoint, the direction it faces at the start (`facing`, degrees: 0 toward the north, 90 toward the west) and a length (`width`, 4 to 160 m); both teams or neither. Carried by `ArenaBounds.spawns` (`SpawnLine`: radians and half-length, `mapBounds`); `spawnLineOf`, `spawnPoint`, `spawnLocal` (arena/layout.ts) give a team's line, a point on the line, and where a point is relative to it: without free lines, exactly the calculations from before (x along the line, z = ±`spawnLine`), so the game's arenas see no difference. They are taken into account by: `spawnTeams` and `respawnBot` (`placeInLine`, turned toward `facing`), planes (the half of their circuit that faces their line, `sideAngle`), sown woods and rocks (`sowable`), validation (each line within the playing area, 2 m from the edge, `spawnOutside`; clear and safe, like the north and south ones; the two at least `SPAWN_APART` (24 m) from each other, `spawnClose`). `tests/spawnLines.test.ts`. A map that has them doesn't play the same for an older client: `PROTOCOL_VERSION` 24.
- **Network:** see "Multiplayer" (`map` message, `join.maps`, `Replica.addArena`, `resolveArena`); `PROTOCOL_VERSION` 22 (23 since the pilot controls, 24 since the free spawn lines, 25 since night: the City by Night, `sky.night`, headlights, beacons and the floodlight mast; 26 since the decorative lights).
- **The map editor (client/editor/):** a screen of its own, like the garage: its own scene on the game's engine (`EditorView`, created on entering, entirely freed on leaving; the arena on standby behind it). You enter it from the main menu (the current draft, otherwise a blank map) and from "Community maps…" ("New map", "Edit"). **State and commands (`MapEditor`, editor.ts):** the map (a `MapFile`), its history (`MapHistory`, shared/map/history.ts: the successive maps, with what doesn't change shared; at most 100 modifications and 48 MB of terrains; a brush stroke counts as one; undo and redo restore the selection each state had, `selections`), the tool, the selection (`ElementRef`s: a list of the map and an index; `spawns`: 0 the blues, 1 the reds), the tool settings; each modification goes through the pure operations of shared/map/edit.ts (`addElement`, `setElement`, `moveElements`, `rotateElements`, `duplicateElements`, `removeElements`, `movePoint`: the props' `rests` supports and `group` buildings follow along; `spawnsOf` gives the spawn lines, the north and south ones until they've been placed) then `commit`. **Drawing (`EditorView`):** the game's renderer (`ArenaView` in editable drawing: `showBoxes`, `showGround`, `reshapeTerrain`; props as instances of their models, `Assets.propSource`) from `arenaFromMap(carte, "map-editor", origins)` (`ArenaOrigins`: where each box and each prop comes from, so that a click on a wall panel selects its house); only what has changed is redone (`changesBetween`: the ground for terrain, water, paths, lava, palette, waterfalls; boxes and props for what places them or, if there are sown woods and rocks, for what they avoid); the decoded terrain is kept per map terrain (`decodeTerrain`, a `WeakMap`). Overlay draped on the ground (draping.ts: ribbons and discs, `alphaIndex` 2: after water, before smoke): playing area, AI area, invisible boundary, spawn lines and their handles (move; rotate, the ball at the tip of the arrow), zones, places, fumaroles, lava, paths, placed limits, the selection (a box, the handles of a trace's points, a wood's disc), the placement ghost (green or red: within the map, within the bounds of `MAP_LIMITS`), the brush ring, the trace in progress, the snapping grid (around the center of the view); projected HTML labels (zones, places, spawn lines, problems: a click leads there). Orbit camera without Babylon's controls (`orbit`, `pan`, `zoom`, `shift` on the keyboard, `toggleTop`: north up, `focus`), its center moved without changing the angle (`setTarget(…, true)`). **During a drag, only the element's meshes move** (`dragBy`); on release, the map is rebuilt. During a brush stroke, the field (shared/map/brush.ts: `applyBrush`, pure and tested) is reshaped live (`reshapeTerrain`, over the affected area: positions, normals by central differences, colors), and the terrain is re-encoded on release. **Panels (`EditorUi`):** top bar (name, "modified", where the map comes from, the "The map is playable" indicator or the number of problems, Test, Save, Leave), toolbar (`TOOLS`, editor/tools.ts: Select, Terrain, Place, Traces, Water and lava, Settings, File), tool panel, selection properties (built from `FORMS`, shared/map/fields.ts: each field of each kind of element with its bounds, those of reading; an optional field has its "auto"), list of problems, key help (`editorKeys`, keys.ts), notes. **Checking:** `checkMap` in a Worker (`MapChecker`, checker.ts; 350 ms after the last modification, only one at a time), on the page if there is no Worker; `issueTarget` (edit.ts) says where a problem is. **Testing:** `App.chooseTestMode` (the mode, the last one first; then the robot), `editor.suspend()` (scene, panels, listeners and Worker freed, state kept), `App.testMap`; the pause and end-of-match screens offer "Back to the editor" (`returnToEditor`, `editor.resume()`: in the same state, view included). A map that has problems doesn't start (the list opens). **Saving:** the map must be playable; `MapLibrary.replace` replaces its previous version (a map from this browser); a map shipped with the game or received from a server is saved as a copy ("(copy)" added to the name). **Draft:** kept in IndexedDB (`drafts` store, db.ts version 2; drafts.ts) 1.2 s after each modification, with where the map comes from and the view; the editor reopens it. Escape cancels what is in progress (a field, a drag, a trace, an import, the selection), then offers to leave (`App.leaveEditor`: save, keep the draft, discard it, go back). **Keys:** the "Map editor" section of the action table (`editor*`, context `editor`: never at the same time as the match or the garage, no gamepad, key combinations). Measured in Chrome without GPU on a loaded machine: opening Lake Vale ~200 to 400 ms (everything is built), moving a house or changing a field ~80 to 130 ms (the whole arena rebuilt, the ground kept: `arenaFromMap` ~12 ms, boxes ~23, props ~13, overlay ~18; redoing the ground would cost ~120 more), the end of a brush stroke ~70 to 110 ms (the ground, already reshaped live, isn't redone, unless there is lava), checking ~70 ms in the Worker; after six editor → menu round trips, two live scenes (the game, the garage) and no Worker (`Runtime.queryObjects`), the heap stable (~105 MB).
- **The example map, "Lake Vale" ("Val du Lac" in French, `maps/val-du-lac.casse-map.json`):** made through the format, as an author would: a terrain drawn as a 16-bit PNG (`tools/maps/val-du-lac.png`, computed by `tools/maps/example.ts`: hills, a deep lake where you drown, a shallow river), imported at a 2 m step over 320 m with mountains at the edge, then a village (brick houses, church and its bell tower), a farm (a barn you can drive through), a blockhouse on the western hill, a ruin on its mound to the east, an old stone bridge on the north-south axis, woods, rocks, five zones and six named places; symmetric about the east-west axis. 253 props including 9 movable, 32 boxes; 75 KB. `tests/communityMaps.test.ts` checks that it is indeed the one its tool makes. Measured (`MAP_PERF=1`, same machine loaded by other computations): a combat step with 12 robots costs 7.2 ms (Valley 7.1, Depot 6.4).
- **Known limits:** the AI follows a skewed bridge poorly (its decks are read along the axes: arena/navgrid.ts, ai/navigation.ts); the boxes and ambiences are those of the game's arenas; a structural error in a map hides its construction issues (you fix the first, then you see the next ones).

### Combat

- **Projectiles (`combat/projectiles.ts`):** every shot launches a projectile (`ProjectileSpec`: speed, share of gravity, flight time, damage and its type, penetration, impulse, explosion, `command`/`homing` guidance, proximity fuse, mine, fire, electromagnetic pulse, smoke, `pellets` spread, `fan`). It advances each step by a raycast between two positions, ignores the robot that fired it, pierces as long as it destroys what it hits, explodes, bursts (EMP, smoke) or settles (mine: the rest is in combat/mines.ts). A shotgun shot (`pellets`) launches nine pellets at once for a single `shot`; a salvo rocket (`fan`) leaves fanned out, then its guidance brings it back toward the aimed point (this is not inaccuracy: the crosshair circle ignores it). Fire rate is counted down on the fixed step, with a tolerance (`canFire`): without it, a leftover rounding error cost one extra step (the laser fired 8.6 times per second instead of 10).
- **Command-guided missiles (`command` guidance):** they follow the aiming axis of their missile launcher (`steer`, combat/projectiles.ts: the point on the line that starts at its muzzle, along the barrel axis, `LINE_LEAD` m ahead of them), like a real command-guided missile: turning the turret brings them back onto the new line; with the missile launcher destroyed, or from the free camera, they follow the aimed point. They are therefore fired straight at the target (`firingDirection`), without the elevation that seekers and the warhead take.
- **Launch along the axis, momentum, seeker head (`steer`, combat/projectiles.ts; `Guidance`):** every guided missile (command-guided, lock-on, anti-air, rockets, warhead) first flies straight along the weapon's axis for `Guidance.launch` s, then its guidance takes over. A homing missile has momentum: it turns no tighter than its lateral acceleration allows (`maxAccel`: the faster it goes, the wider its turn), each turn costs it a share of its speed (`bleed`, per radian), which its motor gives back (`recover`), and it has weight (`ProjectileSpec.gravity`). It must see its target (`sightBlocked`, combat/sight.ts: terrain, scenery, props and smoke block the view, robots do not; the cockpit or a point 0.8 m above it): with the target hidden, it flies on its momentum without turning (`Projectile.blind`), then loses the target after `SEEKER_MEMORY` (`lost`, it flies straight); nanites, which go to an ally, ignore this. Fired upward at a locked target behind a wall or a hill, it climbs on its momentum, finds the target again from above and dives onto it (a lob); fired straight, it hits the obstacle. Lock-on missiles: `maxAccel` 60, `bleed` 0.6, gravity 0.6: all the lobs of `tests/missileSight.test.ts` hit (wall at 20 and 40 m), a target moving straight at 10 m/s is hit, a sharp swerve at 10-15 m makes it miss (at 55 and 0.3, it missed the short lobs; at 80 and 0.5, nothing could dodge it anymore).
- **Turrets (`combat/turrets.ts`, `ai/gunner.ts`):** a head aimed in yaw and pitch, at limited speed, independently of the robot. The AI picks the nearest **spotted** enemy in range that suits the weapon, aims with lead and a ballistic angle, checks the line of fire (no teammate, no scenery, no smoke), then fires. Each turret scores targets (`targetScore`): the nearest, preferably damaged (`integrity`), vulnerable to its damage type (`vulnerability`, based on block resistances) and already engaged by its robot. It aims with an error (`Turret.wobble`, `AIM_BASE` plus `AIM_TRACKING` per m/s of crosswise relative speed): a maneuvering target is missed more often. Two teams (`Bot.team`) fight each other; the free camera is everyone's enemy.
- **Accuracy (`combat/accuracy.ts`):** `Weapon.spread` is a weapon's best spread (scoped, robot stationary); `Weapon.handling` says how it degrades: ×`hip` without the scope, +`move` rad per m/s of robot speed, +`turn` rad per rad/s of rotation (the robot turns, pitches, bounces). A plane in flight is a stable platform: only its rotation counts. `aimSpread` gives the spread of a player shot (at 2 m/s, the sniper strays by 3°: you have to stop to aim); the AI and the free camera fire with `hipSpread` (the former spread), the AI's aiming error already growing with speeds.
- **Lobbed fire (`lobbed`, `combat/ballistics.ts`):** for a slow weapon subject to gravity, neither guided nor laid (cannon, EMP shell, smoke shell), the player chooses the elevation: the barrel points straight at the crosshair (`lobDirection`, which only subtracts the velocity inherited from the robot), with no drop correction. To fire farther, you raise the mouse; the range follows from the elevation (and from the flight time `life`), and a crosshair in the sky no longer sends the shell off at 45°. Higher or lower than the turret can go, it fires at its stop (`aimTurret(…, reachable)`). `predictImpact` follows the trajectory as `projectiles.ts` integrates it (`ballisticPoint`) up to the first obstacle: that is the HUD's impact point. The AI keeps the ballistic solution (`firingDirection`).
- **Line of fire (`lineOfFireBlocked`, combat/turrets.ts):** projectiles ignore the robot that fires them; a turret therefore does not fire if its line of fire crosses its own robot. The line is traced from the head's axis, cell by cell in the robot's grid (no physics), until it leaves the robot's clearance: a block of its part or the head of another of its turrets masks it. Applies to the player and the AI; the HUD says "Shot blocked by your own robot" (red crosshair) when all the turrets of the selected weapon are masked, and the garage flags a turret buried under a block (`buriedTurrets`), which will never fire.
- **Identical weapons (`fireInTurn`, combat/turrets.ts; `stackRate`, combat/arsenal.ts):** the turrets of the same weapon on a robot fire in turn, on a shared rhythm (`Bot.nextShot`): each turret ready to fire (player: aimed, trigger; AI: target, clear path) becomes a request (`ShotRequest`), and each step, per weapon, only the one that has been waiting longest (`Turret.firedAt`) fires, if the rhythm allows. n weapons fire `stackRate(n)` times faster than one alone, with diminishing returns (each extra weapon adds `STACK_FALLOFF` = 0.8 times what the previous one added: ×1.8 with two, ×2.95 with four, never ×5); each therefore fires less often than alone, and its ammo and heat last that much longer. A lone weapon keeps its fire rate. No preset robot has two identical weapons: this only affects garage robots.
- **Lock-on (`combat/lock.ts`, weapon with `lock`):** an enemy must be kept in the weapon's cone (`lock.cone` around the aim) for `lock.time` s before firing; the missiles (seeker head) chase the locked target (`Turret.lockOn`, `lockTime`). Once acquired, the target stays held in a cone 1.8 times wider; out of the cone, the lock decays twice as fast as it builds, then moves to the enemy closest to the aim. Only enemies that are spotted, in range and in the weapon's sight can be locked (`sightBlocked`); a target hidden by scenery or smoke no longer advances the lock, and it is lost after `LOCK_GRACE` (1 s: a passing pole does not make it let go, a target that has just gone behind a hill stays locked long enough to fire a lob; `Turret.lockHidden`). Once acquired, the lock holds as long as the target stays within `LOCKED_HOLD` (~43°) of the aim: you can aim higher than or beside an obstacle to fire a lob. The player locks only through the scope (right click), and only what is under the crosshair (selected weapon only), and the lock drops when they leave the scope; the AI locks what it aims at; both fire only at their locked target. The HUD frames the target with tightening corners, red once the lock is acquired (`Instruments.showLock`); while locking, beeps that come closer and closer together (`LOCK_BEEP_SLOW` to `LOCK_BEEP_FAST`, game.ts), then a double beep; online, each frame's header carries the player's lock (`FrameHeader.lock`, applied by the replica).
- **Piloted warhead (`piloted` guidance, `pilotedWarhead`, `fuseNow`):** one shot per life (a one-round magazine that does not reload), a huge explosion (550 over 5 m). The AI does not fire it at an enemy closer than `minRange` (20 m): the explosion would hit it. While it flies, the player who fired it steers it: it turns (1.3 rad/s at most) toward the aimed point of their controls (`steer`, combat/projectiles.ts); their robot stops and its turrets stop aiming (`thinkPlayer` neutralizes its controls; a plane, which cannot stop, flies level at the target altitude, held by the autopilot, and the warhead launcher weighs only 5 kg so that a plane can carry it); a new click (trigger released since the shot, `Bot.triggerHeld`) detonates it on the next step, as at the end of its run. The AI command-guides it toward its target like a `command` missile. With no preferred range (`engage`), it counts neither in the AI's positioning nor in its retreats to reload. Client side, `ArenaGame` follows the player's warhead through its events (`projectileAdded`/`projectileRemoved`): the camera moves to its nose (the scope mechanism, without magnification, looking up to ±83°), you aim at the center of the screen (`Controls.centerAim`), a panel gives the remaining flight time, the altitude, the speed and the distance to the robot (`Instruments.showWarhead`); after the explosion, the camera watches it for 1.2 s from slightly behind, then returns to the robot. Does not go through the protocol: the controls (`aim`, `trigger`) are enough.
- **Bombs (`Weapon.dropped`, `bombBay` block):** a bomb bay is a fixed turret facing down (`TurretSpec.fixed`: `"back"` for the mine layer, `"down"` for the bay; its head, a rack with two bombs hanging from it, is below the block: negative `height`; the cell below must stay free, `buriedTurrets`). It releases its bombs without aiming (`released`: mines and bombs; `lobbed` excludes them), in a string as long as the trigger is held (eight, 60 plus 170 over 2.4 m); they fall keeping the plane's speed and explode on the ground (`bomb` look). The player sees where the next one would fall: a circle the size of the explosion and the fall time (`ArenaGame.bombing`, `predictImpact`, `Instruments.showBombing`). The AI drops when a bomb released now would fall on its target, where the target will be (`bombsOnTarget`, ai/gunner.ts, with `fallTime` from combat/ballistics.ts), never on a teammate; it only targets ground robots (`suits`). An AI bomber (a plane with a loaded bay that has a target) leaves its circuit for an attack pattern (`bombingRun`, ai/pilot.ts, `AiState.bombRun`): the pass (straight at the target up to `RUN_TRACK` m, then the line held), flying straight away out to `RUN_OUT` m, the U-turn (toward the target's side, or the arena center if the target is straight behind: otherwise the guidance hesitates; exited early based on its roll rate, `ROLL_LEAD`, because a heavy plane rolls slowly), and the pass again; too close to line up, it flies farther out. It attacks at `BOMB_ALT` m at least. Client side: a streamlined bomb with cross-shaped fins, which noses down as it falls; a release sound, a falling whistle that drops in pitch (`FLIGHT_FALL`), a heavy explosion (`explosion-bomb`).
- **Ammo and heat (`combat/arsenal.ts`):** each turret (and each free-camera weapon, `sim.playerArms`) has an `ArmState`: fire rate, heat (automatic weapons: overheat, then resume at `RESUME_HEAT`), a magazine that regains one round at a time.
- **Damage (`combat/damage.ts`):** `strike` (direct impact) and `explode` (area damage, then blast). Damage has a type (`DamageType`: kinetic, piercing, explosive, impact, fire) and each block or prop has its resistances (`resist`). Within a batch (`DamageBatch`), a target hit twice keeps the stronger hit. For blocks that drop to 0: the parts' motion is recorded **before** colliders are removed → debris → broken links → `splitPart` → `refreshWheels` → AI reaction → `damage` event. Each explosion in the catalog (weapons, props) has its look (`Explosion.look`: shell, missile, rocket, flak, mine, warhead, barrel, gas), carried by the `explosion` event (and its `NetEvent`): the client makes its effect from it (simple effects: `EXPLOSION_STYLES`, render/effects.ts, layers of spheres that grow and fade, fireball, smoke, dirt, shockwave, shrapnel; realistic effects: `FIREBALLS`, render/fx/blastFx.ts, a flash, fireballs that roll and then blacken into smoke, the smoke that follows, flung dirt) and picks its sound (`EXPLOSION_SOUNDS`). A destroyed cockpit emits `botKilled`, credited to the last enemy that hit the robot (`Bot.lastAttacker`, from `DamageBatch.attacker`), with its cause (`DamageBatch.cause`: the weapon, `impact`, `fire`, `blast`, `self`, `lava`, `drown`, `exhaust`: an engine's flame jet) for the kill feed. **Structure rule:** a robot whose cockpit part keeps less than `WRECK_INTEGRITY` (25%) of its starting blocks (`integrity`) is out of action, and its cockpit gives way (otherwise a sturdy cockpit survives alone, a rolling block). `inflict` is used for damage prepared elsewhere (collisions, fire).
- **Collisions (`combat/collisions.ts`):** Rapier reports strong contacts (`CONTACT_FORCE_EVENTS`); the closing speed **from before the step** is recovered (`captureMotions`). Below `SAFE_SPEED`, nothing; above it, the share of the impulse due to the excess speed becomes `impact` damage at the contact points, on both sides. Pushing each other or driving against a wall does nothing; ramming at full speed, crashing, does. **Breach:** an anchored prop (tree, wall panel, cactus, lamppost) is a fixed body, which stops the robot dead during the step; if the impact breaks it (`breachOf`: its damage from a dead stop, after its `impact` resistance, exceeds its hit points), the robot goes through: it gets back its speed from before the impact, minus the impulse it took to inflict those hit points (with the same efficiency `1 - SAFE_SPEED / vitesse` as the damage) and a `CARRIED` share (2%) of the obstacle's mass, carried along in passing (a wall slows it more than a tree), and only takes the damage of what gave way; below `BREACH_MIN` (0.5 m/s), it stops. A wall's fragments fly out ahead of it (`Prop.struck`); a felled tree or lamppost falls in the robot's direction of travel (`fellProp`) and does not hit robots while it falls (`felled` group, `Prop.yielding`, restored by `restoreFelled` when no robot is inside it). A prop that only gives way by exploding later (a storage tank), or that holds, stops the robot as before. Measured (`tests/breach.test.ts`, flat ground): the Ram at speed (5.6 m/s) fells a pine and moves on at 1.5 m/s, goes through a palisade at 3 m/s, stops against a brick or concrete wall; the Truck at 10 m/s goes through the brick wall (2.4 m/s afterward); the Buggy stops against the pine. All of a step's collisions are **measured before a single one is inflicted**: inflicting rebuilds and frees colliders. Likewise, `advance` (projectiles) reads a part's frame before hitting it, because the part may disappear. A robot that a flipper has just thrown (`Bot.thrownBy`, 3 s): the damage from its collisions is credited to the flipper (except against the flipper itself). General rule: never reread a `Collider` or a `RigidBody` after damage.
- **Weak links (`robot/structure.ts`):** the bridges of a part's block graph (a neck, an arm one block wide) are `WeakLink`s, computed on demand (`part.links`). An impact (projectile hit, blast, collision) loads each link according to the share of the impulse it must transmit and its lever arm; beyond its strength (`bond`, the weaker of the two blocks), it breaks (`bot.cuts`) and the detachable side comes off, without losing blocks. Splits (`splitPart`, `linkedNeighbors`) do not go through a broken link.
- **Fire (`combat/burning.ts`, `combat/fire.ts`):** a burning block (`Block.burn`, `sim.fires`) loses hit points (`fire`) and can spread to its neighbors, then goes out. It is ignited by the flamethrower, by an explosion (`Explosion.ignite`), by destroying a battery, or by hitting a worn-out engine: below `ENGINE_FIRE_BELOW` (25%) of its hit points, an engine that is hit catches fire one time in five (`ENGINE_FIRE_CHANCE`), not from its own fire (it would burn forever; combat/damage.ts). burning.ts ignites (without depending on damage, so that damage.ts and the projectiles can call it), fire.ts does the burning, in 0.25 s slices. **Scenery wood:** a wooden prop (`PropTypeDef.burns`: crate, planks, roof, pine, oak; not brick, concrete, sheet metal) catches fire (`igniteProp`: `Prop.burn`, `sim.propFires`) from the flamethrower (chance `ignite` × `WOOD_KINDLING`), from an incendiary explosion that reaches it, from a puddle, or from a burning wooden neighbor within reach of their flames (`burns.reach`, a tree's foliage; `PROP_SPREAD` per second: in a wood, one tree sometimes ignites one or two others, a cabin burns from wall to wall); it loses hit points (`PROP_FIRE_DPS`, in a separate batch: a tree that gives way topples to a random side), blackens (`Prop.charred`, announced in steps: `CHAR_STEPS`), sets fire to the blocks of robots brushing against it, and goes out after `burns.time` s if it is not rekindled. `propFire` event (lit, out, one more step). **Fire puddles (`GroundFire`, `sim.groundFires`):** the flamethrower's jet (`ProjectileSpec.puddle`: chance, radius, duration) that hits the ground or the scenery, or dies out near the ground (`groundBelow`, a ray that sees only the static scenery), and the napalm of the incendiary mine (`Explosion.puddle`) leave a puddle (`spawnGroundFire`: a nearby puddle is rekindled rather than doubled; 40 at most; none under water, `ArenaLayout.water`) that burns the blocks and wheels standing in it (`GROUND_FIRE_DPS`, within the height `GROUND_FIRE_HEIGHT`), sometimes sets them on fire, ignites the wood it touches, and goes out at `until`; the robot that lit it (`owner`) does not burn in it and is credited with the damage it does. `groundFireAdded`, `groundFireRemoved` events. In battles (`npm run battle`, Depot), fire hardly changes the balance (13 kills by fire over 8 matches before, 15 after); in the Valley, with three flamethrower robots per match, ~23 puddles and one or two wood fires per match.
- **Engine flame jets (`robot/exhaust.ts`, `combat/scorch.ts`):** a flame engine (`ThrusterSpec.exhaust`: thruster, booster, turbojet; not a rotor, a propeller, nor a thruster laid sideways, drawn as a tail rotor: `exhaustSpec`, `hasFlame`) that is pushing (connected to the cockpit, not stunned, output above `JET_MIN`) projects behind its nozzle (opposite its thrust, from `exhaust.nozzle`: the face of the block, the end of a turbojet's nacelle) a hot cone (`Jet`, `jetOf`, `botJets`): its length goes from a quarter of `reach` at idle to `reach` at full power (thruster 1 m, booster 1.1 m, turbojet 2.7 m, and half again as long with afterburner beyond `afterburner`: 4 m), like its drawn flame; its heat (`jetHeat`, `fire` damage per second before resistance) follows the engine's output (`dps` at full power: 14, 18, 40, and a third more with afterburner) and weakens toward the end of the jet (`TIP_HEAT`). Each engine is processed every 0.25 s, in turn (staggered from one step to the next according to its block): its own part is read in its grid (`ownContact`: an engine's axis follows a grid axis; the first block or turret head along the axis, or a wheel in the cone), the rest by three raycasts in the cone (the axis and two on its edge, which rotate from one slice to the next), which ignore the engine's part (its merged colliders would enclose the nozzle) and debris; a block of its robot behind the nozzle also stops the jet. What it touches heats up: blocks and wheels of any robot, its own included (one batch per engine: several jets on a target add up), with a chance of igniting the block (`IGNITE_PER_DPS` × its sensitivity to fire); scenery wood catches fire (`PROP_IGNITE_PER_DPS`), other props heat up according to their fire resistance (a barrel blows up, brick takes nothing). Credited to the engine's robot, cause `exhaust` ("jet exhaust" in the kill feed); on itself or a teammate, no credit; a worn-out engine heated by a jet does not catch fire through `ENGINE_FIRE_CHANCE` (as with fire). **No ground puddle:** a jet is not fuel that spreads, and flying robots land on their thrusters to recharge: they would sow free puddles (a puddle does not burn its author) that would use up the cap of 40; the scorched ground is only an effect. **Preset robots:** none has a block in its engines' jet (Drone, Hexacopter, Angel, Frigate for lift; Rocket, Dragster, Fighter for propulsion: `tests/exhaust.test.ts`, at full power). **AI:** it does not light boosters that would burn its own robot (`scorchesItself`), and a ground robot with boosters lights them when an enemy is in their jet (`foeInJet`: right on its tail; a fleeing Dragster already burns its pursuer). **Garage:** a flame engine's info card gives its jet (length and damage at full power), and the garage warns of a block placed in an engine's jet (`jetObstructions`, cell by cell along the axis, like `buriedTurrets`). Measured cost: ~0.15% of a 12-robot combat step (the "jets" step).
- **Electromagnetic pulse (`combat/emp.ts`):** `Bot.stunnedUntil`; when stunned, a robot cuts everything (`cutPower`: wheels freewheeling, steering loose, thrusters off, hover pads dropped), and its turrets fall silent. **Local stun** (the shock lance, `MeleeHit.stun`: a targeted EMP): blocks within `radius` m of the hit point and mounted wheels within that radius are cut until `Block.stunnedUntil` / `Wheel.stunnedUntil` (`stunOrgans`, which reads the poses: before inflicting); `organStunned(world, block)` and `wheelStunned` (local stun or whole-robot stun), `localStuns(world, bot)` (what is cut, and until when). Every organ honors it: a wheel goes to freewheel, its steering floating (`cutStunnedOrgans`, in `Simulation.step` right after each robot's controls, AI or player); an engine stops pushing (its share of thrust drops to 0, as during a misfire: `wearEngines`, the flight controller distributes according to what is left); a hover pad drops, a leg freezes (`driveSupports`, per support); a turret freezes and falls silent (`operateTurrets`, `operatePlayerTurrets` skip it; it stays in `liveTurrets`, otherwise the HUD would think it lost and switch weapons); a melee weapon is no longer powered; a shield no longer absorbs (`shieldDamage(…, time)`). The rest of the robot works. `organsStunned` event (robot, blocks, wheels, until when, point) and its `NetEvent` `shock` (and in `describeWorld` for a joining player); HUD: "Short circuit · Shock: 2 wheels on the left, 1 turret out of action for 2.3 s" (`localStunNote`, matchHud.ts); effects: arcs run over the cut blocks and from hub to tire on the cut wheels, a cut engine spits a puff (`stunArcs`, engineFx.ts); sound: the stun crackle, shorter.
- **Smoke (`combat/smoke.ts`):** a cloud (`SmokeCloud`) grows then dissipates; it blocks the view (`smokeBlocks`) of turrets and detection. Client side: seven gray bubbles in simple effects (`SmokeView`), a cloud of billows in realistic effects (`smokeCloudFx`, see "Effects").
- **Electric weapons:** a weapon with `power` (laser, railgun) takes `power` kJ from the robot's batteries with each shot (`fireTurret`) and does not fire without it (`turretReady`): the batteries serve as its magazine (the AI goes to cover to recharge, as for an empty magazine). The laser deals `energy` damage, which heavy armor does not reduce; the railgun pierces several blocks.
- **Shield (`combat/shield.ts`):** a generator (`BlockTypeDef.shield`) on the cockpit part absorbs the `absorb` share of the damage received by blocks within `radius` m, each point costing `cost` kJ; with empty batteries, it no longer protects. Applied in `resolveDamage`, after resistances; emits `shieldHit` (a flash on screen). `Bot.shields` lists the generators.
- **Repair (`combat/repair.ts`):** a module connected to the cockpit repairs the damaged blocks and wheels around it, after a while without being hit, and regrows its lost blocks around it. **Regrowth:** a destroyed block goes into `Bot.lost` (not the cockpit); `regrowable` picks the nearest one that can come back: in its place in the design, against a block of the cockpit part, in a free cell (`cellFree`: no scenery, no prop, no other robot, otherwise the physics would eject it at once); a block left on a torn-off part (a severed wing) also counts: it leaves that part (`splitPart`). `rebuildBlock` puts it back on the cockpit part with 30% of its hit points (the same `Block` object: its turret, its ammo, its engine come back with it), restores its broken links, remounts the wheels it carried and rebuilds the colliders; it emits `blockRebuilt` (`NetEvent` `rebuilt`, with the design cell: the replica of a player who joined after the destruction creates the block, `addThruster`). At most one block every `REBUILD_GAP` s per robot. A lost block's position is computed from the cockpit part, never from its former body (possibly freed). `repairNeed` counts the lost blocks.
- **Repair beam (`repair` weapon, `ProjectileSpec.repair`: `RepairShot`):** a continuous beam (it heats up and draws on the batteries) which, on an ally, restores `amount` hit points to each block and wheel within `radius` m of the hit point and regrows a nearby lost block (`repairAt`); on an enemy, it drains life (`drainAt`): `drain` `energy` damage to the block hit, of which the `steal` share of what it really lost repairs the shooter (its most damaged blocks first): it heals an ally more than it damages an enemy. Nothing on its own robot (projectiles ignore it). Each restored block emits `blockRepaired` (a green spark client side). The AI (`operateSupport`, ai/gunner.ts) picks the most damaged ally in range (`repairNeed`) and aims at the most damaged of its blocks that the beam can really reach (`repairAim`: a raycast checks that the impact falls within repair range of that block; a buried block is repaired through its neighbors); without a patient, the beam fights like any other weapon (it drains life). The `t.target` of such a turret can be an ally: `chooseFoe` (ai/tactics.ts) only counts enemies.
- **Nanites (`nanites` weapon, `naniteLauncher` block, `Weapon.autoSupport`):** an automatic support weapon: its turret picks on its own the most damaged ally in range (40 m) and sends it homing nanites (`homing` on the ally; a flare does not divert them); on impact, they spread over the whole robot (`RepairShot.swarm`: its 8 most damaged blocks regain 30 hit points) and regrow a lost block, wherever it is. For the player too (`operatePlayerTurrets` calls `operateSupport`): they neither aim nor press anything, and the weapon has no key (`ArenaGame.pilotWeapons` leaves it out). Only the beam forces the AI to stick close to its patient (`support` mode): the nanites follow it from afar.
- **Energy walls (`combat/barriers.ts`, `barrier` weapon, `barrierProjector` block, `ProjectileSpec.barrier`: `BarrierSpec`):** the projector launches a projectile which, after `reach` m (or on whatever it hits), deploys into a vertical rectangle (`Barrier`: 4.5 × 2.8 m, standing on the ground, facing the shooter, in `sim.barriers`), for `life` s or until it loses its `hp` (700). It stops the projectiles of its team's enemies (`barrierOnPath`, in `advance` before what the raycast hits: it strips their damage, explosion included, and a shell bursts in front of it) and the blast of their explosions (`barrierBetween`, in `explode`); its allies fire through it, robots pass through it (no collider), it does not block the view. `barrierAdded`, `barrierHit`, `barrierRemoved` (`broken`) events and their `NetEvent`s; client side, `BarrierView` (a honeycomb panel in the team's color, which rises from the ground, lights up with each hit, fades and crackles as it loses hit points). The AI deploys it toward its target within 2 s of taking a hit, not against an enemy right next to it nor near another wall of its team (`barrierUseful`).
- **Flares (`combat/decoys.ts`, `flareLauncher` block):** a flare launcher (`BlockTypeDef.flares`: salvos, reload) ejects, on the player's command (F key held, `PlayerInput.flares`: one salvo every 1.5 s while any remain) or when the AI sees a missile coming at it (`thinkFlares`, within `FLARE_ALERT` m), a salvo of four flares toward the top of its block, slightly backward (`FLARE_BACK`); planes and the Helicopter carry it under the belly, upside down (`HANGING`): their flares go downward and stay behind them (the `flare` weapon, `ProjectileSpec.decoy`: they keep a third of the robot's speed, burn for 3.5 s while slowly falling, pass through robots, go out on the ground). Salvos reload one by one (`updateFlares`) and go into the snapshot (`Bot.flares`). An enemy guided missile (seeker head or command-guided; not the piloted warhead) that sees a flare ahead of it (within 40 m, in a 0.9 rad cone) tries its luck once per flare (`seduce`, `Projectile.tried`), with a chance such that a full salvo diverts it 65 times out of 100 if it has a seeker head, 40 if it is command-guided (`SALVO_CHANCE`; since each flare tries its luck separately, higher per-flare chances made a salvo almost infallible): it follows the flare (`Projectile.decoy`), bursts on reaching it, or, once the flare has gone out, flies straight, lost (`lost`). The HUD counts the salvos (one pip each, robot panel) and signals an enemy missile heading for the player's robot (`incomingMissile`, "Incoming missile · F: flares"). Robots that carry them: Plane, Bomber, Fighter, Helicopter, Tank.
- **Interception (`combat/interception.ts`, `ProjectileSpec.hull`):** missiles, rockets, the warhead (the biggest target: 0.6 m, 150 hit points, slow: it takes several bullets), bombs and mines are spheres that can be shot down; a guided missile takes three rifle bullets, a lock-on missile two, a rocket one. A bullet, a shell, a beam (`strikesProjectiles`: not a missile, a mine, a flare) that crosses one on its path (`projectileOnPath`, before what its raycast hits, not those of its own shooter) deals its damage to it (`projectile` impact); so does an explosion (`blastProjectiles`, except its own shooter's projectiles: a salvo does not shoot itself down). At 0, it bursts on the next step where it is (`Projectile.blown`); a laid mine blows up. The crosshair snaps to such a projectile it passes over (`ArenaGame.pickProjectile`, its sphere enlarged by `AIM_HULL_MARGIN`): you aim at the missile itself, leading it yourself. AI point defense (ai/gunner.ts): an automatic turret with a fast projectile (rifle, laser: `pointDefense`) tracks from 45 m the missile (or bomb) heading for its robot and fires when it is within its range, with the AI's aiming error (easy head-on, hard when it crosses).
- **Mines (`combat/mines.ts`, `ProjectileSpec.mine`: `MineSpec`):** a mine falls like a projectile and settles; `stepMine` then makes it wait `armDelay` s, then watch for what triggers it (`trigger`: an enemy on the ground or in flight within `radius` m, its layer's order, or nothing), and burst (explosion, EMP or smoke, depending on its projectile) or perform its `action`: jump to `height` m and burst there (`bounce`), launch another weapon's projectile at its target (`launch`: the anti-air mine fires a `flak` missile), stick to the block nearest the target, follow it and burst `fuse` s later (`stick`: `Projectile.stuck`). Nine kinds, each on its own layer (a fixed turret facing backward): mine, EMP, incendiary (a `napalm` explosion that sets almost everything ablaze), smoke, bouncing, anti-air, remote, sensor, sticky. **Remote**: the AI detonates it as soon as an enemy is on it; the player, by holding E (`PlayerInput.detonate`, `detonateMines`: one after another, including those from their previous lives, `ownedBy`); the HUD says how many they have (`detonateHint`). **Sensor**: its team spots enemies within `sense` m, through everything (sim/detection.ts), and it beeps as they pass. **Mine clearing**: an explosion sets off, on the next step, the mines within its radius (`blowMines`, called by `explode`), in a chain; a sensor or an anti-air mine is destroyed. **Avoidance**: a team spots laid enemy mines that one of its robots sees within `MINE_SPOT` m (`Projectile.spotted`, sim/detection.ts), and its ground AI steers around them (`avoidMines`, ai/navigation.ts, after `navigate`). The AI sows its mines when an enemy they can catch is in range (`mineUseful`: the smoke mine only when fleeing or in cover, a sensor not where the team already has one); mines against ground robots have a short preferred range (`engage` 12 m): the AI circles near its target, sowing them around it. The `mine` event (jump, stick, sensor beep; with its `NetEvent`) is used for sound; the replica deduces that a mine is laid from the fact that it no longer moves.
- **Detection (`sim/detection.ts`):** each team spots enemies within sight range (`SIGHT_RANGE`) with no wall or smoke in between, and within range of its radars or of its sensor mines (through everything); a jammer limits enemy radars. It also spots enemy mines it sees up close (see "Mines"). `isDetected` serves the AI and the pilot's HUD.
- **Props (`arena/props.ts`):** crates, explosive barrels (in chains), gas cylinders that leak and fly off. Damage only changes their state; `updateProps` triggers what follows. Each prop keeps its spot (`Prop.spot`) and its dimensions (`Prop.half`); an explosion hits it according to the distance to its surface (`propDistance`, arena/structures.ts: a shell against the end of a long wall hits it squarely).
- **Buildings and trees (`arena/structures.ts`):** anchored props (`PropTypeDef.anchored`: a fixed body that nothing pushes; `Prop.fixed`): wall panels and roofs are slabs (`shape: slab`, dimensions given by the spot; mass per m³ and hit points per m² of their largest face: bricks, concrete, planks, sheet metal, tiles), trees (pine, oak, enlarged by `PropSpot.scale`) and storage tanks (which explode and set off their neighbors) are cylinders. A wall panel that gives way breaks into large pieces (`DebrisLook.size`); a roof rests on walls (`PropSpot.rests`): when they have all gone, it is released (`releaseProp`: its body becomes dynamic, `propReleased`) and falls; a tree that gives way topples in the direction of the hit (`toppleProp`, `topples`: it keeps a share of its hit points), and breaks if it gives way again. The walls of the same building (`PropSpot.building`) form a single obstacle for the AI. Collisions damage them too (combat/collisions.ts), according to their `impact` resistance: an average robot at speed sets off a barrel, a solid hit punctures a cylinder, a Ram smashes a crate (wood: it resists bullets, not impacts); a small robot brushing against them only dents them. Wood burns (`burns`, see "Fire"): planks, roofs, trees, crates blacken (`Prop.charred`) and end up giving way.

### Melee weapons (`shared/catalog/melee.ts`, `shared/combat/melee.ts`)

A mass that spins, or an arm that strikes, carried by a block: not a turret, nothing is fired. Fifteen weapons done: the **horizontal spinner** (rotor) and the **pneumatic hammer** (triggered arm), which validate the two basic motions of the foundation; the energy family (see "Energy weapons", below): **laser blade**, **plasma whip**, **shock lance**, **crusher field**; two rotors that bite continuously instead of striking (see "Continuous bite"): **circular saw**, **drill**; the mechanical strikes (see "Mechanical strikes", below): **flipper**, **flail**, **crusher jaw**; and the spinner family (see "Spinners and cutting propeller", below): **vertical spinner**, **drum**, **shell spinner** and **cutting propeller** (a rotor driven by an engine, motion `driven`). Others are built on this foundation (recipe in "Architecture rules").

- **Data (`MELEE_WEAPONS`, `MeleeSpec`):** a block type with `melee` (a `MeleeId`) is its motor and hub. `motion`: `spin` (a rotor that keeps its energy) or `swing` (a cocked arm that strikes on command); `look` (drawing, sound, name of what it reserves); `axis` (`up`, `left`, `forward`: the axis of the rotor or pivot in the block's frame; `meleeAxes` also gives `e1`, angle 0, the front of the block, and `e2` = axis × e1); `hub` (the hub, block frame); `blade` (`SweptRing`: the ring the blade sweeps, radii `inner` to `outer`, half-thickness `half` along the axis; a bar or a disc sweeps a full disc, a drum a long cylinder, a shell spinner a ring around the robot); `spin` (`SpinSpec`: `inertia` and `speed`, hence the energy ½·I·ω², `spinEnergy`, and the angular momentum I·ω; `spinUp`, hence the motor power, `motorPower`; `spinDown`, freewheeling, hence what full spin costs, `holdPower`; `gyro`, multiplier of the gyroscopic effect, 1: physical; `unbalance`, the eccentricity at 0 HP, and `mass`, the rotating mass; `direction`, the direction of rotation); `swing` (`SwingSpec`: `reach`, `radius` of the head, angles `rest` (cocked) and `end` around the axis, θ = 0 in front, π/2 toward the top of the block, the head at `cos θ·e1 − sin θ·e2`, `headOffset`; `strike` and `recover`; `energy`, that of the head at the end of the arc, and `cost`, what a strike takes from the batteries); `hit` (`MeleeHit`: `damageType`, `damage` per kJ of the hit, `bite`, the share of a rotor's energy that a clean hit takes from it, `fling`, the share that throws the target, `push`, the direction of the impulse: along the blade's motion, outward, along the axis, toward world up, `recoil`, the share returned to the hub, `spread`, the share of damage dealt to neighboring blocks, `wheels`, `wear`, `gap`, `minSpeed`); `engage` (the distance at which the AI fights with it); `bite` (`BiteSpec`, a rotor that bites instead of striking: see "Continuous bite"). A blade longer along its axis than it is wide (`isBit`: `half` > `outer`) is a bit, its hub at the middle of its length. Damage type `cut` ("cut", that of blades; `impact` for a hammer): heavy armor 0.5, light 1.3, reactive 1.2, chassis 1.1, wings and control surfaces 1.5; wood 1.5, trunk 1.2, sheet metal 0.7, masonry 0.35, concrete 0.25.
- **Entity (`MeleeArm`, `Bot.melee`):** created with the organs (`registerOrgans` → `newMeleeArm`, also on the replica); `spin` (rad/s), `angle` (the rotor's, for its unbalance), `phase` (`ready`, `strike`, `recover`), `phaseT`, `swing` (the arm's angle), `from`, the step's commands (`wanted`: spin up the rotor; `trigger`: strike), set by the AI or the player and reset by `updateMelee`, `hitAt`, `fatigue`. It follows its block: destroyed, its rotor stops; regrown (`rebuildBlock`), it is the same block and the same weapon; on a torn-off part, it is no longer powered (freewheeling), but still spins, strikes and precesses on that part. Everything is read through `block.part` of a living block, never a freed body; `liveMelee`: those on the cockpit's part.
- **"Contact" step (`updateMelee`, in `Simulation.step` after collisions, before projectiles):** each weapon (spin, reaction, unbalance, measured hit), then the gyroscope of each part, then the hits, all measured before any is inflicted (`landHits`: impulses first, then damage hit by hit; a weak link of a part freed between two hits of the same step is not tested), then the fatigue of unbalanced rotors.
  - **Spin:** E loses E·(1 − e^(−2·dt/`spinDown`)) when freewheeling; commanded and powered (connected to the cockpit, not stunned), the motor gives back at most `motorPower`·η·dt (η = `MOTOR_EFFICIENCY`, 0.8), within what the batteries provide (`supply`, added to `bot.drawn` like thrusters); ω = √(2E/I). The angular momentum the rotor gains or loses, its robot receives in the opposite direction (`applyTorqueImpulse`: the motor's reaction makes a light robot that spins up its spinner pivot). Horizontal spinner: 3.1 kJ at 62 rad/s (592 rpm), I = 1.6 kg·m², spin-up in 2.4 s (1.6 kW), 0.5 kW to hold full spin (the generator provides 1.2).
  - **Hit:** the blade has no collider (like turrets' hitboxes, it collides with nothing): at each step where the rotor spins faster than `minSpeed` and `gap` s have passed, we look for what enters the swept ring, without physics: the blocks of each nearby enemy part, in its grid (a block counts as a 0.28 m ball, `BLOCK_REACH`), mounted wheels (a ball of 0.85 times their radius), and, one step in three, props (their point closest to the hub, `propNearest`; an anchored prop is ruled out from its spot, without reading its body), the scenery and the ground at the edge of the blade (eight `rayArena` rays, on only the boxes within the blade's reach, and `groundLevel`); a robot far from the blade (per `lastPos`) is not read. It strikes whatever reaches closest to the axis: the surface, not the center (`Contact.radial`: the center minus its reach; a tire sticking out from the side is hit before the hull). The hit takes E·`bite`·(0.35 + 0.65·g) from the rotor (g, the quality: see ricochet; on scenery, only 0.4 times as much, `SCENERY_BITE`; on the ground, `hit.ground` times, 0.4 by default); the `fling` share throws: J = √(2·μ·E·`fling`), μ the reduced mass of the two bodies at the point hit, each from its effective mass and inertia (`effectiveMass`: 1 / (1/m + (r × d)·I⁻¹·(r × d))); a fixed body or the scenery: the mass of the weapon's robot alone, and what does not move (ground, wall, anchored prop, `Contact.face`) sends the weapon back along its normal, plus friction against its direction of travel (`SCRAPE`, 0.5): the ground lifts the front of a hammer, and sends a vertical spinner that touches it upward; a rotor whose part is upside down scrapes the ground without being sent back by it. The impulse goes in the direction of `push` (for a rotor: the tangent to the circle at the point hit, in the direction of rotation, plus outward and up), tests the target's weak links (`DamageBatch.shock`); the reaction (`recoil`) goes to the hub, on the weapon's part, and tests its own (a spinner on an arm one block wide can tear itself off). Damage: E (kJ)·`damage`·(0.2 + 0.8·g) to the block hit (×`wheels` on a wheel), `spread` of that to its linked neighbors; credit to the weapon's robot, cause `MeleeId` (the feed, the `hit` hit feedback). The weapon wears: `wear` HP per kJ, divided by the resistance of what it strikes (heavy armor damages it twice as much). Event `meleeHit` (weapon block, point, direction, energy, what it strikes, `glance`). Horizontal spinner: a clean hit at full spin takes 1.69 kJ and does 288 cut damage (a normal armor block goes, its neighbors lose 100); on a Trike, the target flies off at more than 3 m/s.
  - **Ricochet:** on a shaped block, the blade strikes the face that faces it most (area × cosine, `shapeFace`); a cube face: clean hit; a slope: g = clamp((c − cos 70°)/(1 − cos 70°), 0, 1), c the cosine between the blade's direction and the face normal (`RICOCHET_COS`); the impulse loses (1 − g) of its component that drives into the face: it slides along the slope. A 45° glacis taken at an angle (c = 0.71): g = 0.56, `glance`. The blade of a horizontal spinner travels sideways (toward the robot's left, at the front): it is slopes turned toward its path that make it slide, not a frontal glacis facing up.
  - **Gyroscope:** a rotor has an angular momentum L = I·ω·axis (world); all those of a part add up (`gyro` included) and the part receives the torque L × Ω, integrated implicitly: Ω' = (1 − dt·I⁻¹·[L]×)⁻¹·Ω (`precess`, `solveLinear`; `setAngvel`), stable even when the rotor outweighs the robot's inertia. Horizontal spinner (vertical L, 99 N·m·s): yaw does nothing to it (L parallel to Ω); a roll makes it pitch up or down, a pitch makes it roll (measured, in the air: a roll of 1 rad/s gives in 0.3 s a pitch of 0.27 rad/s, against 0.03 with the spinner stopped). The vertical spinner (axis `left`) leans its robot in turns (see below). While an upside-down robot rights itself (`Bot.righting`), the cockpit's gyroscope prevails: no precession.
  - **Unbalance:** below `UNBALANCE_FROM` (50%) of its HP, the eccentricity grows up to `unbalance` at 0 HP (share u, `unbalanceShare`); a force m·e·u·ω² (at most 6,000 N) rotates with the rotor, at the hub; the robot's vibration, `vibration(bot)` = max u·(ω/ω_max)², degrades its aim (counted as `SHAKE_TURN` = 2 rad/s of rotation in `unsteadiness`, combat/accuracy.ts: the auto rifle spreads by 1.4°, the sniper no longer hits) and its wheels' grip (−30% at full vibration, `VIBRATION_GRIP`, robot/wheels.ts), and wears the weapon (`FATIGUE`: 5% of its HP per second at full unbalance and full spin, inflicted in chunks of 3) until it breaks. Everything is computed on the replica (spin and hit points go through the network).
  - **Continuous bite (`MeleeSpec.bite`, `BiteSpec`; `biteRotor`, `landGnaw`):** a hit mode of a rotor (spin, motor reaction, gyroscope, unbalance, network unchanged), generic: it will also serve a laser blade, a crusher field. Instead of striking, the blade bites what it touches at every step, without `gap`: the first thing it meets coming from its block (`rotorContact` with the base of its block: sorted by distance to it, not to the axis; the edge of the target for a saw, the first block on the axis for a bit; the bitten point is the block's entry, on its face turned toward the blade, `entryPoint`), robots and props at every step, the scenery one step in three and kept in between (`SCENERY_MEMO`; a bit: a ray from its base to its tip, and the ground at four points, `sceneryContact`). It takes the cutting power from its rotor: constant torque (`biteTorque` = `power` / full spin), × (0.35 + 0.65·g) on a slope, × 0.4 on scenery, × ω: the spin therefore drops under load down to the equilibrium where the motor makes up for it (`biteSpeed`), and its damage follows (`biteDps`: torque × ω × `damage` per kJ, × (0.2 + 0.8·g)); below `minSpeed`, it no longer bites. Its damage accumulates (`MeleeArm.gnaw`, simulation only) and lands in slices of `BITE_TICK` (0.1 s: otherwise sixty damage batches, `hit` hit feedbacks and network events per second), or as soon as it changes target or stops biting: the slice strikes the bitten block; if it gives way, what remains (minus its HP relative to its resistance) passes to the next one in the direction the blade advances (`feed`: from its block toward what it bites, in the plane of the disc; along the axis of a bit), cell by cell in its robot's grid, on the same part, up to `depth` m (`gnawChain`, like `pierceRobot`; only reads the grid: nothing from a freed body); its neighbors receive `spread` of it (the width of the cut). The blade wears (`wear` per kJ cut, divided by the resistance of what it bites). **Ricochet:** a slope is judged on the direction in which the blade advances (`feed`, not the motion of the teeth): a grazing glacis makes it slide. **Forces (measured, applied before any damage, `PlannedBite`):** the cutting force (tool torque = cutting torque × `gear`, divided by the blade radius, × `grab`) drags the target in the blade's direction at the bitten point and pulls its own robot the opposite way, at the hub (a saw: its grab; a bit, whose tip is on the axis, does not pull); a bit twists the target with its tool torque around its axis; in reaction, the robot receives the torque the motor opposes to the load (the motor's reaction, already there: `gained` only counts the motor and freewheeling, the load comes after) plus (`gear` − 1) times the load (the gearbox). `MeleeArm.bite` (`MeleeBite`: point, blade direction, surface, power in kW, `glance`) says what it bites at this step: the snapshot carries it (effects, sound, view shake). #### Energy weapons (laser blade, plasma whip, shock lance, crusher field)

Nothing spins or weighs at the end of the arm: no gyroscope, no recoil, no unbalance, but they drain the batteries and go out without power. The "clean" counterpart of spinners: an energy consequence, not a mechanical one.

- **Exemption from mechanics, through data:** a massless rotor has `gyro` 0 (no precession), `unbalance` 0 and `mass` 0 (no unbalance), and `SpinSpec.reaction` 0 (its motor's reaction does not make the robot pivot; 1 by default, physics); its "inertia" is now only a measure of its charge (E = ½·I·ω², which the motor rebuilds from the batteries the way a rotor spins up: `motorPower`, `holdPower`). A hit without `fling` or `recoil` neither pushes nor recoils (no impulse, no tested links, no shock at the hub; `landHits` skips what would be worth 0, and wear if `wear` is 0). **`MeleeSpec.quench`**: a weapon that goes out without power; without command, without power (cockpit lost, EMP, local stun of its block) or with its hub in water (`inWater`, arena/layout.ts: below the arena's surface, above a bottom lower than it, shallow or not), its energy drops to zero at once (`stepRegime`), and an arm does not go off. The common spin regime (losses, motor, reaction, gyroscope, unbalance) is `stepRegime`, shared by a rotor (`stepRotor`) and a field (`stepField`). A weapon's power supply (`powerOk`): connected to the cockpit, neither it nor its robot stunned, and (`quench`) out of the water.

#### Spinners and cutting propeller (vertical spinner, drum, shell spinner, propeller)

Heavy rotors, and their mechanical consequences: what they lift, what throws them back, what their gyroscope does to their robot. Tests: tests/spinners.test.ts (`MELEE_REPORT=1 … --silent=false` for the measurements; `SPINNER_BATTLE=1`: six battles with a Tumbler, a Drummer and a Whirlwind per team).

- **Vertical spinner (`verticalSpinner`, look `disc`, axis `left`, direction -1: the front goes up):** a 0.9 m disc (hub 0.72 m in front of its block, 5 cm above its center, between two cheek plates), I = 1 kg·m², 80 rad/s (764 rpm), 3.2 kJ, spin-up in 2.6 s (1.5 kW; measured: full spin in 3.1 s), `bite` 0.5, `fling` 0.8, push mostly upward (`tangent` 1, `lift` 0.6): a clean hit at full spin takes 1.6 kJ and deals 240 cut damage. Measured, on a Trike sideways: the hit goes upward (`dir.y` > 0.6), the target takes off at 3.9 m/s and flips over, then its gyroscope rights it. **Too low, the somersault:** `MeleeHit.ground` (1: a hit on the ground takes as much as a hit on a robot; 0.4 by default, `SCENERY_BITE`, as on a wall, which keeps 0.4); the ground throws the disc back along its normal (`Contact.face`, `floor`), at the hub, in front of the center of mass: the nose lifts. Measured: spun up, dropped from 90 cm with its nose 30° down, the disc bites the ground (1.6 kJ) and the Tumbler does a backflip (nose vertical, then onto its back). The Tumbler has 15 cm of ground clearance under its disc: in battle, it only touches the ground when nosing down, or when its front is wrecked. **When turning:** its angular momentum lies flat (80 N·m·s, along the axle, to the right): the torque L × Ω leans the robot **toward the inside** of the turn, whichever way it turns, and slightly brakes its yaw. With physics alone (`gyro` 1), this is weak: measured on a 2.5 m tower with four fixed wheels pivoting on the spot (1.25 rad/s), 0.4° more toward the inside than without the spinner; on the Tumbler, low and wide, less than 0.1°. A visible effect would require `gyro` 10 to 20, and then the robot hardly turns at all (precession converts its yaw into roll, which the suspension damps): not adopted.
- **Drum (`drum`, look `drum`, axis `left`, direction -1):** a toothed cylinder 0.9 m wide and 0.5 m in diameter, held in front of its block (hub 0.5 m in front, at its height: it occupies the row of three cells in front of it, arms included), I = 0.32, 115 rad/s, 2.1 kJ, spin-up in 1.8 s; the stable version: 37 N·m·s of angular momentum (less than half that of the vertical spinner for a comparable energy). Short, repeated hits (`bite` 0.3, `gap` 0.12 s: 89 damage on the first), which make the target hop (`lift` 0.7, `fling` 0.45) and tear off wheels (`wheels` 2.6: 231 on a wheel, a standard wheel or a track roller comes off in one hit). Measured, on a Buggy sideways, one wheel facing the drum: three hops, the wheel torn off; on a Tank: one roller torn off, no hop (too heavy). The blade strikes whatever reaches closest to its axis (the surface, see "Hit"): a tire sticking out of the side before the hull.
- **Shell spinner (`shellSpinner`, look `shell`, axis `up`):** a steel ring (radius 1.48 to 1.6 m, 0.95 m tall) around the whole robot, hung from four spokes resting on top; its block, at the center of the top, is its hub (the hub of the rotation is 0.185 m below it: the middle of the ring). `SweptRing.inner` > 0 (the robot fits in its hollow; `allAround` from 0.8 m) and `SweptRing.web` (the web of the spokes: a disc to reserve above the robot, which does not strike). I = 24, 24 rad/s, 6.9 kJ, spin-up in 3.2 s (2.7 kW: on the batteries), `bite` 0.25 (173 damage on the first), `gap` 0.2 s; on the ground, it scrapes (`hit.ground` 0.15). It strikes on all sides without aiming: the AI does not present it toward anything (`meleeBearing` ignores it) and the player only has to charge in. It never strikes its own robot (`rotorContact` skips its robot; measured: four walls around it, all cut into, its other blocks intact). **The whole robot becomes a gyroscope** (576 N·m·s vertical); its motor's reaction makes it pivot and skid when the ring picks up speed (measured, full throttle in a straight line for 4 s: 11.6° of heading and 2.4 m sideways, against 1.2° and 0.2 m with the ring stopped). **The ring serves as armor:** its hitbox goes all around the robot, every shot from the side hits it; it therefore has 1,400 points and the resistances of a steel hull (bullets 0.45, fire 0.35; at 600 points, a Ram's rifle and flamethrower broke it in five seconds); a shot from above hits the robot inside. No blur disc: the band can be seen turning by its strikers. **Upside down**, its spinning ring scrapes the ground without being thrown back (see the framework, below): it settles, and the cockpit gyroscope rights it in ~4 s (measured, upside down, ring at full spin); before, each contact relaunched it at several m/s, it never settled, and the match self-destructed it (13 self-destructs over six battles). Tilted (20 to 35°: after righting, a collision), it touches the ground on one side and rolls on its ring like a wheel, at over 10 m/s, until its gyroscope lets it settle flat again.
- **Cutting propeller (`propeller`, look `propeller`, motion `driven`):** the `propeller` block (the aircraft propeller, an engine) also carries a melee weapon: its three blades (dimensions from `BLADES.propeller`: radius 0.975 m, hub 0.35 m in front of the block; a test compares them). **`driven` motion (`DriveSpec`, `drivenSpeed`):** the spin follows the thrust of its block's engine (at idle, `idle` 0.28 of 50 rad/s, faster with thrust, stopped below `stop` 2%: throttle cut), reached in `spinUp` (0.6 s) or `spinDown` (3 s); nothing is drawn from the batteries (the engine pays), no motor reaction (its `torqueRatio` is its own), nobody commands it (`wielded` false: not in `liveMelee`, nor in the weapon bar, nor in tactics, nor in a robot's listed weapons; `meleeOffensive` false), no unbalance (`unbalance` 0: a damaged propeller already has its own, that of a damaged engine), no gyroscope (`gyro` 0: its 40 N·m·s disturbed the autopilot, the Bomber no longer lined up on its target). 1 kJ at full spin, `bite` 0.7, 170 damage per kJ (119 at most), `gap` 0.1 s, **`wear` 60** per kJ: it breaks. Measured, the Plane held in the air at full throttle, its propeller lowered onto a heavy armor wall: two hits (545 and 225 J), 115 points to the wall, the propeller broken in 0.13 s, the engine lost; on normal armor, it holds for three hits (under half its hit points, the engine already loses thrust: `wearEngines`). The blade rendering (`LocomotionView`) takes its spin from the weapon (`MeleeArm.spin`, which goes over the network): a hit slows them down. In battle, the AI's planes graze nothing (not one propeller hit in six battles): the risk is for the player who skims an enemy.
- **Framework, what the spinners required:** hitboxes for blades and arms (see above); the reaction along the surface of what does not move (`Contact.face`, `SCRAPE`); the surface closest to the axis rather than the center; `hit.ground`; a hollow cylinder in the clearance (`Solid.inner`: a tube; `inHole` rules out at once whatever fits in the hollow); no precession while righting; an upside-down part (`FLIPPED_UP_Y`, robot/righting.ts): its blade scrapes the ground (losing its energy there) without throwing its robot back; `meleeSolids` also reserves a ring's web; in the garage, a lying rotor (axis `left`: disc, drum) does not orient to the face (placed on the front of a block, it would stay lying on its back); the contact reads less (a robot far from the blade is not read, props one step in three, only the scenery boxes within reach: `rayArena` accepts a list of boxes).

#### Mechanical strikes (flipper, flail, crusher jaw)

Three more motions (`flip`, `flail`, `grip`), in combat/mechanics.ts, called by the `switch` of `updateMelee`; their hits go through the planned hits (`PlannedHit`, `plans.hits`), measured before any of them is inflicted. What they compute themselves, they hand to the hit (`PlannedHit.impulse`, `reaction`, `damage`). Their blocks are heavy and sturdy (`resist`: cut 0.7, kinetic 0.85, impact 0.8; `bond` 250).

- **Flipper (`flipper`, look `plate`, motion `flip`, axis `left`; block: 40 points, 16 kg, 240 HP):** a 1 m by 1.4 m wedge-shaped plate in front of its block (`PlateSpec`; pivot 0.3 m in front of, 0.1 m below the center of the block; at rest at −0.24 rad, its edge grazes the ground in front of a tracked robot). On the trigger, if it has 8 kJ in its batteries (`cost`), the actuator raises it to 1.15 rad in 0.14 s, accelerating (its angle in `MeleeArm.swing`, its phases like an arm); the first robot (block, wheel) or movable prop that the plate meets above it (`plateContact`: twelve points of the plate, in steps of 0.06 rad, in the grid of the enemy parts, without physics) is lifted, once per lift: the actuator gives it the work it has left (`energy` 4 kJ × the share of the stroke remaining), J = √(2·μ·E·`fling`) up and forward (`push`: the direction of the plate, plus `lift`), without exceeding 1.2 times the plate's speed where it bears (`PLATE_SPEED_SHARE`). The reaction (`recoil` 1) goes to the pivot: a robot on the ground tips around its frontmost supports (`frontContact`: the wheels that bear load or the supports on the ground, within 0.3 m of the frontmost one), which the ground does not let sink in; its effective mass at the pivot takes this into account (a unilateral constraint at that point), the reaction does not push it in faster than 2.5 m/s (`REACTION_MAX`, below the speed at which a collision does damage: the ground absorbs the rest), and what the support holds back lifts its rear. The hit deals 30 `impact` damage per kJ (120 at full stroke), `spread` 0.25; above all, the target is marked as thrown (`Bot.thrownBy`, 3 s): its collisions as it falls back down (combat/collisions.ts) are credited to the flipper (cause `flipper`), except against it. Then the plate comes back down (0.5 s) and the actuator recharges: one lift every 3.3 s. Measured: the Catapult (163 kg) lifts the Reaper 1.5 to 1.8 m and flips it over, and the fall costs it more than the hit; a Trike flies 3.4–4.2 m; a small ~40 kg flipper under the Truck lifts it only 0.2 m, noses down itself by 11–12° and its rear takes off; the Catapult lifts the Truck 0.6 m. The AI lifts when the first half of the lift would raise an enemy robot (`flipWouldHit`).
- **Flail (`flail`, look `flail`, motion `flail`, axis `up`; block: 35 points, 12 kg, 200 HP):** a 0.4 m crank at the top of a mast (hub 0.9 m above the block) and a 7 kg spiked ball (radius 0.16 m) at the end of a 1.4 m chain (`FlailSpec`). A gear motor drives the crank (kinematic: it reaches its spin, 7 rad/s, in 0.4 s, `CRANK_RAMP`, whatever the chain pulls; with empty batteries, more slowly; `flailPower`: enough to launch the ball in 3.5 s, `spinUp`, ~0.2 kW); its flywheel (`inertia` 0.25 kg·m²) has a rotor's gyroscopic effect. The ball (`MeleeArm.ball`: position, velocity, wound chain) is a point integrated at the fixed step: gravity, air drag (`drag`), bounces on what is fixed (Rapier rays filtered on the scenery, the ground and anchored props; `restitution`, Coulomb friction `friction`; resting, it rolls, `ROLLING`) and on robots (in their grid; its own robot pushes it away without damage), then the chain, a unilateral constraint (it only holds back) whose tension is an impulse between the ball and the end of the crank, which the robot receives there (its effective mass): this is what destabilizes it, the ball pulls on every revolution and does not follow the robot's turns. The chain going faster than the ball (the crank leading it by more than 30% of its spin) winds around the hub (`wound`) then unwinds: the ball launches without a jolt. A hit on an enemy robot (one every `gap` 0.12 s at most) has the energy ½·μ·v² (v, the ball's speed relative to the point hit; μ, the reduced mass): 250 `impact` damage per kJ, `spread` 0.3; below 3 m/s (`minSpeed`), it only pushes; it bounces. **Wrapping:** if the chain crosses an upright fixed obstacle (post, trunk, wall: nearly horizontal normal, at least 0.3 m of chain beyond), it wraps around it (`FlailBall.wrap`, the pivot point): the crank locks, the ball turns around the pivot point, the chain holds the robot at that point, until the ball passes back to the other side, the robot pulls with more than 4 kN (it slips), or after 4 s. Upside down or righting itself, its motor cuts out (`capsized`). Measured: launched in ~3.5 s, the ball circles 1.73 m from the axis (`flailOrbit`, conical pendulum) at ~10.9 m/s; as a pendulum (crank stopped, on a gallows), a 2.36 s period for 2.37 expected (2π√(L/g)), fastest at the bottom; twice as fast, four times more damage (3.99 measured); when turning, the robot pitches and rolls ten times more than with the ball stopped (0.38 rad/s against 0.04); the chain wraps around a post. The AI launches it like a rotor (`spinRange`); the player, as long as it is the selected weapon.
- **Crusher jaw (`jaw`, look `jaw`, motion `grip`, axis `left`; block: 45 points, 18 kg, 300 HP):** two toothed jaws 0.8 m by 0.6 m, hinged 0.28 m in front of their block, open to ±0.55 rad (`JawSpec`; the half-opening in `swing`). On the trigger, they close in 0.2 s; the first enemy block in the mouth (`inMouth`: 0.15 to 0.85 m from the pivot, between the two jaws at their current opening) is seized: a bite (60 damage), then the **grip** (`MeleeArm.grip`, `JawGrip`: the seized block, the grip point in each robot's frame, the slip, the accumulated crushing; phase `hold`). It is held **by impulses, not by a Rapier joint**: at each step, the two points are brought back together (a point constraint solved with the effective masses and inertias of both bodies, `pointCompliance`, plus 25% of the gap, `GRIP_BIAS`) and 60% of their relative rotation is damped, within the limit of what the jaw can hold (`strength` 6 kN, and a torque of 6 kN × 0.35 m): so it is the heavier one that does not move. The grip is only a state (two blocks, two points), checked at the start of each step **before reading a body** (`holdable`: the jaw powered on the cockpit's part, the prey alive and in `sim.bots`, the seized block alive on a part still in `sim.parts`); nothing remains in Rapier that would have to be removed before freeing a body (part destroyed, robot removed, split), and the force it requires is known: beyond 6 kN, it slips, and after 0.4 s of slipping (`slip`) it lets go; with the two points more than 0.6 m apart (`tear`), it is torn off. As long as it holds, the actuator squeezes on the batteries (1.6 kW; empty, it holds less) and it crushes the seized block (110 `impact` damage per second, in 0.25 s slices, `spread` 0.25; a 0.35 kJ `meleeHit` per slice, for effects and sound); once the seized block is destroyed, it bites the prey's block closest to the grip point, 0.8 m away at most (`REBITE`; all parts of a robot share its frame), otherwise it lets go. It also lets go when the trigger is released, after 6 s (`hold`), when the jaw is destroyed, torn off or stunned, when the prey is destroyed or removed; then it reopens (0.4 s) and waits 0.8 s. Measured: the Crusher (170 kg) bites a Trike and drags it 3.3 m while backing up, the two together (238 points in 1.5 s); a small ~40 kg jaw on the Truck moves it only 0.19 m and hangs on to it (the Truck is the anchor); it holds a heavy wall for 6 s, then lets go; it lets go without error when the prey is destroyed or removed, or when it is itself destroyed; against a Scarab (AI against AI), two 6 s grips, 18 blocks and 1,860 points in 13 s. The AI closes when an enemy block is in the mouth (`jawWouldBite`), holds as long as it has its prey and drags it backward (`meleeDrive`, called by `thinkGround`: throttle −0.8, without steering, neither stuck nor needing to break free); a fast robot that keeps its distance (the Trike) escapes it.
- **Common:** the player raises the flipper and closes the jaw with the trigger (it holds as long as the trigger stays held); the flail turns as long as it is the selected weapon. Gauge (`meleeReadiness`: the actuator recharging, or the missing battery charge; the ball launching; how much grip is left), weapon bar (`hud.meleeTag` "lifts", "flail", "grabs"; the jaw squeezing: `showArsenal(…, holding)`), sights `flip`, `flail`, `jaw` (`SIGHTS`). Rendering (`MeleeRig`): the plate and its actuator, the upper jaw with the hub and the lower one separately (`MELEE_PIECES`, `meleePieceSource`: the lower jaw, the ball, a link), the crank, the chain as links (`chainPoints`: taut, with a little sag when slack, bent at the pivot point when wrapped) and the ball; the same still pose outside the game (`stillMechanics`, called by `stillMelee`). Recorded sounds: the release of the flipper's actuator (`flipper-swing`; the plate hitting a robot borrows `collision`), the clack of the jaws (`jaw-swing`, played 15% lower; what they seize borrows `collision`) and the crunching (`jaw-crush`, a loop held as long as the crushing slices follow one another), the whirling chain (`flail-whirl`, which swells twice per revolution as the ball passes, with, underneath and lower, `FLAIL_UNDER`, the synthesized low whoosh: a filtered sawtooth voice, `FLAIL_LEVEL`) and the ball's hit (`flail-hit`); their synthesized fallbacks remain. Garage: info cards (lift, recharge, energy; ball, hit, motor; bite, grip, energy), thumbnails (the plate, the jaws, the mast and the ball's disc).
- **Robots:** the **Catapult** (flipper in the middle of a heavy-armor nose, heavy deck, tracks; 319 points, 163 kg), the **Crusher** (jaw between two heavy-armor cheeks at the end of the nose of a tracked tank, dome; 333 points, 170 kg) and the **Thresher** (a heavy-armor slab on tracks, the flail in the middle on its mast; 179 points, 77 kg; on four wheels, it lost them under fire and self-destructed), all three `charge`. ### Effects (`client/render/fx/`)

- **Building blocks:** three fields, each in thin instances (`InstanceLayer`, layer.ts: one mesh, a matrix and a color with its opacity per instance, a single GPU call; only the instances written in the frame go to the GPU): `ParticleField` (particles.ts: particles that are born, move, grow and fade, drawn as spheres or sprites depending on the look, see below; four kinds, lit `smoke`, `vapor` and `glow` in their own color, `fire` (flame, fireball: a glow in simple effects); drag, gravity, stretching along the velocity, a light wind), `StreakField` (streaks.ts: segments that stay in the air, widen and fade; a turning trail is made of segments end to end) and `MarkField` (marks.ts: discs and strips laid on the ground or the scenery, which live a long time; when full, it replaces the oldest; `surfaceAt` gives the height and normal of the ground or scenery under a point). Unlit layers have a white emissive color (otherwise Babylon renders them black), and all use normal blending: in broad daylight, an additive glow turned white on light ground. Caps per kind, lowered by the "Reduced" effects setting (`setReduced`), which also lowers `density`. The randomness of effects is the browser's (`jitter`), never `rand` (the simulation's). A particle or streak is drawn as it is born before it ages (`fresh`): at low frame rates, a spark shorter than a frame would never be seen; `fadeOut` makes a particle fade only at the end of its life (shell casings). To judge a brief effect without a GPU (headless Chrome, ~3 frames/s), advance the simulation by one step and the effects by 1/60 s per frame (`timeScale` at 0, `sim.step()` in `scene.onBeforeRenderObservable`, `fx.update` wrapped): you see what a player sees at 60 frames/s (or, simpler: stop the loop, `engine.stopRenderLoop()`, then call `game.frame(1/60)` and `scene.render()` yourself as many times as needed, before each capture). In a 12-robot battle, ~600 particles at most and ~0.4 ms per frame for the effect systems (measured by wrapping `fx.update`). **Measure on the built version** (`vite build` then `vite preview`, on a port and a cache of your own): on the dev server, a dependency re-optimization partway through makes the page lose the shader chunks loaded on demand (glow and blur no longer compile: their source is the HTML page, "'<': syntax error"), and each frame vainly rechecks their shaders (five times slower).
- **Realistic smoke and flames ("Smoke and flames" setting, `Settings.fxLook`: `realistic` or `simple`):** in realistic effects, particles (`smoke`, `vapor`, `glow`, `fire`) and streaks are **sprites**: quads turned toward the camera in thin instances (`SpriteLayer`, sprites.ts: one GPU call per layer; the vertex shader orients them, since `billboardMode` does not work per thin instance; 20 numbers per instance, stored in the thin instances' "matrix" and color: center and diameter, stretch and angle, atlas cell, age, heat, ground, upright flame, shadow, seed). A **billow** (`smoke`, `vapor`) is a cell of an atlas of four puffs computed at startup (fxNoise.ts: balls melted into one another, with a frayed edge; red and green, the normal of their surface; blue, occlusion; alpha, density; ~0.3 s of computation, a `RawTexture`), lit by the scene's light re-read each frame (sun, sky, ground: `FxMaterial`, fxMaterial.ts) according to that normal, which turns slowly, rolls (a scrolling noise warps its texture) and frays as it ages; black smoke stays black, vapor is almost its own color. **Soft edges**: a billow fades as it approaches the ground below its starting point (`groundAt`, `groundLevel`: no hard cut where it crosses it; no depth render, see below), and a large billow right against the camera fades (it surrounds it). Smoke and fire layers are **sorted** from farthest to nearest each frame (smoke and fire: ~1,200 sprites at most in battle). A smoke particle that does not grow (fragment, chip, shell casing, clod) stays a small solid ball (the sphere layer). A **flame** (`fire`) is a drop-shaped tongue that undulates as it rises (two scrolling noises), from white-yellow to red according to its heat (`PuffSpec.heat`, which drops over its life; `fireRamp`), never darker than a dark red (almost black, it looked stained), with a crisp edge (when going out, it shrinks to its core instead of fading, otherwise it turned pink against a light background); a **fireball** (`billow`) is an incandescent billow that rolls then cools into smoke of its color. **Premultiplied blending**: a flame's core is partly added to what is behind it (it lights up without whitening light scenery, like the former additive blending), smoke hides it. **Streaks** become camera-facing ribbons, with a soft profile, frayed. The **smoke cloud** (smokeCloudFx.ts): 24 billows at the core, opaque, slowly turning around the center, and 14 at the edge, which spill over, drift away while fading and are reborn, given again each frame (`ParticleField.volute`, sorted with the other smokes); it grows and dissipates like the simulation's (`smokeRadius`), fraying as it dissipates; up close, fewer billows, more opaque (the cloud stays as thick, the graphics card draws fewer pixels); with the camera inside, a veil of billows surrounds it at 2.4 m: you cannot see more than a few meters. Elsewhere: **explosions** (`FIREBALLS`, blastFx.ts, exhaustive over `ExplosionLook`: a brief flash, fireballs that widen as they roll then blacken, smoke that follows and rises, a spray of earth the color of the ground for a mine or a bomb, fragments), the **flamethrower jet** (projectileTrails.ts: each jet spits fireballs along its path, redder and redder, and smoke at the end; ProjectileView hides its balls), the **flames of burning blocks** (`blockFireFx`, fireFx.ts, from `fireStarted`/`fireEnded` and `LiveSet`; WorldView hides its cones: the fire stays attached to the block, three tongues placed again each frame on its highest free face (`ParticleField.flame`, flames placed for one frame and sorted with the others; a margin, `FACE_KEEP`, before switching faces when the robot tilts), which undulate in place (their shader's noise scrolls, their size pulses) and lean opposite to the block's motion (`FLAME_LEAN`, smoothed); it catches in `CATCH` s and dies down in `DIE` s; smaller tongues break away at the block's speed, and the smoke leaves with part of its speed, tighter the faster it goes (a continuous trail). Before, each flame was a particle released into the world: it stayed behind when the robot moved forward, and the fire advanced in jerks. Every upright flame leans opposite to its horizontal velocity: its top, in its sprite's stretch, `Sprite.ax`, and its height, the length of that vector), the **dust** of a collapsing wall (`Fx.dust`) and the **engine flames** (flames.ts: an open cone, with no disc at the nozzle, whose shader streams a noise from the nozzle to the tip, softens the edges and makes them flicker, and tears the tip; blue-white core and shock diamonds for a turbojet; `Assets.flameFor`, `jetFlameFor`). In simple effects, everything stays as before (spheres, plain cones, `EXPLOSION_STYLES`, `SmokeView` bubbles). The change applies live (`ArenaGame.setFxLook`: `Fx.setLook`, `Assets.setFlameLook`, WorldView, ProjectileView, SmokeView; living particles change look on the next frame); warm-up (`Fx.warmUp`, `WorldView.warmUp`) compiles the shaders of the current look. The materials of these effects (`FxMaterial`, a `ShaderMaterial`) have two pitfalls: the glow layer draws them with their own shader (`_supportGlowLayer`, uniform `glowPass`: only the fire's core shines in it, smoke is only a black mask there), and a thin-instanced mesh must keep its instanced shader (`isReady` forces instances: the glow layer, which checks the material without them, made it switch shaders twice per frame, ~8 → ~57 ms of rendering). And an integer passed to the shader per instance (the atlas cell) arrives interpolated, at 1.99999 on one triangle and 2 on the other: round it (`floor(x + 0.5)`), otherwise a large nearby billow was cut sharply along its diagonal. **Ruled out:** a true volume for the cloud (a box in which the shader steps through a lit 3D noise): from inside or up close, the cloud covers the whole screen, and 32 to 64 noise steps per pixel cost far more than billows on a small graphics card; fading against all the scenery ("soft particles" based on the scene's depth): Babylon does not read the depth of the current frame, it would need an extra depth render (`DepthRenderer`: the whole scene redrawn; the shadow map, such a render, costs a quarter to half of a battle's rendering, measured by turning shadows off); the fade near the ground, computed from the terrain, covers most of it. **Measured cost** (headless Chrome on the machine's graphics card, GTX 1660 Ti Max-Q via ANGLE, 1264 × 625 image, built version, machine loaded by other computations: averages of alternating series): 12-robot battle in the Depot, 66.6 → 57.7 frames/s (1 to 2.6 ms more per frame depending on load), of which the effect systems 1.3 → 2.0 ms per frame (sorting and writing sprites, block flames); heavy case (three smoke clouds and a wood fire right nearby): no difference at 1264 × 625 nor at 2528 × 1250 (both held at ~128 frames/s), 7.8 → 16 to 18 ms per frame at 5056 × 2500 (the graphics card fills the big billows). The Low preset keeps simple effects.
- **Systems:** `Fx` (fx.ts) holds the fields and the effect systems (`FX_SYSTEMS`, systems.ts: one file per family, one line in the list); each receives an `FxContext` (displayed world, fields, camera position, the robot whose scope the camera is in, `density`, `look`: the look of smoke and flames) and listens to world events, from which it unsubscribes in `dispose`. `ArenaGame` creates it, runs it each frame after the simulation, and attaches it to the replica online (`bind`): an effect reads only what the renderer reads, so it works online without changing anything in the protocol. `emissions` smooths a rate from one frame to the next; `FX_RANGE`: beyond it, nothing to emit.
- **Projectile trails (`projectileTrails`, render/fx/projectileTrails.ts):** one look per weapon (`STYLES`): smoke in puffs evenly spaced along the path (continuous at all speeds; puffs are born bigger than their spacing, so that a missile in flight keeps fewer than 200 of them and a salvo of eight rockets ~600) and booster flame: guided and lock-on missiles (white), anti-air (gray), rockets (thin and short: the fan is visible), warhead (thick), shell and smoke (a thread), flares (ample smoke that draws arcs as it falls; it replaces the old smoke from `game.ts`); blue sparks of the EMP shell, a swarm of green sparks for the nanites (which no longer have a body: `ProjectileView` does not draw them). A lost missile (`Projectile.lost`, flare burnt out: locally only, the replica does not know it) spits dark smoke in bursts. Where a `flak` explosion bursts, a black cloud floats for a few seconds. A shot-down projectile (`Projectile.blown` locally; online, an `impact` with surface `projectile` very close within 0.35 s): an incandescent fragment spins off (`FRAGMENT_LIFE`), its streak drawn in small steps (round even at low frame rates). Sniper and railgun: a vapor wake (and, for the railgun, a glowing core and crackling arcs) from the muzzle to the impact, from the `shot` event and the `impact` that falls on its line (`LINE_MATCH`), or up to `LINE_MISS` m without an impact after `LINE_WAIT` s: bullets go too fast for the replica to see them all. When scoped, nothing from one's own shots within `OWN_NEAR` m of the lens.
- **Firing (`muzzleFx`, render/fx/muzzleFx.ts):** from `shot`, `impact`, `hit` and `blockRepaired` (all sent over the network), the turret of a shot found by its muzzle (`firingTurret`): shell casings ejected to the right of the breech, which fall keeping the robot's velocity (`CASINGS`: rifle, sniper, shotgun in red, cannon as a big casing); smoke lingering at the muzzle (`MUZZLE_SMOKE`: cannon, sniper, shotgun, railgun, EMP, smoke); a ring of dust on the ground under the robot on a cannon or railgun shot (`surfaceAt`, if it is within `DUST_REACH` m of the ground); a plume blown out the back of the tube when a missile launches (`BACKBLAST`, with a flash); an incandescent spot and smoke where the laser and plasma hit (the impact that falls on the line of a pending shot); repair beam: on a `hit` with cause `repair`, red streams flow from the enemy's block nearest the beam's line toward its muzzle (life steal), and on a `blockRepaired` of an ally close to the line of a teammate's recent beam shot, green streams go from the muzzle to the block (at most one flow every `FLOW_GAP` s per robot; particles stretched along their path, which arrive at the end of their life).
- **Tracers (`ProjectileView`):** one rifle bullet in `TRACER_EVERY` (based on its `id`, the same on the replica) is a tracer: longer, thicker, in the shooter's team color (`TEAM_COLORS`, whitened; yellow for the free camera).
- **What can be read (`LiveSet`, fx/tracking.ts):** parts still in the world (from `partAdded`/`partRemoved`) and wheels not yet removed (`wheelRemoved`): an effect reads the pose of a block (`blockPos`, a live block on a part still present) or of a wheel only through it, never in an event listener, where a body may be in the middle of being freed; a wheel wreck removed by `removeBot` keeps its freed body in `rb`. Also: `countOf` (number of emissions during `dt`, the remainder drawn at random), `groundRgb` (ground color under a point: the terrain like `ArenaView.groundColor`, the flat ground of small arenas, a neutral gray on the scenery) and `toHex` (color rounded to 1/24: the fields' color cache stays small).
- **Damage (`damageFx`):** a block below half its hit points smokes, darker below a quarter; the list of damaged blocks is kept from `blockDamaged`, `blockRepaired`, `blockRebuilt`, `blockDestroyed` (we don't go through all the blocks), and each robot draws only a few billows from it (`BOT_SMOKE` per second at most, among its damaged blocks, the most damaged ones more often: 48 blocks each smoking made an opaque cloud that hid the robot). Damaged battery, shield, radar, jammer: arcs and sparks in bursts. A robot close to the structure rule (`integrity` less than `CRITICAL_MARGIN` above `WRECK_INTEGRITY`) blazes: flames and thick smoke on its most damaged blocks (the cockpit is often buried; the flames leave at the robot's speed: they race along with it). A torn-off part (or the whole wreck) smokes and spits sparks as long as it moves fast, for `DETACHED_LIFE` s at most. A destroyed robot leaves a column of smoke for `WRECK_SMOKE` s, which blazes at first and throws embers, at the biggest of its parts still present (pulverized, where it was). Damaged mounted wheel: smoke, and a scraping rim makes sparks (wheel hit points and load: locally only, they do not go through snapshots); wheel wreck: it burns for `WHEEL_BURN` s (torn off: it no longer has a hub carrier, which is also visible online). Barrel of a weapon heating up (`Turret.arm.heat`, not the repair beam): a glow at the end of the barrel, from dark red to orange beyond `GLOW_HEAT`, and smoke when it cools down or overheats. Nothing for the robot whose scope the camera is in.
- **Block wear (`wearColor`, render/worldView.ts):** a damaged block darkens, scorches (green and blue drop more than red) and gets stained (each block in its own way, from its identifier); it blackens with soot (`WorldView.soot`) if it caught fire (`fireStarted`) or if an explosion licked it (`blacken`: blocks within `SOOT_REACH` radii, from the displayed pose of the parts, without re-reading their bodies), and gradually in an engine's flame jet (`readJets`: `JET_SOOT` per second at `JET_SOOT_HEAT` damage per second; the block the jet hits, from `jetContact`, re-read every `JET_SOOT_EVERY` s of simulated time). A repair erases part of it, a regrown block comes back clean.
- **Ground (`groundFx`):** in each lane of a robot (same lateral offset), among its lowest mounted wheels, the leading one leaves the trail (`Lane`: the front one going forward, the rear one in reverse, according to the speed along the robot beyond `LEAD_SPEED`; the others roll in its rut, a single trail per lane; a track is a lane, its front roller leaves the trail under the belt): strips (`MarkField.strip`) end to end, every `MARK_SPACING` m or as soon as the trail turns by `MARK_TURN` (otherwise the outside of turns was left with gaps), and each frame a provisional strip from the last one laid to right under the wheel (`MarkField.liveStrip`, outside the ring: given again each frame, otherwise it disappears): the trail comes out from under the wheel instead of appearing behind it; when the robot changes direction, the current strip is laid up to the last contact (`finishTrack`); darker than the ground (more so for a track), they fade in `MARK_LIFE` s; beyond `MARK_RANGE` m from the camera, nothing. A wheel touches the ground if a ray cast downward from its center (`rayArena`, and the terrain) finds it less than `TOUCH` below it: this is read from its pose, online too; the ground found is reused as long as the wheel has not moved by `FLOOR_REUSE`. Dust the color of the ground, lightened: speed on dirt, skidding (speed along the axle), bursts of throttle. In the river (below the `arena.water` level, the bed lower than the surface): splashes and foam instead of trails, for wheels, hover pads skimming over it and feet; an impact or explosion in the water raises a plume (droplets, foam, and a column of spray for an explosion). Legs: when a foot lands (the walking phase makes the cosine that lifts the foot go below 0, as in `LocomotionView`, whose `FOOT_OUT` and `HALF_STEP` are exported), a puff of dust and a footprint (`MarkField.disc`). Heavy landing (a fall at more than `HARD_LANDING` m/s that comes to a stop): a ring of dust, or a plume in the water. Collision (`collision`): a flash and a spray of stretched sparks, matching its force; an overturned robot that slides scrapes the ground (sparks). When changing arenas, the old one's ground marks disappear (`arenaChanged`).
- **Explosions and scenery (`blastFx`):** on the `explosion` event (the explosion itself: in realistic effects, here, `FIREBALLS`; in simple effects, the layers of `EXPLOSION_STYLES`, render/effects.ts, which `ArenaGame` then does not play in realistic effects), what remains: near the ground (`GROUND_REACH`: not for an airburst), a dark crater, a scorch mark around it and, for a mine, a bomb or the warhead, a ring of upturned earth (`CRATERS`, exhaustive over `ExplosionLook`, in explosion radii; `MarkField` discs that fade in a minute), smoke that keeps rising for a few seconds (a smoldering spot, `Smolder`) and dust raised in a ring by the blast; embers falling back in arcs with their trail (tracked by the system, `MAX_EMBERS`, put out on the ground). And the scenery: the white gas jet of a punctured cylinder (from its hole, `state.leak`), the sparks of a barrel's fuse (`state.kind === "fuse"`), the smoke from the ruins of a destroyed wall panel or roof (longer and blacker if it was burning; position from its spot, `spotPose`, or its last recorded position if it had fallen: never its removed body).
- **Scenery fire (`fireFx`):** burning wood spits flames (three tints: yellow core, flame, red tongue; in realistic effects, tongues of fire of three heats, 1.45 times bigger, `flameScale`) at its surface (`pointOn`: the cone of a pine, the ball of an oak, a face of a crate or a wall, mostly the top; born inside, they were hidden), a column of dark smoke and embers, the more so the bigger it is; a puddle of fire, flames at ground level (higher in the center), a little smoke, and scorched earth (a disc that stays 45 s). Everything is read from `prop.burn` and `world.groundFires`: online too. **Charred wood (WorldView):** each charring step (`charLevel`: scorched at 25%, charred at 75%, on the steps announced by `propFire`) has its material (`PropModels.source(…, char)`: the same texture darkened, `CHAR_TINT`; a tree has its bark blackened and its foliage scorched then charred); the prop switches source at the same pose (`charProp`). **Trees that bend (WorldView.swayTrees):** an explosion's blast makes nearby standing trees lean away (`SWAY_MAX` at most, depending on distance), around the foot of their trunk, then they oscillate, damping out, and return to their pose (the trunk does not move in the physics).
- **Optional lighting (`render/lighting.ts`, `SceneLighting`, created by `ArenaGame`):** three graphics settings. **Glow** (`GlowLayer`, in a texture at 40% of the screen): whatever is unlit and has an emissive color shines (engine flames, glowing projectiles, mine lights, glows from explosion effects), except labels, zones, vapor, smoke and marks (`NO_HALO`); the glows of thin-instanced effects (`Fx.glowMeshes`) go through their own material (`referenceMeshToUseItsOwnMaterial`), to keep each instance's color, and realistic effects (sprites, engine flames: `FxMaterial`) through their own shader (`_supportGlowLayer`), where only the fire's core shines; other meshes mask the glow (it is not seen through a wall). **Dynamic lights** (setting `Settings.lights`, "Dynamic lights"): if the graphics card can do clustered lights (WebGL 2, float texture blending: Babylon's `ClusteredLightContainer`, `SceneLighting.clustered`), a pool of 48 point lights and 20 spotlights (`LightPool`, render/nightLights.ts; always all in the scene, parked with no range under the ground when unused: changing the number of lights would recompile every material; with the sky and the sun, the scene has only three lights for the materials), where each fragment computes only the lights of its screen tile. Each frame, everything that gives light requests one (`gatherLights`, render/lightSources.ts, without Babylon: see "Night") and current flashes are added (an explosion, `BLAST_LIGHT`, exhaustive over `ExplosionLook`; a gunshot, `MUZZLE_LIGHT`, the small ones only with the pool); the ones most useful to the camera are turned on (`chooseLights`, render/lightChoice.ts: strength × range / distance from the camera to the sphere it lights, a light already on weighs `KEEP` times more: no flickering; nothing beyond `LIGHT_SIGHT`), each keeping its pool light from one frame to the next and appearing in `FADE_IN` s (a flash all at once); a cone's edge is softened (`coneExponent`: its light falls there to 1% of that on its axis). Without dynamic lights, the pool lights only the night's lamps and headlights. Without clustered lights: two `PointLight` in reserve (off at zero intensity); an explosion or a big gunshot takes the weaker one for the duration of a flash; when free, a light illuminates the nearest scenery fire, flickering. These lights cast no shadows (they go through slabs: a lamp on a deck has a short range, so as not to light the street below). **Heat haze** (a post-process, `HAZE_SHADER`): the air shimmers above burning wood, puddles, burning blocks, behind thrusting nozzles (flame or turbojet) and for a few moments above an explosion; the `HEAT_SOURCES` (16) nearest in front of the camera, projected to the screen each frame. Cost measured in Chrome without a GPU (12-robot battle in the Depot, ~3 fps): glow ~15%, light flashes within the noise, haze ~8%, all three ~30%; the effect systems themselves cannot be measured (2.9 fps for the old code, 2.75 to 3.25 after).
- **Engines and flight (`engineFx.ts`)**, all read from the displayed world (thrust, hit points, velocities: online too), without smoke from one's own engines right against the lens when scoped (`OWN_NEAR`):
  - `engineDamage`: an engine below `ENGINE_WORN` of its hit points smokes, gray, then black and thick below 25% with sparks; a wing or control surface below half smokes a little; a hit on an engine or a wing (`blockDamaged`) knocks off fragments and sparks;
  - `jetFx`: a turbojet above the `AFTERBURNER` engine speed (85%: full throttle, sprint; deduced from the engine speed, since others' controls do not go over the network) has a bluish core and shock diamonds in its flame; fast (`CONTRAIL_SPEED`) or high (`CONTRAIL_HEIGHT`), it leaves a contrail (vapor streaks, one every `CONTRAIL_STEP` m);
  - `wingtipVortices`: a plane pulling hard (load factor |ω × v| / g beyond `VORTEX_LOAD`) leaves a vapor streak at each wingtip (the leftmost and rightmost wings of the cockpit's part);
  - `downwash`: under a lifting engine (pointing down) within `DOWNWASH_HEIGHT` m of the ground or the scenery, dust spreads out in a ring, the color of the arena's ground (ArenaView's `groundColor` on the terrain, concrete otherwise); on the Valley's water, spray; under a hover pad, a little dust and small blue sparks, orange sparks if it scrapes the ground;
  - `exhaustPuffs`: a wheeled or tracked robot that accelerates spits dark puffs from the top of its rear;
  - `stunArcs`: a robot that has just been stunned spits a puff at each engine, then zigzagging electric arcs run from one block to a neighbor, on the surface (pushed toward the outside of the robot: from one block center to another, they passed through the hull); a local stun (shock lance): the arcs run only over the cut-off blocks, and from the hub to the tire of the cut-off wheels, and a cut-off engine spits its puff (read from `stunnedUntil`, online too);
  - `fallingWrecks`: a shot-down flying robot (`botKilled`) falls spitting black smoke and fire, part by part, down to the ground (forgotten on `partRemoved`: a freed body is never re-read).
  - `exhaustFx` (exhaustFx.ts): where an engine's flame jet hits a surface (`jetContact`, robot/exhaust.ts: without physics, its own part through its grid, other robots cell by cell in the grid of each of their nearby parts, props, the scenery through `rayArena`, the ground when the bottom of the cone licks it; re-read `CONTACT_RATE` times per second per jet), small flames spread along the surface then rise (three tints), a brief glow each frame, bouncing sparks, a little smoke (more on a block or a prop than on the ground); on the ground or the top of the scenery, a scorch mark (`MarkField.disc`, one every `MARK_GAP` s or as soon as the point moves by `MARK_MOVE` m: they overlap and darken); in water, steam. Nothing from one's own jets within `OWN_NEAR` m of the lens when scoped.
  Elsewhere: a damaged engine's flame hiccups and that of a turbojet in afterburner lengthens (`WorldView.syncFlames`), and every flame stops at whatever its jet hits (`jetStops`, from `readJets`: it no longer goes through a wall, a robot or the ground); fast-spinning blades have a translucent blur disc of their diameter (`BLADE_DIAMETER`, a fixed opacity: per-instance opacity did not work), those of a damaged engine wobble (imbalance, `WOBBLE`), and the glow of hover pads dims and flickers with the batteries (`padGlow`; `LocomotionView`). In a 12-robot battle, these systems cost ~0.2 ms per frame (measured in Chrome without a GPU).

### Night

- **A night arena (`ArenaSky.night`, `MapSky.night` of a community map):** nothing changes for the simulation (detection and the AI see as in daytime); it is lighting. `applyArenaLook` (render/scene.ts) switches to the night lighting set (`NIGHT`: a bluish moon ~33° above the horizon, which keeps its shadows, a faint sky light, a dark ambient light; `DAY`: the previous one) and turns on the night sky (`nightDome`: a dome that follows the camera, without fog, whose shader makes the fog gradient from the horizon to the zenith, the twinkling stars, a pale Milky Way and the moon where its light comes from). `Assets.setNight` (`PropModels.setNight`) lights the glass of the scenery's lamps (an unlit emissive material, which the glow makes shine) and the windows of the facades (an emissive texture covering four patterns by three, `WINDOW_TILES`: about one window in three, warm lamps, bluish screens, a few fires behind blown-out windows); `ArenaView` does the same for the buildings at the edge (`drawTowerWindows`). The map editor stays lit as in broad daylight (you test the map to see it at night).
- **City by Night (`CITY_NIGHT`, arena/city.ts):** the City, its streets, its zones and its props at the same indices, plus floodlight masts (four at the corners of the square facing the monument, two at the end of the station platform, two on the roof of the parking garage) and lampposts (the central avenue, the expressway), never on a spawn line or against a facade; a night-blue sky, slightly thicker fog, no suspended dust (its grains shone like marbles); the City's soundscape (`ambience`). Lamps topple and break: you can plunge a zone into darkness.
- **What gives light (`gatherLights`, render/lightSources.ts):** at night, the scenery's lamps (`PROP_LIGHTS`: the lamppost, a cone pointing down under the head of its arm; the floodlight mast, a cone far ahead of its floodlights, along the axis of its arm; standing and intact: toppled, they go out, and below half their hit points, they flicker) and robots' lights (powered headlights and beacons: `lightPowered`, connected to the cockpit and not stunned). With dynamic lights, day and night: glowing projectiles (`PROJECTILE_LIGHTS`, exhaustive over the projectile look: missiles, rockets, warhead, plasma, laser, railgun, EMP shell, repair beam, nanites, barrier in flight, one rifle bullet in four as a tracer in the team color, one flamethrower ball in three, and above all flares; a laid mine, its light when it blinks), burning blocks, burning wood, puddles, energy walls, engine flames (bigger for a turbojet), the glow of hover pads and glowing energy weapons (`MELEE_LIGHTS`). A source is recognized from one frame to the next by its key (the entity, or a stable text: `fire:<id>`).
- **Light cones (`LightBeams`, render/lightBeams.ts):** at night, the lit air is visible under a lamppost, in front of a mast's floodlights, in front of a headlight (`LightRequest.beam`: the visible length of the cone, 6.5 m, 15 m, 9 m): one open cone per light, as instances of a cone of its color (at most `MAX_BEAMS`, the nearest), placed each frame from the light; its shader (an `FxMaterial`) adds it to what is behind, denser at the core, fainter the farther from the lamp, erased by the fog and right against the camera, a slow haze that undulates; nothing in the glow. With the light pool only.
- **Robots' lights (`BlockTypeDef.light`, `LightSpec`: `kind`, `range`, `cone`, `color`: `LightColor`, `pattern`: `LightPattern`; `Bot.lights`, listed by `registerOrgans`):** blocks with no effect in the simulation, which orient themselves according to the face they are placed on (top, bottom, on a side or the tip of a wing). The headlight (`headlight`) lights in a cone (80°, 34 m) along the top of its block, the way an engine pushes (in the garage, the ghost's yellow arrow); the beacon (`beacon`) glows all around (9 m), in its team's color, pulsing slowly; the navigation light (`navLight`) is steady, red on the robot's left side, green on the right, white in the middle (`color: "side"`, from the block's cell: placed symmetrically, they make the right pair); the strobe light (`strobe`, white, double flash) and the anti-collision light (`antiCollision`, red, one flash per cycle) for planes; the rotating beacon (`rotatingLight`, orange) casts a cone that turns around the top of its block, tilted slightly downward (`kind: "sweep"`, `sweepDirection`), with its cone visible in the air; the police light bar (`policeBar`) has two lights, blue on the left and red on the right, which flash alternately (`wigwag`). The pattern (`lampLevels`, render/lightSources.ts) is computed from world time and the block number: the same on the replica; a flash turns on all at once (`LightRequest.sudden`). Their lit glass is separate (`LIGHT_LENSES`, render/models/lights.ts: one or two per block, disc, bead, dome or box; `Assets.lightLensSource(type, n°, couleur)`, in the color given by `lampColors`), placed on the model by WorldView (`syncLenses`) as long as the light is powered and in time with its pattern (a rotating beacon's mirror turns in its translucent dome); in the garage, lit (`stillBlockParts`). The Truck and the Ram have headlights, the Truck and the Drone a beacon (the Tank and the Buggy have none: a headlight on the Buggy's nose kept it from getting through the trail to the Canyon's arch, and the Tank's changed the duel in the energy wall test enough that the Guardian, hit from more than 30 m away, no longer deployed its wall).
- **Measured cost** (built version, headless Chrome on the machine's graphics card, 1280 × 760 image, 10-robot battle in the City, the camera above the square): by day, 60 fps (the cap); at night, 53 to 55 fps, ~30 lights on; choosing and gathering the lights, ~0.1 ms per frame.

### Sound (`client/audio/`)

- **Recorded sounds:** generated with ElevenLabs (sound effects `eleven_text_to_sound_v2`: several variants per sound, `loop` for a loop; about 3.3 credits per second of sound and per variant). `tools/sounds/catalog.json` keeps, for each sound, its prompt, its settings, `stereo` (ambience) and the variants kept (`keep`, files in `tools/sounds/raw/<son>/`, ignored by git). Tools: `download.mjs` (downloads the variants from the generations' download links, valid for 2 h), `analyze.mjs` (envelope, peak, audible duration, loop seam; flags the near-silent, the too-short, the loop that jumps or dies out), `build.mjs` (`npm run sounds`). Without being able to listen, one also judges by the level per band (lows, mids, highs) every 50 ms: a charge that precedes a hit reads as highs alone, then a jump in the lows; and a whine, by the peaks of the average spectrum (the old wheel engine sound had some, from +20 to +37 dB). The generator readily turns a "charge then hit" sound into a continuous plateau or an overly long charge: a short prompt ("quick rising electric zip, instantly followed by…") worked better than a detailed description. A 5 s loop came out four times out of four with a start and an end 8 to 15 dB louder (a jolt on every pass), the 4 s ones even; so did the 3 s ones of the melee weapons. In a loop prompt, "pulsing", "whoosh", "throbbing" make loops that swell and fall back (swells of 15 to 45 dB), "constant", "steady even level" make even loops; an energy saber almost always comes out as an ignition (it rises from silence), even with "idle": "Sci-fi plasma weapon humming…" worked better (2 out of 8); "deep" is not enough to make a drill sound low ("heavy-duty boring machine… gearbox drone" did it). The estimate for a launch (`estimate_only`) announces ~11 credits per second: what is billed (`credit_costs` of each generation) stays ~3.3. **ElevenLabs queue limit:** about twenty pending generations at most; beyond that, the launch is refused (error 429, nothing is billed): launch the batches one after the other.
- **Preparation (`build.mjs`):** a one-shot sound has no silence at the start or the end, a fade-out, a peak at -1 dB. Loop: resampled over three copies end to end, constant-power crossfade of its end into its start (the generator does not always make a seamless join), average level at -16 dB (two variants of an engine sound equally loud); Opus damages the edges of a file: the loop is encoded with `LOOP_PAD` (0.1 s) of its end before its start and of its start after its end, and the game loops only between the two (`loopStart`, `loopEnd`); after decoding, `mendLoop` re-blends its first 20 ms with the margin after its end (Opus does not decode the same passage identically twice: a low wind clicked on every pass). Mono (Opus 64 kb/s), stereo for ambiences (96 kb/s).
- **`SAMPLES` (`samples.ts`):** key → number of variants, base volume, `loop`; `tests/sounds.test.ts` checks the files and their agreement with the catalog. `SampleBank` loads and decodes everything during the startup loading screen (`Sound.preload`, with its progress) and picks a variant without replaying the last one; a browser that cannot play Opus in Ogg keeps the synthesized sounds. The audio context is created as soon as loading starts (`createContext`), suspended until the player has made a gesture (it decodes anyway; `needsGesture`, `resume`), and at **48 kHz** (`SAMPLE_RATE`, the rate of the Opus files): at the sound card's rate (192 kHz on some machines), the browser decoded everything four times too large (the home screen music weighed 130 MB instead of 33, the JavaScript heap ~750 MB instead of ~350). The home screen music is prepared first (it used to wait behind the ~290 sound effects).
- **Range of a sound (`SampleDef.reach`, `hearing`):** up to `reach` m, it keeps its full volume (5 by default), then it falls off; beyond `hearing` m (90 by default), it is not played: an explosion carries to 220 m (the huge one to 350), the beep of a mine arming to 25. Under an explosion, a synthesized bass layer. The player's shots (fired less than 1.5 m from one of their turrets) are played without spatialization: the camera is about ten meters away, they were heard at half volume. The "Show played sounds" setting (Sound tab, `hud/soundLog.ts`): the name of each sound played and its distance, under the score, to spot the one that bothers you.
- **`Sound` (`sound.ts`):** every sound has its synthesized equivalent as a fallback (`sample` returns false if it is not loaded). One-shot sounds: each weapon's shot (`SHOT_SOUNDS`, an exhaustive `Record`; flamethrower and plasma: a loop that lasts as long as the weapon fires, `sustain`; railgun, `rail-shot`: a high-pitched charge of 0.1 to 0.3 s then a single huge discharge that decays, 1.5 s in all, the bang thus coming a little after the streak), impacts by `impact.surface` (robot, prop, scenery; at most one every 40 ms), explosions by their radius (small, medium, huge), collisions, blocks destroyed, links broken, robot destroyed, a fire igniting, EMP, stun, smoke, shield, crate broken, and the interface (`UI_SAMPLES`). Loops (`LoopVoice`: a source replaced with a fade, its volume, its position): the engine of the nearest robots according to what moves them (`locomotion`: tilt rotor, helicopter; propeller and wings, plane; lift rotors, drone; then legs, pads, tracks, wheels (`wheels-roll`: knobby tires on gravel, transmission and combustion engine underneath; it follows speed, when freewheeling too, and keeps only a little engine when stopped); one variant per robot, volume and pitch according to speed or thrust), flares (ejection, and their burning that hisses in flight), a missile hit in flight, mines (arming as they land, bounce, sticky mine that sticks then beeps until the explosion, a sensor's beep, the detonator's click when the player blows theirs), the nearest projectiles in flight (`FLIGHT_SOUNDS`: booster, whistle of a shell or a bomb, the latter lower and lower as it falls, `FLIGHT_FALL`; Doppler effect from their speed toward the listener), the nearest fires (blocks, wood in the scenery, louder, and puddles; the ignition of wood or a puddle is heard too), the arena ambience (`AMBIENCES`, by arena identifier; an arena without its own stays silent; the Valley's, wind in the pines, river and birds, mostly high-pitched, is played 6 dB lower). Someone else's bullet (`FLYBY_WEAPONS`) passing within 3 m of the camera or of the player's robot whistles past the ear. Also: the gyroscope of a robot righting itself, its footsteps if it walks (`stepSounds`: a foot lands each time the walk phase passes a half-turn, as `LocomotionView` animates it), the mine arming as it lands, a barrel's fuse and the gas of a punctured cylinder (looped, from the props' state), scenery giving way (`BREAK_SOUNDS`: a wall panel or a roof collapsing, sheet metal crushing, wood splintering) and falling (`propReleased`: a tree toppling, a roof caving in), respawn (a single sound for a whole team; `botAdded` is emitted while the robot is being built, before its cockpit: it is heard on the next frame). An error while listening to events is reported once and does not propagate into the simulation (`Sound.listen`). **An event listener (sound, rendering) never rereads the body of what is being removed** (`propRemoved`, `partRemoved`, `wheelRemoved`, `debrisRemoved` are emitted after the body is removed): reading a freed body makes Rapier's WebAssembly panic, after which it stays locked ("recursive use of an object…"); physics is dead until the page is reloaded. For this reason the sound keeps the last position of each prop (`propAt`). Caught in JavaScript, the error is already fatal. Alerts for the player's robot (`updateAlerts`): critical damage, batteries almost empty, and a nearby enemy missile heading straight at it (judging from its trajectory: an enemy's lock-on does not go over the network). Match (`updateMatch`): start siren, countdown of the last ten seconds, hill moving. `ArenaGame.weaponSounds`: overheating of the selected weapon, a round returning to an empty magazine, trigger pulled on an empty magazine. Interface: menu buttons (click, hover, back with Esc), the garage (`Garage.onSound`: place, remove, rotate, wheel, error, unlock; save), end-of-match credits. `UI_GAP` spaces out repeated interface sounds.
- **Melee weapons (`MELEE_SOUNDS`, `meleeHit` and `updateMelee` of `Sound`):** each weapon names its recorded sounds there (a sound from `SAMPLES`, or a borrowed sound played at another pitch and another volume, `MeleeSample`); null or not loaded yet, the synthesized sound from before. Spin loops (`spinner-whine`, `disc-whine`, `drum-whine`, `shell-whine`, `saw-whine`, `drill-whine`, `saber-hum`, `field-hum`, `flail-whirl`): the three nearest rotors, played at 0.5 to 1.2 times their speed and at the square of the spin (or of the charge); a saw or a drill that bites adds its cutting to it (`saw-bite`, `drill-bite`, louder with its power, wavering slightly). Hits (`spinner-hit`, `disc-hit`, `drum-hit`, `shell-hit`, `propeller-hit`, `hammer-hit`, `flail-hit`, `whip-hit`, `lance-hit`): louder with energy (×(0.5 + 0.5·k), k = energy / 1.5 kJ), lower too (from ×1.1 to ×0.88), and ×0.85 on the ground, ×0.6 if it glances; under the hit of a heavy steel mass (bar, disc, drum, ring, hammer, ball) of more than 0.45 kJ, a synthesized thump (`STEEL_THUMP`): the recordings have few lows. A hit whose sound is a loop (the laser blade's cutting, `saber-cut`, every 0.08 s; a jaw's crushing, `jaw-crush`, every 0.25 s) goes through `sustain` and lasts as long as the hits keep coming (`MELEE_HOLD`, 0.35 s). Launches (`hammer-swing`, `flipper-swing`, `jaw-swing`, `whip-swing`, `lance-swing`): when the arm, the plate, the jaws or the tip set off. Borrowed: the flipper's plate and the jaws when they grab, `collision`; the field when touched, `shield-hit` lower; the cutting propeller whines with its engine (`propeller-big`). The flail's chain (highs only) swells twice per turn as the ball passes, with the synthesized low rush underneath (`FLAIL_UNDER`). Generated on October 7, 2026 (8 batches, 141 generations, ~1,060 credits) and chosen from their analysis (evenness of the loops, attack of the hits, level per band): nobody has listened to them yet.
- **What sounds on which screen (`soundScene.ts`):** a single place decides. `App` goes through `enter` at every screen change (match, pause, end of match, menus in front of the demo, garage, connection) and announces it to the sound (`Sound.setScreen`, with `online`); `soundScene` then gives the volume of two buses, the world (shots, explosions, engines, fires, projectiles, props, the player's shots: everything that goes through `panner` and the world's `LoopVoice`s) and the arena ambience, whether the world is there (`live`) and whether the player's combat cues get through (`cues`). Interface sounds (`ui`) and music go straight to the master volume. In a match, everything; in pause, the frozen world falls silent (bus at 0, the ambience stays, lower; online, the match goes on on the server: it is still heard, from afar); at the end of a match and behind the menus, the battle goes on, quieter, and the victory or defeat sting lowers the world further for a few seconds (`STINGER_DUCK`); while a match is loading (`loading` screen), nothing from the world either (it is frozen behind the loading screen): only the music, and the start siren waits for the game screen (`updateMatch` only takes a new match into account when the combat cues get through); in the garage (the arena on standby, `update` is no longer called), nothing from the world: `releaseWorld` frees all loops (engines, projectiles in flight, fires, props, continuous fire, ambience), which restart on their own when you return to the arena. This was the cause of the engines still heard in the garage after trying out your robot: suspended, the arena no longer called `update`, and its loops stayed frozen at their last volume. Outside a match, combat cues (`COMBAT_CUES`: hit, damage, alerts, countdown, siren, zones, lock-on, respawn…) do not play; those of the menus and the garage always do. Changing world (`setWorld`, network) also frees all loops and forgets the old world's projectiles, mines and sticky mines (their removals will never arrive there: a sticky mine beeped forever). `Sound.debugState()` (console: `__casse.game.sound.debugState()`) gives the screen, the bus volumes, the one-shot voices and the loops playing; `tests/soundScene.test.ts` checks the screen table.
- **Music (`music.ts`):** generated with ElevenLabs (`eleven_music_v2_5`, instrumental; the estimate announces ~27.5 credits per second, the amount billed is ~15). Each screen has several tracks (`THEMES`: home 3, garage 3, match 12, from 51 s to 3 min 13; `Sound.playMusic`: home, garage and robot trial, match), played one after the other from a shuffled bag (`ShuffleBag`: all of them play before one comes back, never the same one twice in a row), a 3 s constant-power crossfade (`CHAIN_FADE`) moving from one to the next near the end of the first (`chainMove`, driven by `timeupdate`); at the end of a match, a victory or defeat sting (`Sound.stinger`, three of each, also drawn from a bag). **Streaming playback:** decoded, a track would weigh ~0.4 MB per second (~75 MB for 3 min, double with the next one); each one is therefore played by an `<audio>` element (`preload` "auto", on a `blob:` URL of the compressed file, downloaded when the track is prepared: the game server does not serve range requests) connected to the bus by `createMediaElementSource`, the fade on a `GainNode`. Kept in memory, compressed (112 kb/s, ~2.5 MB for 3 min): the current track and the next one for its screen, plus the first one of each of the other screens (ready: `canplaythrough` reached), five during a fade: ~15 MB at most (7 MB measured); a finished track is released (element emptied, node disconnected, URL revoked). The stings, which must start instantly, stay decoded (~3 MB each, 17 MB in all). `__casse.game.sound.musicMegabytes()` gives both (`decoded`, `compressed`), `musicState()` what is playing and what is ready, `skipMusic()` skips to the next track (for testing). Measured in headless Chrome, after a garbage collection: 140 MB of buffers (`ArrayBuffer`, sounds included) versus 228 with the old player, which kept one track per screen decoded (90 MB of music). They must never arrive "after a moment": the stings and the first home track are ready during the loading screen, those of the match and the garage right after, in the background; a match's loading screen waits until its first track can start (`Sound.prepareMusic`, 15 s at most). With the audio context still suspended (no gesture), a track waits for it to resume before starting; a playback refused for lack of a gesture moves on to the next one. If the next one is not ready in time: the track restarts from its beginning (its end leads there, see below) and the chaining happens on the next pass; unplayable: we move on to the next one in the bag. Low-memory machine (`navigator.deviceMemory` ≤ 4): the garage is not prepared in advance. A screen change (`request`) cuts the chaining in progress; from one screen to another, a 1.5 s fade. Prepared like the loops (intro and outro removed, margins, end faded into the start over 3 s), at 112 kb/s: a track is played from its start margin and chained before its end margin. Generated on September 30, 2026 (the first two combat tracks, the home track, the garage track, four stings) and on October 14, 2026 (five 3 min combat tracks: orchestral hybrid, drum and bass, synthwave, industrial metal, bass music; a home track, a garage track, two stings; 16 generations, 32,573 credits billed against 59,730 estimated; chosen from their analysis, nobody has listened to them yet). The "Music" setting (Sound tab, `Settings.music`), on top of the master volume.

### Combat AI (`ai/tactics.ts`)

- `planCombat` (every 0.4 s, ground and flying robots, not planes) chooses an opponent (`TacticsState.foe`: the one its turrets are aiming at, otherwise the one it was fighting, otherwise the nearest spotted enemy; an opponent hidden behind a pillar stays its opponent for `FOE_MEMORY` s) and a mode:
  - `engage`: it circles the opponent at its **preferred range** (`preferredRange`: the average of the `Weapon.engage` of its weapons that reach, without exceeding the range of the shortest one). The destination is a point `LEAD` m ahead of it, in a direction that blends the tangent to the circle with an approach or a retreat according to the gap from the range: the paths converge onto the circle without a U-turn. The direction (`orbit`) is chosen from its heading; it only reverses when backed into a corner;
  - `cover`: behind the nearest pillar, on the side opposite the opponent (`coverSpot`), when its magazine weapons are all empty or its repair modules have work to do (`repairWork`); it comes out with magazines half full, repairs almost done, or after `MAX_COVER` s. A flying robot also lands there to recharge its batteries;
  - `charge`: a robot built to charge (`behavior`) and armed for melee rams its opponent; a spinner robot only goes in at full spin, and circles it at 7 m while waiting; a drill aims at its cockpit, a saw that bites runs along it (see "Melee weapons");
  - `support`: a robot carrying a repair beam goes to heal the most damaged ally (at least `SUPPORT_NEED` points lost, within `SUPPORT_SEARCH` m; not a plane): it circles it at `SUPPORT_DISTANCE` m (its beam only reaches one side at a time), before anything else except a breather in cover; when hit, it does not flee;
  - `patrol` without an opponent.
- **Zone capture:** `objectiveZone` chooses the zone to take (the nearest among those its team does not hold, each teammate heading there pushing it `CROWD_COST` m further away so that the team spreads out); as long as it remains to be taken, it comes before the pursuit (its turrets fire anyway) and its patrol takes it to a point in the zone (`TacticsState.holding`).
- Hit in the middle of combat, or on its way to a zone, it does not flee (`onHit`); otherwise, it flees or charges as before.
- **Nav graph (`NavGraph`, arena/navGraph.ts; `routeGoal`, ai/navigation.ts):** in an arena whose terrain cuts off routes (the Canyon), points (x, z) linked when the line joining them is passable (`walkable`: nowhere steeper than `MAX_GRADE`, ~32°, sampled every meter; with a side margin, the two lines running alongside it too, and no cross slope beyond `MAX_CROSS`: it does not run along an embankment), plus links declared across gaps (a bridge, an arch); `linkNav` computes them once. When the straight line to its destination is not passable, the ground robot follows the shortest path in the graph (Dijkstra: starts, the points it sees in a straight line; ends, those that see the destination, or failing that the closest to it), recomputed when the destination moves by `REPLAN_SHIFT` m or every `REPLAN_EVERY` s, and cuts to the next point as soon as it sees it (`SKIP_EVERY`, with a margin according to its size, `sideMargin`). On a bridge, or to get onto one, `bridgeGoal` stays in charge. In such an arena only: only obstacles at its height count (`atLevel`: not the roof of a tunnel above it, nor a rock at the foot of the cliff it runs along; likewise for taking cover), the edge of a cliff or a slope too steep ahead of it counts as an obstacle for local avoidance (`edgeAhead`, on `surfaceHeight`: the terrain, or the deck of a bridge at its height; rays do not see the void), and a random destination is a place the graph reaches (`onNav`: not the top of a butte). The other arenas don't have one: nothing changes there.
- **Getting around scenery (`ai/navigation.ts`):** local avoidance (three rays) cannot get around a low wall or find a ramp. `navigate` looks at the straight-line route: if it crosses an obstacle (`obstacles`: pillar, low wall, platform, rock, container, and standing anchored props: the footprint of each building as a whole, each tree or storage tank; recomputed every step, since walls fall), the ground robot first aims at the most convenient corner of that obstacle; an obstacle lower than it (the piers of the bridge it is crossing) does not count. A destination on a platform goes via the foot of the most convenient ramp; a bridge is entered and left by one of its ends (`bridgeGoal`), never from underneath. Cover (`coverSpot`) is taken behind the same obstacles, trees excepted. The computation is done in the plane, on the ground footprint of the boxes (rotated or not). The footprint of an anchored prop is computed once (`footingOf`); a prop thinner than `SLENDER` (a lamppost) is not walked around; nothing beyond the edge of the arena (`BEYOND`) counts. **Generic, with no effect elsewhere (battles in the Depot and the Valley stay identical):** an elevated roadway (`StaticBox.underpass`) is passed underneath, and only makes the robot climb for a destination at its height (zone destinations carry their height), via the approach to its end (`approach`: the foot of its embankment), up onto the deck; a high ramp (more than `TALL_RAMP` m) forms a single obstacle with its platform, it is taken from further away and climbed staying in the middle (`alongRamp`), and the robot follows it down to its bottom rather than butting against its side (`besideRamp`). **In a city (`ArenaLayout.urban`):** a destination in a building or an obstacle, or too close to it, is brought back into the street (`clearOf`), and the AI does not draw its random destinations inside a building (`wander`, `insideObstacle`); a robot that has entered a building leaves it through an opening in its walls (`buildingExit`); a robot running along a wall goes around it if its body (`BODY` of its radius) was going to scrape it, and first moves away from it if it is too close; it does not aim at the corner where it already is, counts the next corner when the obstacle still hides its destination, and keeps the corner it was aiming at (`CORNER_KEEP`). Several blocks edge to edge (a barricade) share a `building` number: a single obstacle. Measured in the City: 3 to 7% of the time blocked in battle (`blockedT` over 1.5 s, ground robots), as in the Depot (7 to 14%) and the Valley (5 to 8%); of 40 trips from a spawn line to a zone (8 robots × 5 zones), 38 succeed.

### Player and matches

- **Piloted yaw (A and E, `PlayerInput.yaw`, `Controls.rudder`):** for any piloted flying robot or plane, independent of roll, smooth like the stick (`STICK_RATE`); remote mines have their own key there (G by default: the `detonateAir` action, which only applies in flight, `ArenaGame.flying`). Flying robot: it pivots on the spot, level, without changing its movement (`HOVER_YAW_RATE`, sim/player.ts; `flyToward(…, yaw)`, see "Hover"). With camera steering (the "Steering" setting, the default), without yaw, it turns toward where the camera is looking; held yaw takes precedence. Plane with the mouse: flat turn, wings level (`flyMouse`: desired yaw rate `FLAT_TURN_RATE`, stiffer fin `FLAT_TURN_GAIN`; the instructor judges by the flight path, which turns with the nose, and does not counter it); manual plane: the rudder (altitude remains the pilot's business). In both, the flat-turn assist (`slipAssist`, ai/pilot.ts) turns the horizontal velocity toward the nose without slowing it (`SLIP_GRIP`, `SLIP_MAX`), as long as the key is held and for `SLIP_FADE` s afterward (`AiState.slip`): without it, the fin brought the nose back into the wind, the plane slid sideways and barely turned (0.4 rad in 6 s in manual); by removing the sideways velocity without carrying it forward, it slowed down and sank. Measured (`tests/flatTurn.test.ts`): the Plane, the Bomber and the Fighter with the mouse turn ~95 to 125° in 4 s, wings within 10°, sideslip under 10° (the Plane in manual: 105°, sideslip 12°); drone, helicopter, hexacopter do a U-turn in 2.5 s, within 7° of attitude, without moving from the spot, and stop turning one second after release. The AI goes through none of this.
- **Piloted robot (`sim/player.ts`):** `Bot.controller === "player"` (`takeControl`, `releaseControl`); `thinkBot` applies `Bot.input` to it (locally, `sim.input`) (`PlayerInput`: forward, turn, climb, boost, brake, aim point, trigger, weapon, camera heading, look direction `look`, yaw, throttle `power`, manual piloting). **Robocraft-style controls** (default keys; ZQSD are the WASD keys of a QWERTY, designated by their position): the camera steers, and the throttle is separate from steering. On the ground, it drives like the AI (`drive`); with camera steering (`relative`, the default), ZQSD give a direction on screen (see "Camera-relative steering"). A flying robot moves relative to the camera, climbs and descends as long as Space or C is held (the target altitude runs no more than `CLIMB_LEAD` m ahead of it: released, it stops where it is) and, with camera steering, turns toward where the camera is looking (`FACE_GAIN`, the cockpit's gyroscope helping it as long as it is far from it, `FACE_ASSIST`); A and E make it pivot (see "Piloted yaw"). In a plane, with the mouse (the default, `flyMouse`, ai/pilot.ts; see "Plane pilot"), it goes where the player is looking (`PlayerInput.look`, the direction of the crosshair ray): an instructor banks and pulls; looking up and keeping going makes it loop, go inverted and come back; on the keyboard (`look` null), `steer` turns (Q and D), `climb` pulls up (Space; held, a loop) or pushes down (C), `yaw` is the rudder (A and E); in manual piloting (`PlayerInput.manual`, `flyManual`), the player holds the stick (`climb`: > 0 pull up, `steer`: > 0 roll left, `yaw`: rudder); in both, the throttle (`power`, 0 to 1; 0: engine off; `CRUISE_POWER`, 0.4, at the start: its cruising speed) only changes its speed, on forward and back (Z and S). While its warhead is in flight, it flies straight and level (`holdPlane`). The old assisted piloting (choosing bank and altitude) is gone: the mouse does the same thing better, and manual remains for aerobatics. On the client side (`ArenaGame.steerPlane`): the "In a plane" setting (`Settings.flight`: `mouse` or `manual`; an old `assisted` becomes `mouse`), V toggles it in flight (`ArenaGame.toggleFlight`, saved by `onFlightChange`; a kill feed line gives the keys of the chosen piloting); forward and back raise and lower the throttle (`POWER_RATE` per second), boost (Shift) puts it to full while held, X cuts it (`cutEngine`); the stick follows the keys smoothly (`STICK_RATE`); with the mouse, while turning or pulling up on the keyboard and for `KEY_STEER_HOLD` s afterward, `look` stays null and the camera follows the nose (`CameraRig.chaseDirection`, `KEY_CHASE_RATE`): once released, the plane heads back toward the crosshair, which is ahead of it; in manual, with the mouse still for `CHASE_DELAY` s, the camera moves back behind the nose (`CHASE_RATE`); a plane that spawns starts at `CRUISE_POWER`, the view behind its nose, level (`snapView`: the starting camera looked at the robot from above, and it dived into the ground); while it flies, the camera has no pitch limit (see "Mouse look"); a marker shows where its nose is going (see "HUD"); the flight panel gives the mode ("Mouse", "Manual"), the throttle (the player's), the height above the ground and the bank all the way round; throttle cut, the propeller stops (`PROPELLER_STOP`) and the engine falls silent (`ENGINE_OFF`); the turrets of the selected weapon turn at their own speed toward the aim point and, trigger pressed, fire from their muzzle along the axis their barrel actually points, without waiting to be aligned (the AI, for its part, waits until it is on target); on the client side, one mark per turret of the selected weapon shows where its barrel's axis lands (`ArenaGame.showGunMarks`: first obstacle, or its range; not for a lobbed shot, mines, bombs, the warhead), offset from the crosshair while the turret is turning or at its stop; the others return to rest, barrel straight ahead (`restTurret`, combat/turrets.ts). `sim.player` is its robot (replaced at each respawn). On the client side, a weapon that is no longer available (all its turrets destroyed, or the warhead fired) is struck through in the weapons panel ("out of action", "empty"); if it was the selected weapon, `ArenaGame.switchFromLost` moves to the next available one (after the flight of the warhead being piloted) and says so in the feed. An empty magazine or overheating don't count: they pass.
- **Boost and brake (`PlayerInput.boost`, `brake`; `DriveOptions`, robot/propulsion.ts):** on the ground, boost (Shift) puts the boosters at full (`runEngines`) and makes the wheel and support motors sprint (`SPRINT`: desired speed and allowed voltage ×1.3, an overvoltage that draws `SPRINT_POWER` kW from the batteries; when they are empty, it falls back to what the generator gives), without ever holding the robot back: the wheels freewheel on a ratchet (`Wheel.overrun`: the motor only pushes in the commanded direction; faster than its target, or without throttle, the wheel turns freely) and the supports only push forward in the direction of the throttle. Before, Shift braked: the wheels were disengaged (no more motor, only `FREEWHEEL_DRAG`: a robot without boosters slowed down, a robot with boosters lost its wheels' traction while the booster spun up, 0.5 to 1.4 s) and the supports aimed to stop (throttle and steering at zero: pads and legs braked hard). The brake (Space on the ground, `brake` from 0 to 1, bounded by the server) takes precedence over throttle, boost and sprint: the wheel motors are disengaged (their voltage still follows the command: released, the robot sets off again without waiting) and every wheel, tracks included, brakes (`Wheel.brake`, robot/wheels.ts: an implicit force that would stop the contact point in one step, capped at `BRAKE_GRIP` of what the tire carries: no lock-up, the wheel still holds sideways; it holds the robot at rest), as hard as the robot's stability allows (`PITCH_MARGIN` of `pitchoverAccel`, robot/steering.ts: the deceleration that would flip it over its front wheels; only the Stilt and the Crane are limited by it); pads and legs aim to stop, faster (`BRAKE_GAIN`), a pad gripping harder (`BRAKE_HOVER_TRACTION`); a flying robot stops on the spot (with the default keys, the brake only applies on the ground: in the air, Space makes it climb); in a plane, nothing (no airbrake: S reduces the throttle, X cuts it). Measured (`tests/brake.test.ts`, from cruising speed): stop in 0.8 s (Trike), 0.3 s (Tank, Spider), 0.9 s (Hovercraft), 1.5 s (Stilt), versus 1.1, 0.8, 0.6, 1.8 and 1.8 s with the throttle released, without the robot tipping. The AI does not brake; its boost (fleeing or charging, with a booster) goes through the same ratchet freewheel, without the sprint.
- **Matches (`sim/match.ts`):** `startMatch(sim, rules)` (Battle is played to 15 kills); each `botKilled` gives a point to the opponent; respawn on its team's side (`respawnBot`) after `respawn` s, or never (elimination); an AI robot immobilized too long (overturned without being able to right itself, without wheels, falling) self-destructs; end on score, on time, or when a team has nobody left (`matchOver`). **Zone Capture** (`MatchRules.capture`): kills no longer count; a team alone in a zone flips it (`ZoneState.progress` from -1, red, to 1, blue: first neutralized, then taken, √n times faster with n robots), both teams at once contest it; each zone held brings `rate` points per second (the score has fractions, displayed rounded); `zoneChanged` at each change of hands. **King of the Hill** (`CaptureRules.hill`): only one zone is in play (`ZoneState.active`), the center one first; every `hill` s (`Match.nextHill`), it moves to another, drawn at random, and the old one returns to neutral. Zones out of play cannot be taken, the AI only targets the hill (`objectiveZone`), the snapshot carries the state (one bit), the client hides zones out of play and grays out their badge, and the feed announces the move.
- **Righting (`robot/righting.ts`):** the cockpit's gyroscope sets an overturned robot that has been immobile for `RIGHTING_DELAY` s back upright (a small hop then a rotation toward vertical, by directly setting the velocities of the cockpit's part), for the AI as for the player; the same hop frees an AI robot stuck despite its maneuvers (`unstick`, after `UNSTICK_DELAY`). Not for planes.
- **Teams (`sim/wave.ts`):** `spawnWave` (teams alternating around the circle; inner circles when it is full, then a circle near the walls as a last resort: without it, a very large wave placed its last robots straddling their neighbors) or `spawnTeams` (two lines facing each other `SPAWN_LINE` m from the center, blue to the south and red to the north, about sixty meters apart: out of rifle range). `matchEntries` (modes.ts) composes the teams of a piloted match: the player at the head of the blue team, then the robots drawn at random, distributed from most to least expensive into the team that costs the least so far (the player's robot included): the two teams have a similar cost (`teamCost`), and a player who takes a small robot gets heavier teammates. The server fills its teams the same way. This was the real cause of unbalanced matches: replayed with sides swapped, the same compositions won in the north as in the south, in all three arenas.
- **Budget (`design/budget.ts`):** every block and every wheel has a cost (`cost`); `validateDesign` refuses a design over `ROBOT_BUDGET`.
- **Progression (`design/progression.ts`, `client/progress.ts`):** every type of block and wheel has an unlock price (`BLOCK_PRICES`, `WHEEL_PRICES`: exhaustive `Record`s, a new type must have its own; 0 = available from the start; a steered wheel costs more than the fixed one of its size). Parts unlocked in a previous version go through `upgradeUnlocked` (client/progress.ts, server/progressBook.ts): whoever had the heavy wheel also has its steered version. A piloted match earns credits (`matchReward`: match played, victory or draw, the player's kills, zones taken by their team, counted by `ArenaGame.matchStats`), displayed at the end of the match. The player keeps their credits and parts in the browser (`Progress`, key `casse-robot.progress`); in the garage, a locked part shows its price and is unlocked with a click; a robot that contains some can be tried out, but not played in a match (`lockedParts`). The "Every part" setting (sandbox).
- **Garage:** `client/garage/garage.ts` edits a `RobotDesign` (place, remove, orientation, mirror), saves it (`storage.ts`) and has it tried out (`trial` mode); **inventory** (right panel, `client/garage/inventory.ts`): parts by category (`partCategory`, tabs with their count, plus "All" and "Recent", kept in the browser, `casse-robot.garage.recent`), sorted by group (`partGroup`: direct-fire, explosive, guided, support weapons, mines, dropped; shapes; fixed, steered wheels, casters), an accent-insensitive search on the name, the category and the info sheet (`matchesSearch`, "/" goes there, the key of `garageSearch` named by the field: "!" on an AZERTY keyboard; Enter takes the first one), 3D thumbnails (`PartThumbnails`, render/partThumbnails.ts: a small off-page Babylon engine renders each part once, a few per frame, then keeps the image; released when the garage closes) and the info sheet of the chosen part (`partInfo`, client/garage/partInfo.ts, derived from the catalogs: what it is for, cost, mass, structure, resistances, and what is specific to it: damage, range, rate of fire, thrust, charge…; its rotating 3D preview, a single-part `RobotPreview`; the button to unlock it); 1 to 9 recall the recent parts, the middle click copies the part pointed at (`eyedrop`: it becomes the tool, and a copied block keeps its exact orientation, `copied`, which takes precedence over face orientation until the next part choice; O returns to it). **Robot direction:** on the ground, a "FRONT" arrow in front of it, "BACK", "LEFT" and "RIGHT" around it and the axis of symmetry dotted (`createMarks`, placed by `placeMarks` according to its clearance; drawn mirrored: the ground receives its texture flipped); an on-screen compass that follows the camera (`updateCompass`: the robot's axes projected onto the screen); **orientation:** a block that lends itself to it (`orientsToFace`: non-fixed turret, shape, flare launcher, radar, jammer; not engines, which push toward their top, nor wings, supports, fixed turrets) takes as its top the face it is placed on (`target` returns the face pointed at, the dominant axis of the normal: on a 45° slope, the top): under a block, a turret hangs, on a side it sticks out sideways, barrel at rest toward the front (`faceForward`), a shape has its solid underside stuck to its support; R rotates it a quarter turn around its top (`spin`), Shift + R tilts it (the top moves to the next axis, orientation becomes manual), O turns face orientation off or back on; a preview (`ghost`, `buildGhost`) shows the block as it will be placed: its shape, a turret's head, a yellow arrow for an engine (the direction of its thrust) or a flare launcher; a block's mirror counterpart is its mirror image (`mirrorFacing`, design/robotDesign.ts); `design/custom.ts` turns it into a playable profile (mobility and speed derived from the organs). Every change to the design goes through `edit()`, which makes it undoable (Ctrl+Z, Ctrl+Y). **Shortcuts:** all those of the garage (place, remove, copy the part pointed at, zone, rotate, tilt, face orientation, mirror (M), layer view, layer above and below, copy, paste, undo, redo, clear, search, recent parts; the keys quoted here are the defaults) are actions of the key table ("Garage" section, `garage` context: see "Keys and gamepad"), rebound like the others: `Garage.actionFor` finds the action of a key press or a click (`eventChords`, `chordCode`: the combination first, then the key alone), `run` performs it; its help texts (panel, help bar, notes, search) name the chosen keys (`Garage.keyName`, which the `App` connects to `Controls.keyName`), redone by `refreshKeys` when the keys or the language change (without redoing a panel with a focused field). Layer view (L, Page↑/↓): the grid rises to the working layer, the layers above are hidden, those below darkened; Ctrl+C / Ctrl+V copy one layer onto another. Zone: Shift + click on two blocks delimits a box (over several layers, yellow outline); Ctrl+C copies it relative to its corner, Ctrl+V pastes it into the cell under the pointer (free cells, without a second cockpit), Delete clears it. The palette sorts wheels by kind (fixed, steered, casters, tracks). A wheel is placed on the face pointed at (side or underside), offset by half a cell toward the edge pointed at (`WheelMount.shift`); a track roller can also be placed on another one (`stackOn`: on its top or underside, the track goes up or down a cell; on its outer face, it widens); a ghost shows where it will go. The fittings (`wheelFittings`, render/fittings.ts: fork of a caster or of a wheel placed underneath, bracket of a caster on a side) and the track belts are drawn as in the game. Outside layer view, the grid floor lowers beneath whatever hangs from the robot. A red ball (seen through the blocks) and a plumb line show the center of mass (`designCenterOfMass`), repeated in the panel. **Clearance (`design/clearance.ts`):** what each part occupies beyond its cell, in simple volumes in the robot's frame (`Solid`: box, cylinder along x, y or z, capsule; `Zone`: the part it belongs to, what it is (`ZonePart`, named in each language: `zonePart.<id>`), the cells it is allowed to encroach on), from the catalogs: a turret's head (`TurretSpec.head` around `headLift`, the height at which it is drawn) and its barrel at rest (a capsule from the head's axis to its muzzle, `barrel`, of caliber `caliber`, straight ahead, horizontal; its orientation `facing` followed), a mine layer's exit (the cell behind), the bombs' path under a bay (the cell below), a wheel (its disc, widened by what it sweeps when steering: `steerClearance`), a track's belt (a box around each group of rollers, `trackGroups`), blades (`BLADES`: tilt rotor, propeller, tail rotor of an engine laid on its side, chosen by `bladeKind` as in the game), a turbojet's nacelle (`JET_NACELLE`), a leg at rest (`restLeg`, outward from the center of mass). A turret only reserves its rest pose, not the circle its barrel sweeps: a block next to its head only limits its field of fire (`lineOfFireBlocked`), and reserving the circle would forbid almost any compact robot; a wheel does not reserve its suspension travel either. A full cell counts whole (the grid remains the truth), except a plate (wing, control surface: a slab, thickened by what a control surface sweeps, `plateBody`): a wheel passes under a wing. A part may encroach by `CLEARANCE_SLACK` (4 cm) on a neighboring cell; two zones get in each other's way if a point is 4 cm inside each (less for a thin volume, like a blade disc); two wheels, by the rule of `validateDesign` (`wheelsOverlap`). `placementConflicts(plan, pièce)` says, in both directions, what a placement would obstruct (a block in a part's zone, or a part whose zone would enter a block or another zone), with the reason (`ConflictReason`, a code the client states in one line, `conflictText`: "In the way of the barrel (Machine gun turret)", "The wheel would hit the propeller (Propeller)") and what is in the way on the other one (`Conflict.solids`); `designConflicts` all those of a design (one line each: `conflictLine`). `validateDesign` ignores them: a design from before stays playable (the panel flags "Parts in each other's way"). No preset robot has parts in each other's way (`tests/clearance.test.ts` checks it for all of them): the Dragster, the last one, had the air intakes of its four turbojets 18 cm into the chassis in front of them; they are now one cell further away (see "Propellers and turbojets"). In the garage, the preview of the part to place (block or wheel) is green if it fits, red otherwise (occupied cell included), with its clearance shown transparently over the blocks and what it would obstruct in red (`ClearanceView`, garage/clearanceView.ts), and the reason under the chosen part (`.g-clash`); a click on an impossible placement places nothing, plays the error sound and states the reason (`refuse`). In mirror mode, the mirror counterpart is checked after the part (if it gets in the way, the part is placed alone and this is stated; an already occupied mirror cell remains silently ignored); pasting a zone or a layer only pastes what fits, part by part, and says how many were left out (`pastePieces`). What the game draws in addition to a block or a wheel (turret heads and munitions, blades, nacelles, legs, pad glow, forks, brackets and steering arms) is also drawn, still, in the garage, in the robot picker's preview, a part's info sheet and the inventory thumbnails (`stillBlockParts`, `stillWheelParts`, render/stillParts.ts), with the same sources and the same dimensions as in the game; the grid floor lowers beneath the feet of a legged robot. `design/flight.ts` estimates a design's lift, thrust and flight endurance (the same one that `liftToWeight` measures in the game).

### Vehicles

- **AI driving (`ai/brain.ts`):** three rays in front of the robot (range depending on its speed) make it slow down and steer around scenery, props and robots (except the enemy it is charging). With steered wheels, it never takes a turn tighter than its stability allows (`rolloverAccel`), builds up momentum to turn around and backs up while counter-steering when it is stuck. Its boosters, if any, fire at full power when fleeing or charging, well aligned, or when an enemy is in their jet (`foeInJet`), never if they would burn its own robot (`scorchesItself`).
- **Driving, all organs (`drive` in robot/propulsion.ts):** wheels and tracks (`driveWheels`), and supports (`driveSupports`), with the same commands on top of throttle and steering (`DriveOptions`: boost, sprint, brake; see "Boost and brake").
- **Wheelless supports (`robot/supports.ts`):** a hover pad or a leg (`SupportSpec`) measures the ground beneath it and pushes like a spring-damper tuned for its rated load; it also pushes horizontally toward the command, within the limit of its grip (pad: slides, consumes energy; leg: grips). The renderer animates the legs (inverse kinematics, alternating gait).
- **Propellers and turbojets (`ThrusterSpec.look`, `topSpeed`):** each engine has its look (`look`: flame by default, `rotor`, `propeller`, `jet`), which decides how it is drawn and how it sounds (no longer `gimbal`). The **propeller** (block `propeller`): a three-blade disc nearly 2 m across in front of its block (`Assets.propellerSource`, `LocomotionView.syncBlades`: spin of `PROPELLER_RPM`, painted tips, anti-strobe); its thrust drops with the airspeed along its axis (`propellerFactor`: all of it at a standstill, none at `topSpeed` = 45 m/s; `t.thrust` remains the engine's spin, which the blades show). The **turbojet** (block `jet`): 700 N (five boosters), slow to spool up (1.4 s), 0.6 kW (two run on the generator, beyond that batteries are needed), a nacelle that sticks out of its block (`WorldView.nacelles`, `jetNacelleSource`) and a flickering afterburner flame more than 2 m long (`jetFlameSource`, from the nozzle `JET_NOZZLE`). Both can be placed in any direction, like the other engines: facing forward they propel (on the ground, when sprinting: Shift), facing up they lift (vertical takeoff; a turbojet, being slow, lifts poorly when hovering), sideways they turn. Sounds: `jet-engine` (in flight, or on the ground when they push), `propeller-big`. A garage plane flies faster the harder it pushes (`cruiseSpeed`, design/custom.ts: `PLANE_SPEED`, from 11 to 20 m/s; it used to aim for 5 m/s). Robots: the Plane has a propeller on its nose, the Bomber one on each wing, the Fighter two turbojets under its wings (18 m/s), the Dragster four at the back of a wheeled chassis (when sprinting, it goes much faster than its wheels can; one cell behind the chassis, held by a spine in the middle, on two levels, so that the cell in front of each stays free: the nacelle's air intake sticks out there 0.43 m from the block's center, `JET_NACELLE`; a second row of heavy armor at the bow counterbalances the 24 kg of the moved-back engines: the front carries 40% of the weight at rest (39% before, 34% without it), its front wheels no longer leave the ground when setting off at a sprint, it steers as before; 109 kg instead of 100, hence a sprint 7% less lively, 24.7 m/s after 2 s instead of 26.5: `tests/engines.test.ts`). Thrusters, boosters and turbojets spit a flame jet that burns whatever is behind their nozzle (see "Engine flame jets").
- **Tail rotors:** a thruster laid on its side (`Thruster.role === "trim"`) is drawn with a two-blade propeller, without a flame (`LocomotionView.syncBlades`, like the tilt rotor's blades). The blades turn like a real rotor: at a nearly constant spin as long as the engine is powered (connected to the cockpit, robot not stunned), a little faster at full thrust, with inertia (`ROTOR_RPM`, `TAIL_RPM`, `SPOOL_UP`, `SPOOL_DOWN`); the rotation shown per frame is capped (`STROBE_LIMIT`) so that the eye does not see them stop or turn backward.
- **Tracks:** rollers (`WheelTypeDef.track`) on a side, inside a belt drawn by `LocomotionView` (and by the garage): neighboring rollers on the same side (less than two cells apart along the side, one cell apart in height, or one on top of the other outward; `trackGroups`, shared/design/tracks.ts: clearance uses it too) form a single track, whose belt follows the convex hull of their centers (`beltShape`, `beltPath`: straight lines from one roller to the next, arcs around the corner ones, at the roller's radius plus `BELT_CLEARANCE`: the tip of the grousers, which bites 1 cm into the ground). **Rendering (render/models/tracks.ts, render/belts.ts):** all around, raised shoes (`trackShoe`: plate, grouser, hinge, steel connectors, one guide per row of rollers, which passes between its twin wheels), one thin instance per shoe every `SHOE_PITCH` (12 cm; `BeltShoes`, placed by `placeShoes`, render/trackShape.ts, from the normal of the path: they pivot in the arcs like links); under them, a thin belt (`beltMesh`), seen between the shoes and from the inside; the rollers are banded twin wheels (`TRACK_MODELS`) and the rear roller of each run (the highest one if they are stacked: `sprocketRollers`) carries a toothed sprocket (`sprocket`, which follows its pose). The belt (its texture) and the shoes scroll by however much the rollers have turned around their axle, read from their pose (the bottom moves back, the top moves forward): online too, since the replica does not have the wheels' rotation speed. Per frame, only the shoes' matrices are rewritten (one buffer per track, no mesh rebuilt). The shoes and the sprocket cast no shadow (the belt's has the same silhouette). **Levels of detail:** beyond `ROLLER_DETAIL_RANGE` (20 m) from the camera, the rollers switch to a simple model (band, flange, hub: `addLODLevel`, which Babylon also applies to instances and shadow maps); beyond `TRACK_DETAIL_RANGE` (35 m; `LocomotionView.shoeRange`, adjustable from the console), the track no longer has shoes or a sprocket, but the old thick belt (`beltMesh(…, false)`), and nothing to place. A Tank: 2 × 80 shoes of 144 vertices, a roller of 1,250 vertices (~150 from afar), a sprocket of 1,590. Measured in Chrome without a GPU: an ordinary battle (12 robots including the Tank and the Bastion) runs as before (3.2 vs. 3.3 fps following the Tank, 4.3 vs. 4.2 from afar); twelve tracked robots packed near the camera cost ~20% more in frames per second, and 0.8 ms of placement per frame for 24 tracks. The garage draws the same shoes and sprockets, motionless (`showBelts`). Taller (`rise`), only its bottom rollers touch the ground (the rays of the others do not reach it) and the robot sits that much higher; wider (`layer`), it has twice as many rollers, hence twice the motors and rated load. Differential steering. **Progressive damage:** each roller carries and pulls on its own; a roller torn off (or carried away by a part that breaks off) does not make the belt disappear: it is rebuilt on the remaining rollers of the same part (`buildBelts`, grouped by part then by `trackGroups`), and splits into two runs if the gap is too large.
- **Energy (`robot/energy.ts`):** thrusters, boosters and hover pads draw (`power`) on the batteries of the cockpit's part; the generator (`GENERATOR_POWER`) recharges more slowly than a flying robot consumes; with empty batteries, the engines only have the generator. A flying robot's AI lands to recharge (`landing`).
- **Damaged engines (`wearEngines`, robot/propulsion.ts, once per step and per robot):** below `ENGINE_WORN` (50%) of its hit points, an engine loses thrust, down to `WORN_OUTPUT` (60%) of its full thrust when spent, and misfires (it cuts out for 0.18 to 0.5 s, at random via `rand`, up to `MISFIRE_RATE` times per second when spent): `Thruster.output` (not transmitted: the replica sees its effect in the thrust) caps each thrust axis, and the hover pilot distributes according to what remains. At 45% when spent, planes fell too often (in battle, twice as many deaths by impact for the Plane and the Bomber). A spent engine that is hit can catch fire (see "Fire").
- **Loop (`client/game.ts`):** accumulator × `timeScale` (slow motion), at most 4 `sim.step()` per frame; `readInput` fills `sim.input` from the keyboard, the mouse, the touch controls and the camera.
- **Mouse look (`client/input/controls.ts`, `input/cameraRig.ts`):** while piloting, a click in the arena captures the mouse (`requestPointerLock`, via `captureMouse`): the mouse turns the camera (`CameraRig.lookBy`, sensitivity and inverted axes in the settings), you aim at the crosshair (`Controls.aimPoint`; the aiming ray starts from the robot's plane: scenery between the camera and the robot does not count, `ArenaGame.aimAt`), and Esc releases the mouse and opens the pause menu (`onRelease`). Holding the right button (or toggling it: `Controls.scopeToggle`) goes to the scope (`PlayerInput.scope`): the camera glides into the selected weapon (just above its turret; with several turrets of the same weapon, in the middle of the highest ones, chosen in the robot's frame so that the choice does not change when it pitches: `ArenaGame.scopeEye`, `CameraRig.setEye`) and zooms in a little (more for the sniper); on entering, it turns toward the last point aimed at from behind (`CameraRig.lookFromEye`, with `ArenaGame.backAim`: the point of the switching frame is already taken at the center of the screen, before the camera turns, and does not count), and on leaving, it turns so that the crosshair from behind falls back on the point aimed at in the weapon (`CameraRig.lookFromBehind`, `scopeAim`): you aim at the same spot from behind and through the scope, and it looks around there as freely as from behind (`CameraRig.eyeBetaRange`): the turret follows up to its stop, as from behind (when limited to the turret's travel, measured against the horizon without accounting for the robot's tilt, it could hardly aim at the ground from a plane); from behind, the camera only looks up 30°, but, behind and below the robot, it aims higher than it looks: on leaving the scope, a view raised higher comes back down smoothly; the mouse wheel does nothing there; in the weapon, your own robot is no longer drawn (`WorldView.hidden`, `LocomotionView.hidden`), nor its muzzle flashes, nor its projectiles within `OWN_NEAR` m of the lens (fired from neighboring barrels, they blocked the view on one side then the other) and labels keep their size on screen; the spread of the player's shots is the weapon's best (see "Accuracy"), and a `scopeOnly` weapon (the sniper) only fires through the scope. While piloting, the camera aims above the top of the robot (`OVER_TOP`, from `Bot.top`): you see over it, even a tall robot; once the robot is destroyed, it keeps that height above the wreck (`ArenaGame.pilotLift`): lowered to ground level, it dove into the wreck when you looked up. It can go below the robot to aim at the sky (`PILOT_BETA_MAX`): its target rises and it moves closer so as not to go under the ground (`CameraRig.update`, zoom requested with the wheel in `zoom`). A piloted plane, as long as it flies, lifts this limit (`CameraRig.setFreePitch`, `freeLook`): the camera turns with no pitch stop, goes through the vertical and upside down (Babylon's `allowUpsideDown`, β wrapped by `betaWithin`), without raising its target (`LOOK_UP_RISE`): the crosshair follows the gaze, and the plane with it, all the way around a loop; `chaseDirection` brings it back behind a direction (the nose), by whichever of its two ways of looking at it is closer. Nor does it go behind scenery: a wall, a pillar, a ramp, a hill between its target and itself, and it moves closer to the robot (`CameraRig.setOcclusion`, with `rayArena`, shared/arena/ray.ts: a raycast on the scenery boxes and the terrain, without physics, which also works online); it comes in at once and goes back out smoothly (`held`). It does not go below the terrain, and the free camera does not go beyond the arena walls (`CameraRig.setArena`, through `ArenaGame.showArena`). The mouse is released as soon as you stop piloting (menu, end of match). With the mouse captured, its buttons are keys like any others (`Mouse0` to `Mouse4`; by default, left: fire, right: scope), read from the `buttons` mask of each event (`Controls.syncButtons`): a second button pressed or released while the other is held only emits a `pointermove`, not a `pointerdown` or a `pointerup`. Headless Chrome refuses the capture: the tests simulate it.
- **Crosshair and scope (`client/hud/reticle.ts`):** each weapon has its crosshair (SVG centered to the pixel on `Controls.aimPoint`: 45% of the height from behind, the exact center through the scope) and its magnifications (`SIGHTS`); through the scope, the edges darken (a round scope for the sniper and the railgun) and the mouse wheel switches from one magnification to another (sniper ×2.5, ×4, ×8). The player's shot subtracts its robot's velocity (the projectile inherits it): it reaches the aimed point even while driving. The crosshair traces the circle the shots will go into (`aimSpread` converted to pixels: it opens up when the robot moves) and, for a precision weapon that movement makes shake, invites you to stay still; the scope has optics (thick posts, fine cross, graduated marks). A gauge surrounds the crosshair (`Gauge`, from `readiness`, combat/arsenal.ts, which only reads the state of the weapons: it also works online): on the right, an arc fills from bottom to top until the next possible shot (white: rate of fire, at the shared rhythm of identical weapons; amber: a round is reloading, magazine empty; red: overheating; blue: batteries of an electric weapon), then fades in a flash; a rate of fire under 0.3 s is not shown. On the left, the magazine (one segment per round, the next one filling during its reload; a single bar beyond 12 rounds), or the heat of an automatic weapon (mark at `RESUME_HEAT`). **Instruments (`client/hud/instruments.ts`):** for a weapon that fires in an arc, a panel next to the crosshair gives the barrel's elevation and the one it is moving toward (with a gauge), the heading, the range and the flight time to the point of impact (or "Out of range": the shell ends its course in the air), and a diamond marks that point of impact on screen (`ArenaGame.gunnery`, `toScreen`); for bombs, a dotted circle on the ground, the size of the explosion, where the next one would fall, with its fall time (`ArenaGame.bombing`); for a flying robot, an artificial horizon (pitch, bank), the altitude, the speed, the vertical speed and the heading.
- **Recoil (`client/render/recoil.ts`):** the simulation pushes the robot opposite each shot (`Weapon.recoil`, applied at the muzzle), but a rifle only moves a robot by a few cm/s. So the client shows the kick, based on `Weapon.recoil` (nothing under 1 N·s: laser, plasma, flamethrower, mines, bombs): on `shot`, it finds the turret whose muzzle is at the shot's origin (`firingTurret`, also works online); its head moves back along the barrel then returns in 0.18 s (`WorldView.kicks`, from 2.5 cm for the rifle to 16 cm for the cannon), and, for a player's shot, the view jumps upward (a little sideways, at random) then returns to where the mouse had left it (`CameraRig.kick`, from 0.3° for the rifle to 2.5° for the cannon through the scope, half as much from behind). The aimed point follows the view: a burst climbs a little.
- **Hit feedback (`client/hud/hitFeedback.ts`):** the simulation emits `hit` (victim, shooter, weapon, destroyed blocks) for each robot hit by a weapon; the game turns it into a marker at the crosshair (stronger if blocks fall, and for a kill), an arc toward the shooter when the player's robot is hit, and interface sounds (`Sound.ui`). The scoreboard (Tab) shows the frames per second (the "Frames per second" graphics setting puts them in a corner).
- **Camera-relative steering** (the "Steering" setting, Controls tab, `Settings.drive`: `camera` by default, as in Robocraft, or `tank`, keyboard; `PlayerInput.relative`): on the ground, ZQSD give a direction on screen, the robot turns toward it, or reverses if it has its back to it (`cameraDrive`, sim/player.ts); a flying robot turns toward where the camera is looking. Keyboard: tank steering, and a flying robot only pivots with yaw. Settings saved before keep their value (`tank`, the old default).
- **Keys and gamepad (`client/input/bindings.ts`, `gamepad.ts`, `controls.ts`):** all commands go through an action table (`ACTIONS`: label, section of the key screen, context where it applies, default keys; pure logic, `tests/bindings.test.ts`); the player chooses their own (`Settings.bindings`: two per action on keyboard or mouse, the mouse wheel included for a one-shot action, one on the gamepad; read by `parseBindings`, which restores the default key for any missing or invalid slot: settings from before therefore have the keys from before). A key is designated by its physical position (`KeyboardEvent.code`: ZQSD on AZERTY, WASD on QWERTY), and named according to the player's keyboard (`codeLabel`: `navigator.keyboard.getLayoutMap()`, otherwise learned while playing, `Controls.learn`; digits remain digits). Each action applies in a context (`InputContext`: always, while piloting, on the ground, in flight, in free camera, in the garage; `Controls.contextOn`; the garage only overlaps itself): two actions that never apply together share a key (Space: brake on the ground, climb or pull up in flight; E: mines on the ground, yaw in flight; F: flares while piloting, next robot in free camera; R: new wave in free camera, rotate in the garage). Assigning a key already taken in the same context (`assignBinding`) removes it from the other action, which receives in exchange the old key of the action being set if that creates no other conflict (otherwise its slot stays empty): the screen says so under the row (`displaced`). Esc (pause, cancel) and the gamepad's Menu button are reserved; pause and the sticks are fixed. **Combinations** (in the garage only: `chordCode`, `isChord`): modifier keys (`MODIFIERS`: Ctrl, Shift, Alt) then a key or a button ("Control+KeyZ", "Shift+Mouse0"); with Ctrl, a letter is read from the typed character (`eventChords`: Ctrl+Z undoes on AZERTY as on QWERTY), the rest from its position. `Controls` only reads the table: `holding(id)` for an action you hold (forward, boost, brake, fire…), `trigger` for a one-shot action (at the moment of the press, `press`); a game key does nothing else in the page (`preventDefault`). **No text writes out a key:** help texts, HUD reminders, part sheets (the flare launcher), robot traits (the Dragster), feed lines (the flight mode), the garage and the key screen cite a key through a parameter (`{key}`) filled in from the table (`keyLabel(action)`, which `Controls` has named by `keyName`: `setKeyNamer`; outside the browser, the default keys in QWERTY), and are redone when the keys or the language change (`ArenaGame.refreshKeyHelp`: the controls table, `keys.ts`; the weapon keys, `Hud.weaponKey`; the HUD reminders, `[data-key-action]` in index.html; "F: flares", mines, scope; `Garage.refreshKeys`); on the gamepad, its buttons (`Controls.keyName`). `bindingName` picks, of an action's two keys, the one that types the letter of its default key on QWERTY: the map and symmetry (M) have the position of the M on a QWERTY keyboard and that of the M on an AZERTY one, and the help says "M" on both keyboards. `tests/keyMessages.test.ts` rejects a key name hard-coded in the message catalogs, and checks that made-up keys appear in the part sheets, the traits and the help texts, in French and in English. **Gamepad** (Gamepad API, standard layout; `GamepadInput`, polled each frame by `Controls.poll`, connection and disconnection detected when polling, indicator at the top left: `PadBadge`): left stick, movement (analog), right stick, camera (`CameraRig.turn`; sensitivity, inverted axes, settings separate from the mouse), adjustable radial dead zone (`stickDeadzone`), RT and LT triggers: fire and scope, then buttons (A: brake on the ground, climb in flight, pull up in a plane; B: descend, push down; X: flares; Y: mines; LB, RB: previous, next weapon; L3: boost, full throttle; R3: cut the throttle; D-pad: map, flight mode, yaw; View: scoreboard; Menu: pause; in a plane, the left stick sets the throttle and turns, the right stick steers it); it aims at the crosshair (`Controls.reticleAim`); behind a menu, it navigates it (`Menu.navigate`: the neighboring control in that direction, or the focused control receives the keyboard arrow: robot list, tabs, sliders; A confirms, B and Menu go back, LB and RB switch tabs; `body.pad-nav` makes the focus visible). Key screen (Settings, Controls): one row per action, by section (on the ground, in flight, weapons, interface, free camera, garage, without gamepad), two keyboard-or-mouse slots and one gamepad slot (`SettingRow` `binding`); click a slot, then the key, the mouse button or the gamepad button (`App.listen`: listens in the capture phase, before everything else, and swallows the press and its release; for a garage action, the combination, a modifier key released on its own counting for itself; Esc or Menu cancel; right-click clears); ↺ resets an action's keys (`resetAction`), "Reset all" resets all of them. **Migration:** the table has a version (`BINDINGS_VERSION`, 2; that of the saved settings: `Settings.bindingsVersion`, absent: 1); `migrateBindings` gives the new default keys to the slots (keyboard, gamepad) of an action that the player had left at the old ones (`FORMER_DEFAULTS`), keeps those they had changed, and leaves empty a slot whose new key already belongs to one of their actions in the same context. Version 2: Ctrl no longer descends (in flight, Ctrl held with the throttle key made Ctrl+W, which closes the tab). The new actions (those of the garage) take their default keys.
- **Touch controls (`client/input/touchPad.ts`):** as soon as you pilot with a finger (`pointer: coarse`, or a first touch), a stick on the left and buttons to hold on the right (fire, climb, descend, turbo); you aim at the crosshair, in the center of the screen (`Controls.aimPoint`); swiping elsewhere turns the camera.
- **HUD (`client/hud/hud.ts`, `matchHud.ts`, `minimap.ts`):** on screen, only the essentials: at the top the score, the time and the zones (`MatchHud`), the kill feed below; at the bottom (`.bottom-dock`) the weapon bar (one key per weapon, ammo or heat; in free camera, the whole catalog as small buttons) then the status of the piloted robot; at the top right the minimap; in a plane piloted with the mouse, a nose marker (`#noseMark`, `ArenaGame.showNoseMark`, `NOSE_MARK_RANGE` m ahead of it) shows where it is going, the crosshair where it will go. The rest is in the **scoreboard** (`Hud.pressTab`/`releaseTab`: holding Tab shows it for as long as it is held, a single press pins it until the next one; by touch, the button under the minimap): the robots of both teams (status, locomotion, structure, and kills and deaths of each slot, the best at the top: a slot passes to the robot that respawns in the same team with the same robot, based on `botAdded`/`botRemoved`, which also works online; reset at each new match), "you" and "player" for the humans, the statistics, the Free Arena tools and the controls (`keys.ts`). **Minimap (`MiniMap`):** north (+z) at the top, west (+x) on the left, like the 3D view; its background (ground, terrain shaded with the colors of `ArenaView.groundColor`, water, paths, static scenery) is computed once per arena (`setArena`), buildings, roofs, tanks and standing trees are on a separate layer, redrawn when one of them falls (based on `propAdded`/`propRemoved`/`propReleased` and the spots), then, ten times a second, the zones (in their team's color, only the hill in play), the robots (an arrow in the team's color, hollow if it flies; only spotted enemies while piloting) and the camera's view cone. In a large arena, it shows the player's surroundings (`MINI_RANGE`, 60 m); M opens the whole map, with the named places (`ArenaLayout.places`). Pause and a new match close the scoreboard and the map (`ArenaGame.closeOverlays`).
- **Shadows (`render/scene.ts`):** cascaded (`CascadedShadowGenerator`, if WebGL 2 is available): several shadow maps along the camera's field of view, fine up close, coarse in the distance; three cascades up to 240 m in a large arena, two up to 110 m in a small one (`applyArenaLook`). A single map framed on the whole Valley was blurry; framed around the robot, it left everything seen in the distance without a shadow. Without WebGL 2, a single map that Babylon frames on everything that casts a shadow (sun 250 m away along the axis of its rays).
- **Loading screen (`client/menu/loading.ts`, `LoadingScreen`, markup `#loading` in index.html):** opaque, above everything (the scene being prepared behind it cannot be seen), a progress bar and the current step. **At startup** (`App.boot`, launched by main.ts): physics, the scene, then, in parallel, all sounds decoded and the title-screen music prepared (`Sound.preload`) and the warm-up of the effects (`ArenaGame.prewarm`); the title screen and its demo wait behind; finally, if the browser waits for a gesture before playing sound (`Sound.needsGesture`), "Click to start" (a click, Enter or Space), and the title-screen music, already prepared, starts with that gesture (it was waiting for the audio context to resume). **Before each match** (`App.play`: local, "Restart", garage trial; and the online match, `connect`: the replica first receives the world, `waitForOnlineWorld`): the arena and the robots are built, the match stays frozen (`ArenaGame.hold`: no simulation, no commands; online, the replica keeps receiving), what it will show and its music are prepared (`prepareMatch`), then it begins (`beginMatch`: `release`, music, mouse). A loading is abandoned by a return to the menu or a dropped connection (`loadTicket`, `cancelLoading`). **Warm-up (`ArenaGame.prewarm`):** one instance of each projectile, mine and indicator light, tracer (`ProjectileView.warmUp`), block fire, engine and turbojet flame, prop fragment of the arena (`WorldView.warmUp`), smoke cloud (`SmokeView.warmUp`), energy wall of each team (`BarrierView.warmUp`), explosion of each look, muzzle flash of each weapon and small effects (`Effects.warmUp`), particle, streak and mark of each kind (`Fx.warmUp`) is placed in front of the camera, a few frames are drawn, we wait for the scene to be ready (`whenReadyAsync`, at most `READY_WAIT` s), then everything is removed (`Effects.clear`, `Fx.clear`). Without this, the first shot of each weapon, the first explosion, the first effect built their model and compiled their shaders in the middle of the match: measured with a GPU, the first shot of each of the 23 weapons caused 7 frames of more than 50 ms (worst 125 ms); afterward, like a second pass. **No top-level `await` on startup in main.ts** (`start()` is launched without being awaited): in production, the shader code chunks, loaded on demand, import the main module, and would wait for it to finish evaluating while it waited for the shaders (the loading screen never finished).
- **Screens (`client/app.ts`):** main menu (Play, Multiplayer, Garage, Settings; a demo battle behind it, `startDemo`), choice of mode then of robot, match (`startMode(id, pilot)`), pause (`frozen`), end of match, garage (the arena is on standby: `suspended`). A screen that has a `back` returns to it with Esc (`Menu.goBack`). A screen can carry content built elsewhere (`MenuView.content`, in the widest panel, which places the focus itself) and release it when it goes away (`onClose`, called when the screen is replaced or closed).
- **Robot picker (`client/menu/robotPicker.ts`, `App.showPicker`):** the same screen everywhere a robot is chosen (match, "Change robot", multiplayer, and "My robots" in the garage, where you also open an unfinished robot or one still to unlock). Filters by locomotion (wheels, tracks, legs, pads, flyers, planes, and "My garage", each with its number of robots, only those that have any), a search (name, description, weapons, locomotion, accent-insensitive) and a sort (game order, cost, name), kept for the duration of the visit; a scrolling list (one row per robot: thumbnail, name, locomotion, weapons, cost; keyboard: arrows, Home, End, Page Up/Down, Enter; mouse: click to select, double-click to choose); the selected robot's sheet: a rotating 3D preview (you turn it with the mouse), description, cost against the budget, mass, locomotion, speed, weapons (×n for several turrets of the same one), parts to unlock, and the button that picks it. The robot chosen last time is selected from the start and marked (`lastPick`, key `casse-robot.lastRobot`). Everything is derived from the design (`robotCard`: `locomotionOf`, `weaponsOf`, `designCost`, `designMass`): a new preset robot or a new weapon finds its place there on its own. **Thumbnails (`render/robotSketch.ts`):** drawn in 2D (canvas, orthographic projection from the front right, shaded faces, faces hidden by a solid neighbor omitted, wheels, track belts (`beltPath`: the facets turned toward the eye, drawn right after the rollers), turret heads and barrels, and what sticks out of the blocks, in the place its clearance reserves for it (`protrusions`: translucent blade disc, nacelle, leg); colors `blockColors`, `wheelColors` from materials.ts), a few milliseconds for the whole list. **Preview (`render/robotPreview.ts`):** its own Babylon engine on its own canvas (the game continues behind it on its own), created at the first robot shown, released with its WebGL context (`loseContextOnDispose`) when leaving the screen; the blocks and what sticks out of them (`stillBlockParts`, render/stillParts.ts: turret heads, blades, nacelles, legs, hover pad glow), the wheels and their fittings (`stillWheelParts`) and the tracks (`stillBelts`, render/belts.ts: belt, shoes and sprocket, motionless), the same functions as in the garage, framed on their bounding sphere (`FRAMING`), and further away if the bounding box of their clearance (`designZones`) would leave the image at one of the angles the preview turns through (`fitDistance`: a 2 m propeller, legs). On a phone, the sheet (reduced preview) stays at the top while the page scrolls, and the list only scrolls with it (`reveal` only scrolls the list: the title and the filters stay in view on opening).
- **Settings (`App.showSettings`, `client/settings.ts`):** Graphics, Controls (mouse, steering on the ground and when hovering, plane piloting, gamepad, then the keys: see "Keys and gamepad"), Sound and Profile tabs (the language first: see "Languages (i18n)"; "Default settings" keeps it, like the name and the server); one row per setting (`SettingRow`: toggle, choice, slider, text, button, information, keys of an action). Each change is saved then applied by `applySettings`, which passes all the settings to the game (methods with no effect if nothing changes: `setShadowQuality`, `setRenderScale`, `setReducedEffects`, `setFxLook`, `setGlow`, `setDynamicLights`, `setHeatHaze`, `CameraRig.setFov`, `Sound.setVolume`, `FpsBadge`); the graphics presets also set the smoke and flames, glow, light flashes and heat haze (low: simple effects, nothing else; medium, the default: realistic effects, glow and light flashes; high: realistic effects and all three; settings from before this setting switch to realistic effects, except those on the Low preset, `parseSettings`); the screen redraws and the focus stays on the control. A new setting: a field in `Settings` (with its default value and its validation in `parseSettings`), a row in the tab, its application in `applySettings`.
- **Ramps (`arena/layout.ts`):** inclined slabs thickened downward, whose underside goes below the ground (no gap where a robot could get stuck).
- **Robot frame:** forward is local +z, left is +x (steering > 0: to the left). Babylon uses a right-handed frame to match Rapier.

## Architecture rules

- `src/shared` never imports Babylon, the DOM or `src/client`. This is checked by `src/shared/tsconfig.json` (no DOM lib) and `tests/architecture.test.ts`. Whatever depends on the browser (the `performance` clock, storage) is provided by the client.
- **No displayed text in `src/shared` or in `src/server`** (see "Languages (i18n)"): a catalog only has identifiers, and what the shared code or the server tells the player is a code with its parameters (`DesignIssue`, `ConflictReason`, `RewardLine`, `Refusal`), which the client translates (client/i18n/names.ts). A new server message: one more code in its type (protocol.ts, `PROTOCOL_VERSION` +1), its text in each language, and its translation in names.ts. Messages for developers (console, errors, server logs) stay in French.
- **Displayed text (recipe):** never a hard-coded string in the client code: a key in the file of its zone, in French (`client/i18n/locales/fr/<zone>.ts`, the source language: the text exactly as it should be displayed, parameters in braces, plurals as `{ one, other }` chosen by `n`) and in every other language (same file, same keys, same parameters: TypeScript checks it), then `t("zone.clé", { … })` where it is displayed; a number goes through `num`, `fixed`, `pct` or `measure` (format.ts, i18n.ts), never `.replace(".", ",")`; a text in index.html, through `data-i18n` (or `data-i18n-title`…). Whatever is built once (a button, a texture) and must follow a language change subscribes to `onLocaleChange` (i18n/state.ts). A string that looks like French without being displayed text (an internal key) is marked `// i18n-ignore`: `tests/i18nSource.test.ts` rejects the rest.
- **Language (recipe for a translator):** copy `client/i18n/locales/en/` to `locales/<code>/` (ISO 639-1 code: `de`, `es`…), translate the values (never the keys or the `{paramètres}` (the parameters); the plural forms the language requires: `zero`, `one`, `two`, `few`, `many`, `other`, following the CLDR rules of `Intl.PluralRules`), rename the exports if needed and check each file against French (`satisfies ZoneOf<typeof fr>`); add the code to `LOCALE_IDS` (i18n/state.ts) and the language to `LOCALES` (locales/index.ts: its name in its own language, `complete(…, true)` for a complete language; without `complete`, a partial language is displayed in English where it is missing); `npm run check`. The units (`unit.*` of `common`) adapt too (symbols, space before the symbol). The language then shows up on its own in the settings, and `detectLocale` picks it for a browser that speaks it.
- `erasableSyntaxOnly` is enabled: no `enum`, no `namespace`, no constructor parameter properties (so that Node can run the server's TypeScript without compiling it).
- Game data lives in typed catalogs, and each entry has its client-side look in an exhaustive `Record`. TypeScript therefore rejects an incomplete addition:
  - **block type:** `BLOCK_TYPES` (`shared/catalog/blocks.ts`, with `cost`, `bond`, `resist`; a light: `light`, its model in `LIGHT_MODELS` and its lens in `LIGHT_LENSES`, render/models/lights.ts, its info-card sentence in `LIGHT_SUMMARIES`, garage/partInfo.ts; a new color, `LIGHT_COLORS`, a new pattern, `lampLevels` and `LAMP_INTENSITY`, render/lightSources.ts; see "Night") + `BLOCK_LOOKS` (`client/render/materials.ts`) + its price in `BLOCK_PRICES` (`shared/design/progression.ts`) + its name in each language (`block.<type>`, i18n/locales/<language>/catalog.ts) and its info card in the garage (its sentence in `parts.ts`, based on what it is: garage/partInfo.ts). A thruster is a block with a `thruster` field (tilt rotor: `gimbal`; flame engine: its jet, `exhaust`), a support a block with `support`, etc. The garage palette builds itself. **3D model (optional):** a block can have its own instead of the textured cube (`BLOCK_MODELS`, render/blockModels.ts, which gathers one file per family in render/models/: propulsion.ts, weaponsDirect.ts, weaponsGuided.ts), and a turret its head (`HEAD_MODELS`); a model is made of vertex-painted primitives (render/modelKit.ts: `box`, `cylinder`, `ring`, `sphere`, `fuse`), merged into one mesh with a single material (thin-instance batches only have one; each instance's wear tint multiplies their colors), in the block's frame (±0.25 m, up +y, forward +z); collisions remain the cube, and in the garage it is targeted through an invisible box of its cell (`Assets.pickBoxSource`). The propulsion parts all have their own (thruster, booster, rotor, propeller engine, turbojet cage, hover pad, leg hip); guided weapons, mines, drop weapons and support: `GUIDED_HEADS` and `GUIDED_BASES` (render/models/weaponsGuided.ts); a mine layer has a symmetrical head (a drum), because it turns half a turn in game but not in the garage, and its chute, facing backward, is in the base; the muzzle of each head falls `barrel` m in front of its axis. A block with a model has no per-instance color (`registerInstancedBuffer`): Babylon does not blend it with vertex colors on regular instances (garage, previews); wheels too (`WHEEL_MODELS`, with its type `WheelModel`: axle along x, symmetrical; render/models/wheels.ts: tire with chevron lugs, rounded sidewalls, spoked rim, nuts, hub cap, orange rim for a steered wheel, deep lugs and a bead ring for a heavy one, smooth tire for a caster; the track rollers in render/models/tracks.ts); **visible ammunition**: a head can show its rounds separately (`HEAD_ROUNDS`, `Rounds`: a round and its slots in the head, in firing order; missiles, anti-air, rockets, lock-on missiles, warhead, bombs, smoke canisters), placed under the head by `Assets.addRounds`; in game, `WorldView.syncRounds` only shows the share of the magazine that remains (`visibleRounds`, render/rounds.ts: at least one as long as a round remains, the first slots go first, based on `Turret.arm.ammo`, which also goes over the network), and a reloaded round slides back into its slot (`ROUND_RETURN`); the head has a dark muzzle on the front face of each tube (the model kit's tubes are solid);
  - **block shape:** an entry in `SHAPE_SPECS` (`shared/catalog/shapes.ts`: half-spaces that cut the cube, one or two convex pieces, and its mirror symmetry, `swap`), then block types `shaped(matière, forme)` (mass, hit points and cost in proportion to volume; their name in each language: `block.<type>`); collider, rendering and mass follow from it; its inventory subgroup (`SHAPE_GROUPS`, garage/partInfo.ts) and its info-card sentence (parts.ts);
  - **wheel type:** `WHEEL_TYPES` (`shared/catalog/wheels.ts`) + `WHEEL_LOOKS` (`client/render/materials.ts`) + `WHEEL_PRICES` + its name in each language (`wheel.<type>`). Four kinds (`wheelKind`): fixed, steered (a `steering` field), caster (`caster`), track roller (`track`); the garage palette sorts them by kind;
  - **weapon:** `WEAPONS` (`shared/catalog/weapons.ts`, with `engage`, its preferred range for the AI, and `handling`, how it handles) + `MUZZLE_FLASH` (`client/render/effects.ts`) + `SHOT_TONES` and `SHOT_SOUNDS` (`client/audio/sound.ts`: fallback synthesized sound, and recorded sound, a sound from `SAMPLES`) + `SIGHTS` (`client/hud/reticle.ts`: crosshair, scope zoom levels, scope lens or darkened edges) + its name in each language (`weapon.<id>`, catalog.ts; the kill cause in the feed follows from it); the projectile's look follows `projectile.look` (a new look: its light in `PROJECTILE_LIGHTS`, client/render/lightSources.ts), and that of its explosion `explosion.look` (effect in `EXPLOSION_STYLES` and, with realistic effects, in `FIREBALLS` (render/fx/blastFx.ts), noise in `EXPLOSION_SOUNDS`, ground marks and embers in `CRATERS` (render/fx/blastFx.ts), light in `BLAST_LIGHT` (render/lighting.ts): exhaustive `Record`s). A turret is a block type with `turret` + its head in `TURRET_LOOKS` (`client/render/models.ts`); its head and its base (the block) can also have a 3D model (render/models/, by family: `DIRECT_HEADS` and `DIRECT_BASES` for direct-fire and explosive weapons, in weaponsDirect.ts), which takes precedence over the box and tubes of `TURRET_LOOKS`: the barrel's muzzle falls `TurretSpec.barrel` in front of the head's axis, and the base rises as a pivot up to just under the head (`TurretSpec.height`), two values read from the catalog; `TurretSpec.head` (head dimensions) and `caliber` (barrel diameter) give its hitbox, to be kept in agreement with the model; a weapon without an aimable turret (mines, bombs) sits on a fixed turret (`TurretSpec.fixed`); a mine has its 3D model in `MINE_MODELS` (`client/render/models/mines.ts`, exhaustive over `MineWeaponId`, which TypeScript infers from the catalog: ribbed disc with a pressure plate, coils and dome of the EMP mine, tanks of the incendiary mine, vented canister of the smoke mine, mound and antennas of the bouncing mine, missile tube and radar of the anti-air mine, box on legs and antenna of the remote mine, tripod and lens of the sensor mine, dome on suction cups of the sticky mine; origin at the laying point) and its indicator light separately (`light`: color, position, `Blink` pattern), a glowing bead (`Assets.mineLightSource`) attached to the mine by `ProjectileView`, lit only once the mine is laid or stuck, which blinks at its own pattern (`blinkOn`: short flash, pulse, double flash, fast; offset from one mine to the next);
  - **prop:** `PROP_TYPES` (`shared/catalog/props.ts`; `burns` if it is wooden; a lamp, its night light in `PROP_LIGHTS`, client/render/lightSources.ts, and its glass in `PropModels.setNight`) + `PROP_LOOKS` (`client/render/propModels.ts`: painted, with staves and a conical roof for the water tower, building material, tree (fir, oak, palm, kapok), cactus, car (whole or burned-out shell) or street lamp; blackened in steps) + `BREAK_SOUNDS` (`client/audio/sound.ts`) + its name in each language (`prop.<type>`), and its spots in the arenas (`ARENAS[id].props`, `shared/arena/layout.ts`);
  - **arena:** an entry in `ARENAS` (`shared/arena/layout.ts`; at night: `sky.night`, and lamps, see "Night"), its name and its menu sentence in each language (`arena.<id>`, `arenaInfo.<id>`, i18n/locales/<language>/world.ts) and its map places (`places`: a `PlaceId`, a new one if needed, and its name `place.<id>`), nothing else on the client side (except its ambience, `AMBIENCES` in client/audio/sound.ts; the Canyon reuses the Fortress's, Volcanic Island the Valley's, the City the Trenches', the Harbor the Depot's): the menu offers it on its own, and the server adds it to its rotation. Its ground palette (`ground`), the look of its boxes (`StaticBox.look`, `BoxLook`: a material in `ArenaView.lookMaterial` — the harbor's in `HARBOUR_LOOKS`, a drawn texture and its tiling — and a color in `LOOK_COLORS` of the minimap), its navigation (`navGrid` or `nav`), its lava and its waterfalls are optional; they are drawn from its data (ArenaView: `groundColor(…, arena)`, the lava as emissive terrain triangles under a scrolling crust, the waterfalls as scrolling curtains, `update` every frame; minimap: darker deep water, orange lava) and `terrainFx` (render/fx/terrainFx.ts) makes the fumaroles smoke (the crater's plume can be seen from everywhere), the lava bubble and the waterfalls spray;
  - **community map:** a file `maps/<nom>.casse-map.json` (docs/maps.md), and nothing else: the menu, the server, the tests (`tests/communityMaps.test.ts`: validation and a battle on each one) pick it up on their own. **Format field:** its type in `MapFile` (map/format.ts), its bounded reading in read.ts (a malformed field is a `MapIssue` `field`, never an exception), its conversion in build.ts, its check in validate.ts if needed, its paragraph in docs/maps.md; a change that makes existing maps unreadable bumps `MAP_FORMAT` to the next version, with its migration (`MAP_MIGRATIONS`, read.ts). **Prefab:** a case of `MapPrefab` (format.ts), its reading (`readPrefab`), its expansion (`expandPrefab`, prefabs.ts: bounded, built at the origin then rotated and placed), its paragraph in docs/maps.md. **Map issue:** a `MapIssue` code and its text in each language (`mapIssue.<code>`, i18n/locales/<language>/maps.ts; `mapIssueText`, names.ts).
  - **AI mode:** `AiMode` (`shared/sim/entities.ts`) + its shade in the scoreboard (`MODE_TONES`, `client/hud/hud.ts`) + its name in each language (`aiMode.<mode>`, world.ts);
  - **game mode:** an entry in `GAME_MODES` (`shared/modes.ts`), and its name and its menu sentence in each language (`mode.<id>`, `modeInfo.<id>`, world.ts): the menu lists it on its own (`listed`).
  - **preset robot:** an entry in `PRESETS` (`shared/design/presets.ts`, without a name: its identifier makes up `PresetId`) + its name and its short description in each language (`bot.<id>`, `botTrait.<id>`, i18n/locales/<language>/bots.ts);
  - **kill cause** (`KillCause`, other than weapons), **design flaw** (`DesignIssue`), **what a part reserves** (`ZonePart`), **credits line** (`RewardLine`), **server refusal** (`Refusal`): one more code, and its text in each language (`cause.<id>` in world.ts; `designIssue.<code>`, `zonePart.<id>` in design.ts; `reward.<kind>`, `refusal.<code>` in net.ts);
  - **player action (key):** an entry in `ACTIONS` (`client/input/bindings.ts`: section, when it applies, conflict-free default keys, checked by `tests/bindings.test.ts`) + its label in each language (`action.<id>`, and if needed its detail `actionDetail.<id>`, i18n/locales/<language>/keys.ts), then its effect in `Controls` (`trigger` for a press, `holding` for a held action); the key bindings screen shows it on its own. A key that does not type a character has its name in each language (`NAMED_KEYS`, `key.<code>`);
  - **effects system:** a file in `client/render/fx/` (an `FxFactory`) and a line in `FX_SYSTEMS` (fx/systems.ts).
  - **map editor palette item:** an entry in `PALETTE` (shared/map/palette.ts: its tab, its group, the element it places with its default values, or `trace` if it is traced point by point) and its name in each language (`editor.palette.<id>`, `NamedPaletteId`; a prop or a box take `prop.<type>`, `editor.boxKind.<sorte>`); a new kind of element in the format (a list of `MapFile`): its list in `ElementList` and `ElementOf` (shared/map/edit.ts), its form in `FORMS` and `formOf` (shared/map/fields.ts; its fields with the bounds of the reader, which tests/mapEditor.test.ts checks; their names `editor.field.<clé>`, `editor.kind.<formulaire>`), and its overlay if it does not show up in the game's rendering (`showOverlay`, editor/editorView.ts); a new field: one line in its form;
  - **map editor tool:** an entry in `TOOLS` and `TOOL_ACTIONS` (client/editor/tools.ts), its action (`editorTool<Nom>`, at the end of the "Map editor" section of `ACTIONS`), its name and its help text in each language (`editor.tool.<id>`, `editor.toolHint.<id>`), its panel (`EditorUi.renderPanel`, editor/editorUi.ts: TypeScript demands it) and what a click does with it (`MapEditor.onPointerDown`).
  - **melee weapon** (catalog/melee.ts, see "Melee weapons"): an entry in `MELEE_WEAPONS` (`MeleeSpec`: motion, axis, hub, blade or arm, hit, `engage`); a block type with `melee` in `BLOCK_TYPES` (mass, including that of the moving part, hit points, cost, `resist`, a solid `bond`) + its price in `BLOCK_PRICES` + `BLOCK_LOOKS`; its name and that of its block in each language (`melee.<id>`, `block.<type>`); its moving part in `MELEE_MODELS` (render/models/melee.ts: in the block's frame, origin at the hub, at angle 0, along `e1`; its dimensions read from the catalog) and its base in `MELEE_BASES`; its sight in `SIGHTS` (hud/reticle.ts); its sounds in `MELEE_SOUNDS` (client/audio/sound.ts: sounds from `SAMPLES`, or a borrowed sound played at another pitch, `MeleeSample`; null: the game synthesizes it, as it does while a file is not loaded). TypeScript demands these `Record`s (and `BLOCK_LOOKS`, `BLOCK_PRICES` for the block); a new look (`look`) adds to `MELEE_ZONES` (clearance.ts) if what it reserves is made of several pieces, its name in each language (`zonePart.<look>`, design.ts), what sets it apart in the weapon bar (`hud.meleeTag.<allure>`, i18n/locales/<language>/hud.ts), and its synthesized hit in `energyHit` (sound.ts) if it is not a clang of steel, its effects in `meleeFx` (by look). A weapon that glows (an energy weapon) has its glowing part in `MELEE_GLOWS` (render/models/meleeEnergy.ts), and the voice of its loop in `MELEE_SOUNDS[id].tone`. Massless: `gyro`, `unbalance`, `mass`, `reaction` at 0 and `fling`, `recoil` at 0; one that goes out without power or in water: `quench`; one that sets fire to what it hits: `hit.ignite`; one that stuns locally: `hit.stun`. A new look also adds its pattern spacing (`STROBE_GAP`, meleeView.ts) and, for a rotor, its info-card sentences (`parts.meleeSays.<allure>`, `parts.meleeGyro.<allure>`, i18n/locales/<language>/parts.ts, read by garage/partInfo.ts). A blade with arms (`SweptRing.arms`) has a hitbox that rotates and, like an energy blade or a biting blade, the blur disc; a solid blade, a cylinder (or boxes, if hollow: `inner`); a ring around the robot (`inner` ≥ 0.8 m, `allAround`) and its web (`web`) are reserved as a tube and a disc. A rotor that bites the ground (an upright disc): `hit.ground`. A rotor driven by its block's engine (motion `driven`, `drive`) has no moving part of its own (`MELEE_MODELS` null: the engine's is enough) and is neither wielded nor commanded (`wielded`). Nothing else for a rotor (`spin`, `driven`), an arm (`swing`), a point (`thrust`) or a field (`field`): spin, hits, ricochet, gyroscope, imbalance, hitbox, network, AI, controls, gauge, rendering, effects, clearance, still drawing (`stillMelee`) and info card follow. A weapon that grinds instead of striking: a rotor with `bite` (`BiteSpec`: cutting power, feed direction `radial` or `axial`, grip, gear reduction, depth); the bite, its progression, its forces, the snapshot, the AI (charge, `meleeSkim`, `chargePoint`), the continuous effects, the grinding sound (`RotorTone.grind`, optional; `MELEE_SOUNDS[id].bite`, the recorded cutting loop) and the info card follow; a drill bit is a blade longer than it is wide (`isBit`). A new motion (like the flipper, the flail and the jaw, in combat/mechanics.ts): one more case in the `switch` of `updateMelee` (exhaustive over `motion`) with its functions in combat/melee.ts or a file of its own (build on `meleeFrame`, `stepRegime`, `powerOk`, `pathContact` (`headContact`, `tipContact`), `rotorContact`, `landHits`, `effectiveMass`, `precess`), its command in `operateMelee` (ai/brawl.ts) and `operatePlayerMelee` (sim/player.ts), its pose in `placeMoving` and `MeleeRig.pose` (render/meleeView.ts), its clearance in `meleeSolids`, its gauge in `meleeReadiness`, its rest position in `restSwing`, and the state the replica needs in the snapshot (snapshot.ts) if `spin`, `phase` and `swing` are not enough (a block and numbers per weapon: `mechanicsState`, `applyMechanics`); its extra moving pieces in `MELEE_PIECES` (render/models/melee.ts) and their still pose in `stillMechanics`. One test per rule in tests/melee.test.ts (tests/meleeEnergy.test.ts for energy weapons, tests/meleeBite.test.ts for the biting ones, tests/meleeMechanics.test.ts for mechanical strikes, tests/spinners.test.ts for the spinners, the propeller and the hitboxes).
  - **part that sticks out of its cell** (a head, blades, a nacelle, a leg, a wheel of a new kind…): its clearance in `blockZones` or `wheelZone` (shared/design/clearance.ts; what it reserves has a `ZonePart` and its name in each language, `zonePart.<id>`), with its dimensions as shared constants (like `BLADES`, `JET_NACELLE`, `headLift`) that the renderer reads too, and its still drawing in `stillBlockParts` or `stillWheelParts` (render/stillParts.ts): the garage then rejects whatever would get in its way, and the drawing matches what it reserves. Otherwise, the garage lets a block be placed through it.
- A robot design is JSON data (`RobotDesign`): `spawnBot` rejects a design that does not pass `validateDesign` (a single cockpit, all blocks connected, wheels on an existing block, a wheel underneath on a free cell, rollers stacked within their limits, no overlapping wheels, budget). A design from a previous version (a steered wheel was a fixed wheel with `steer: true`) is read back with `upgradeDesign`: the garage (storage.ts) and the server (room.ts) do so when loading it; `validateDesign` rejects a leftover `steer`. Two overlapping wheels push each other apart: one stays lifted, its suspension crushed (a standard wheel is 1.1 m in diameter: two wheels on the same side are at least three cells apart).
- Randomness goes through `shared/math/scalar.ts` (`rand`, `randSign`), so that it can be made deterministic later.

## Physical model of a robot (to be kept)

- Block grid of 0.5 m. Integer grid coordinates, keys `"x,y,z"`.
- Each block type has a nominal mass and hit points (`BLOCK_TYPES`). Armors form a scale: light (40 HP, 0.5 kg), normal (100 HP, 1 kg), heavy (250 HP, 2 kg, resists bullets); reactive armor (90 HP) stops explosions but is vulnerable to piercing. The cockpit has 800 HP: it is the structure rule that takes a wrecked robot out of the fight. Reference values (tuned with `npm run battle`): rifle 22 damage (two bullets for light armor), sniper 220 piercing, cannon 40 plus 120 splash over 1.2 m, missile 70 plus 150 over 1.4 m, laser 16 (`energy`, 10 shots per second, 0.15 kJ each), railgun 380 piercing (10 kJ per shot), shotgun 9 pellets of 20 (180 at point-blank range, scattered at a distance), rockets 20 plus 55 over 0.9 m (salvos of 8), plasma 13 `energy` 20 times per second up to ~27 m (3.5 s before overheating), bombs 60 plus 170 over 2.4 m (strings of 8, four per second), horizontal spinner 288 cut from a clean hit at full spin (plus 100 to each neighbor), pneumatic hammer up to 330 impact, circular saw 450 cut per second at full spin and ~234 under load, drill 480 and ~200 (both bore from one block to the next), vertical spinner 240 cut from a clean hit at full spin, drum 89 (231 on a wheel), shell spinner 173, cutting propeller 119. The standard wheel has 50 HP: three rifle bullets rip it off.
- **One rigid body per part** (`part`), with merged colliders. Never one body per block.
- All the parts of a robot share the same local frame. When a part is split off, the new body is created at the same pose as the parent, and the blocks keep their local coordinates.
- On destruction (or when a link breaks): the connected components are found (6-neighborhood, ignoring broken links), and the component that contains the cockpit keeps the body (otherwise the largest one). The others become new bodies, with the parent's velocity at the point of their center of mass.
- **Wheels:** a wheel is mounted on a face of a block (`WheelMount`: block, side `dx`/`dz`, or underneath `dy` = -1, offset `shift` of half a cell along the face; its axle always follows the x axis); a wheel that pivots (steered, caster), on a left or right side, is moved away from it so it can pivot without entering it (`steerClearance`); a track roller on a side stacks: `rise` (-2 to 2 cells higher or lower, with no block behind it) and `layer` (0 to 2 rollers outward); `wheelLocalPos` gives its position, and everything (physics, replica, overlaps) goes through it. A caster placed under a block touches the ground at the level of a heavy wheel placed on its side. A track roller hangs 12 cm below its block (`WheelTypeDef.drop`): without this ground clearance, the edge of the Tank's hull touched the slightest rise in the terrain and carried the robot. **Raycast wheel (`robot/wheels.ts`):** when mounted, a wheel has neither a body nor a joint. At each step (`stepWheels`, before the physics), a ray goes from the top of its suspension toward the bottom of the part and only sees the ground and the static scenery (nothing that moves: the wheel would climb onto it all at once); a ray starting inside an obstacle carries nothing. If it hits, a spring-damper (tuned for `ratedLoad`, with a bump stop at the end of travel) pushes the part at the contact point, and the tire applies there the motor's traction and its lateral grip, together within the limit of `grip × appui` (grip × load; friction circle: a pivoting track no longer holds sideways). Suspension and lateral grip are **implicit**: each wheel computes its force from the part's velocity at the end of the step and its effective mass at the contact point (mass and inertia of the part), then leaves this velocity to the following wheels, like a constraint solver; when explicit, the damper of a light part with widely spaced wheels (the Tank) reversed the motion from one step to the next. The forces of a part add up and go to Rapier in two calls. Steering angle (`steer`), travel (`travel`), rotation (`spin`, `spinRate`) and load (`load`) are plain numbers, from which `placeWheels` deduces, after the physics, the pose of the wheel (`Wheel.rb`) and of its hub carrier (`Wheel.hub`), `WheelPose`s read like bodies by the renderer, the shots and the network. The wheel's collider, attached to the part at its rest position, carries its mass, receives shots and pushes crates and robots. Ripped off (`releaseWheel`), it becomes a real body again (`Wheel.body`), which rolls and bounces. **Wreck:** once ripped off, it keeps a share of its hit points (`WHEEL_WRECK_HP`) and gives way under hits and explosions (`discardWheel` at the end of the damage batch: its body disappears, `wheelRemoved`, a burst of fragments); it also disappears on its own after `WHEEL_WRECK_LIFE` (30 s, `expireWheelWrecks`): no more invincible wheels cluttering the field. Once removed, it no longer has a part or a body, keeps a frozen pose (a freed body is never read again), and leaves the snapshots; the replica unmounts it when it receives `wheelGone` (ripped off and destroyed between two frames, it still thought it was mounted). A wheel follows the part of its supporting block (`moveWheel`), and it is ripped off if that block is destroyed (`releaseWheel`). Only the wheels of the cockpit's part are powered and steered.
- **Three kinds of wheels (`catalog/wheels.ts`):** fixed, steered (same size, `STEER_EXTRA` more hit points and more expensive to unlock: `steered`, `smallSteered`, `heavySteered`, given by `steeredVariant`), caster (`caster`). These are separate types (no longer a "steered" checkbox). **Steered wheels (`robot/steering.ts`):** the steering angle reaches the setpoint at the rate `steering.rate` (`aimWheel`); unpowered, a steered wheel keeps its steering angle and slides sideways (`LOOSE_STEER_GRIP`). `driveWheels` follows Ackermann geometry: center of rotation on the line of the fixed wheels (without a fixed wheel, level with the center of mass; casters do not count); each driven wheel turns at the speed of its own path (differential). Without a powered steered wheel, differential steering (`BotProfile.turn`). **Caster:** a free-swiveling wheel with no motor (`stallTorque` 0: never `engaged`, it rolls freely), which pivots toward the velocity of its contact point (`swivel`, robot/wheels.ts: the faster it rolls for its trail `caster.trail`, the faster it swivels, at most `SWIVEL_RATE`; in reverse, it turns around; only on the ground) and barely holds sideways (`CASTER_SIDE_GRIP`); its long downward travel keeps it in contact. It serves as a support: tail wheel of planes, a two-wheel-drive robot that pivots on the spot. Its swiveling goes through `Wheel.steer`, like a steering angle (snapshot, replica). The cruise speed of a garage robot does not count its casters (`cruiseSpeed`).
- **In-wheel motor:** torque = `stallTorque × (tension − ω / freeSpeed)`, capped at `stallTorque`, the wheel rolling without slipping (ω = contact point speed / radius); disengaged (`engaged` false: freewheeling, stun, brake), a slight drag (`FREEWHEEL_DRAG`); in ratchet freewheel (`overrun`, boost), torque that would go against the command is replaced by this slight drag; braked (`brake`), see "Boost and brake". The voltage follows the command with a ramp (`DRIVE_RAMP`). The suspension is tuned for the nominal load of the wheel type (`ratedLoad`) and sags beyond it.
- **Block orientation:** a block can have a `facing` (its up and its forward among the robot's 6 axes, 24 orientations). An engine pushes toward the top of its block: toward the top of the robot it is a lift rotor (`lift`), toward the front a booster (`cruise`), sideways a tail rotor (`trim`). A turret aims in its block's frame (`aimAngles`, `lineOfFireBlocked`, `buriedTurrets`: everything follows its up): placed on a side, it sweeps that side; under a block (`HANGING`), the underside. The mirror image of a block (`mirrorFacing`, `DesignGrid.pair`) reflects its up and its forward; for a shape whose symmetry swaps its left and its front (the corners), its forward becomes the reflection of its left, otherwise the mirror image would be the same corner rotated.
- **Shaped blocks (`catalog/shapes.ts`):** wedge (prism, 45°), corner (two slopes that meet, like a hip roof), inner corner (two crossed wedges: two convex pieces), round (quarter cylinder with six facets), round corner, low slope and high slope (a 27° slope over two blocks), half block; each shape is the intersection of the cube and half-spaces (block frame: left +x, up +y, forward +z), its underside solid, its slope facing up and forward; `shapePieces` turns them into polyhedra (faces, vertices, volume, computed once), whose convex hull the physics takes (`ColliderDesc.convexHull`) and whose faces the renderer takes (`shapeVertexData`, materials.ts: flat-shaded; an axis-aligned face takes the panel like the cube face that carries it, a slanted face takes it stretched). In light and normal armor (and heavy for the wedge and the corner, the glacis pieces): mass, hit points and cost in proportion to volume (`shapeFraction`); same material, same resistances. A ray that hits a slope finds its block through the grid cell (`hitTargetOf`). The grid remains the source of truth for everything else (links, lines of fire, splits): a shape occupies its whole cell.
- **Aerodynamics (`robot/aero.ts`):** flat-plate lift and drag per wing or control surface; the mixer `steerSurfaces` converts the stick into deflections based on the actual effect of each control surface. **Runs (`robot/surfaces.ts`):** control surfaces end to end along their span (same type, same up, same forward, linked: same part, link intact) form a single control surface (`flapRuns`, `flapGroups` for the cockpit's): the mixer reasons per run, with the combined effect of its blocks, and all its blocks deflect by the same angle (a run that has just formed starts from the average of its blocks). A block destroyed in the middle cuts the run in two, a part ripped off takes its own with it (and the mixer only deflects the cockpit's). Two runs one behind the other remain two control surfaces: the mixer uses the difference between their lever arms (with a single set per aileron over two chord rows, the Plane could no longer hold its altitude in a tight turn and crashed in `tests/aircraft.test.ts`). Per run rather than per block, a one-piece elevator no longer helps with roll: the Plane rolls at 96°/s instead of 101 (stick fully over, manual flight), the Bomber at 97 instead of 101, the Fighter at 143 instead of 147; pitch unchanged (74, 68, 94°/s); the AI's planes do not crash more (three planes per team, six 150 s battles, the same flight time: 52 fatal impacts instead of 68 at the Depot, 133 instead of 127 in the Valley). The hinge (`hingeChord`, drawing only): at the leading edge if a block precedes the run, at the middle of its chord otherwise (single-block aileron); `carrierCell`: the run of control surfaces just ahead, which carries the second one. The network snapshot gives only one deflection per run, named after one of its blocks; the replica finds the same runs from its live blocks and their parts.
- **Plane pilot (`ai/pilot.ts`):** instruments (`instruments`), desired bank (L1 guidance on the circuit for the AI, or on its attack circuit for a bomber, `bombingRun`; `bankToward`), then flight (`fly`: attitude, stick, integral elevator trim, throttle). The AI only goes through that; the player, through `flyMouse` or `flyManual` (see below), and `holdPlane` while their warhead is in flight. **Turns:** it does not bank more than its wings can carry at its speed (`sustainableBank`: maximum lift of the surfaces in level flight, before stalling, relative to weight, with a margin; the Plane at 13.5 m/s holds ~45°, a large wing or more speed allow more), at most 43° for the AI; in a turn, the elevator pulls extra based on the load factor (`TURN_PULL`); too far below the desired altitude, the bank decreases (`LOW_START`, `LOW_SPAN`: a turn held at its tightest ended on the ground), likewise near the ground (the ground below: the terrain ahead of the plane makes it climb, but no longer limits its bank) or when it sinks. The control surfaces deflect 29° (at 20°, the Plane only rolled at 17°/s; it now rolls at ~45°/s, with full-chord ailerons at the wingtip). **Limits:** the autopilot takes over beyond the walls, but at least `CIRCUIT_ROOM` (18 m) beyond the circuit: in a small arena, the circuit runs along the walls, and it took over as soon as you turned outward. An arena can impose a floor altitude on the AI (`ArenaBounds.airFloor`: 23 m in the Valley, above the chimney and the trees; planes spawn there at that height, and the player can climb 12 m higher than elsewhere). Without an engine it glides (`gliding`). **Weakened engines** (`Instruments.power`, the share of their full thrust that its propulsion engines can deliver): below `WEAK_SLOW` of its cruise speed, speed comes before altitude (it gradually takes the gliding attitude instead of pitching up until it stalls); low (`GROUNDED` m) without the thrust to climb back (`TAKEOFF_POWER`), it lands: throttle cut, wings level, nose slightly up (`FLARE`), then it stops, stranded (`stranded`: the match self-destructs it if it stays there). Otherwise it skimmed the ground at full speed and hit the scenery, or rolled along its circuit until it hit a wall (the Plane with its engine at 25% crashed seven times out of eight; `tests/engineWear.test.ts` lands it on the Valley's runway). **Manual flight (`flyManual`):** the player holds the stick and the throttle, with no help except damping on each rotation (`ROLL_DAMP`, `PITCH_DAMP`, `YAW_DAMP`: stick released, the plane stops turning and keeps its attitude, the elevator trim adjusting itself, `AUTO_TRIM`); loops, rolls, flat turns with the rudder, gliding with the throttle cut; beyond its limit, the autopilot takes over (`awayFrom`, as tight as its wings allow: `returnBank`, `RETURN_BANK`) and holds the altitude it was flying at (`ai.alt`, at least `RETURN_ALT`). **With the mouse (`flyMouse`, `MouseFlight`):** as in Robocraft, the plane goes where you look. An instructor (`instructor`) judges the deviation on the flight path (the velocity), not on the nose (in level flight, the wing lifts with the nose slightly up: a direction straight ahead seemed to be below the nose, and it rolled the wrong way, in a spiral): almost straight ahead (less than `LEVEL_OFF` rad), it corrects with the elevator and the rudder, wings level (`PATH_GAIN`, trim `TRIM_RATE`); beyond that, it rolls to put the desired direction above the nose and pulls (fully at `LEVEL_OFF + BANK_SPAN`); a direction below the nose, within `PUSH_MAX`, is taken by pushing; a roughly horizontal direction, to the side or behind, that would require rolling more than `ROLL_FREE`, it takes in a banked turn without exceeding what its wings can carry (`sustainableBank`, between `MIN_HARD_BANK` and `HARD_BANK`, less near the ground, `low`, and less if it sinks below the desired direction, `SINK_SPAN`): it no longer lies on its side; but a direction above it (the raised view that keeps going) is taken by pulling, without rolling: a loop, on its back, then it comes back. It does not pull (or push) beyond `AOA_LIMIT` of angle of attack (`AOA_GAIN`): pulling more made it stall. The rudder follows the turn (coordinated turn) and, almost straight ahead, aims a little (`RUDDER_AIM`). The player's throttle (`power`) sets a desired speed, from `SLOW_SPEED` to `FAST_SPEED` times its cruise speed (raw throttle meant nothing from one plane to another: at 60%, the Fighter went three times faster than the Plane), more when climbing (it does not stall in a loop); below `ENGINE_CUT`, engine cut, it glides. With the keyboard, without a look direction (`mouseTarget`): the target direction is the flight path, turned by `KEY_TURN` toward the side of the turn, raised by `KEY_PULL` above the nose (pull up: held, a loop) or lowered by `KEY_PUSH` (dive); with nothing pressed, it flies straight and level; the rudder, a flat turn. **Limit:** the instructor checks it where the plane will be in `BOUNDARY_LEAD` s (`awayFrom(f, true)`), and beyond it, instead of following the look, it aims for the planes' circuit, a little above the horizon (`RETURN_CLIMB`), at cruise throttle (`CRUISE_SETTING`), taking full control halfway: the autopilot, which gives priority to altitude at the foot of the mountains, turned too wide, and the plane hit the Valley's invisible limit. Measured (`tests/mouseFlight.test.ts`, in the Valley): looking 69° to the left and 11° up, the flight path gets there (67°, 12°), likewise to the right; the view raised continuously at full throttle, a full loop (360° of pitch, on its back, never lower than 48 m), then it levels off toward the center; pull up held on the keyboard, a loop too; turning with the keyboard, 93° in 4 s; full throttle 19 m/s, idle 13, without changing its path. `fly` splits into `flightControls` (stick and throttle of the autopilot) and `applyControls`. A plane's propeller loses thrust only with airspeed (`propellerFactor`): a thrust "hole" at high speed comes from the autopilot reducing the throttle to hold `profile.speed`.
- **Hover (`flyToward`):** desired force and torque using the body's actual inertia, distributed among the thrust axes of the thrusters by bounded least squares (`boundedLeastSquares`) with priorities: attitude > thrust > yaw. When the player pilots it (`yaw`: desired yaw rate and assistance), yaw is actively held (`YAW_KP_PILOT`), the propellers may become more unbalanced for it (`YAW_SHARE_PILOT`, `WEIGHT_YAW_PILOT`), and the cockpit's gyroscope makes it pivot as long as A or E is held and for a moment afterward (`GYRO_KP`, `GYRO_ACCEL`): the reaction torques of a Drone's propellers only give ~0.2 rad/s² (it needed 7 s to stop turning). Outside these moments, the gyroscope does nothing: a helicopter that loses its tail rotor still spins on itself. A tilt rotor (`gimbal`) adds two tilt axes (swashplate, response `TILT_TIME`); a tail rotor (`trim`) makes yaw firmly controllable. No assistance: with 3 thrusters out of 4 the Drone can no longer hold its altitude; with 2, it falls; without a tail rotor, the Helicopter spins on itself. A helicopter's rotor must be directly above its center of mass, otherwise its tilt saturates.
